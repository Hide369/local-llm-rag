# Markdown取り込みとサブフォルダ対応 設計書

作成日: 2026-08-12

## 1. 目的

`source/家電製品/` に置かれた30件のMarkdown製品仕様書を、既存のRAGチャットから
検索・引用できるようにする。あわせて `source/` の走査をサブフォルダまで広げ、
資料を分類して置ける構成にする。

## 2. 現状なぜ取り込めないのか

独立した2つの理由がある。

1. **サブフォルダを見ていない。** `scripts/ingest_source.py` の `_target_files` は
   `source_dir.iterdir()` で直下だけを列挙し、`path.is_file()` でディレクトリを弾く。
   `家電製品/` の中身には到達しない。
2. **`.md` が未対応。** `ingest/parsers/__init__.py` の `_PARSERS` は
   `.pdf` / `.docx` / `.pptx` の3つだけで、`SUPPORTED_SUFFIXES` による絞り込みで
   `.md` は落ちる。

したがってUIの「差分を取り込む」を押しても結果は変わらない。両方を直す必要がある。

## 3. 前提と用途

- **用途は個別照会と横断比較の両方。** 「UD-0900iの設置寸法は」のような特定機種の
  照会と、「9キログラムで静かなモデルは」のような条件からの絞り込みの双方を想定する。
- **既存コーパスと同じコレクション（`local_docs_v2`）に統合する。** チャットは1つのまま、
  社内文書にも製品仕様にも答えられる状態にする。
- 完全ローカルで動作するという前提は変わらない。新しい外部依存は追加しない。

## 4. 対象データの実測

`source/家電製品/*.md` 30件を計測した結果。設計判断はすべてこの数字に基づく。

| 項目 | 実測値 |
|---|---|
| ファイル数 | 30 |
| `##` セクション総数 | 181（1ファイルあたり5〜7） |
| セクション文字数 | 最小76 / 中央値157 / 最大448 |
| 800字を超えるセクション | **0件** |
| フロントマター（YAML）を持つファイル | 30 |
| H1見出しを持つファイル | 30 |
| コードフェンスを含むファイル | 0 |
| BOM付きファイル | 0 |
| CRLF改行のファイル | **30（全件）** |
| `source/` 配下のファイル名の重複 | 0件 |

見出しの構成はほぼ統一されている（`機種概要` `基本スペック` `設置情報` `主な機能`
`こんなお客様に最適` が各30回、`年間使用コスト目安` が29回、`保証・サポート` が2回）。

最大セクションが448字であることは重要である。`CHUNK_SIZE = 800` を超えないため、
**再分割は一度も発生せず1セクション = 1チャンクになる**。最小が76字であり
`MIN_CHUNK_CHARS = 10` による切り捨ても起きない。

## 5. 採用する方針

**`##` 見出し単位でユニット化する。** PPTXで「1スライド = 1ユニット」としたのと同じ
発想で、見出しは書き手が引いた話題の境界そのものである。既存の `ParsedUnit` の枠組みに
素直に収まり、上記の実測どおりチャンク分割の副作用も受けない。

### 却下した案

- **ファイル全体を1ユニットにする（docxと同じ扱い）。** 実装は最小だが、1ファイル
  2,400〜3,000字が800字で機械分割される。見出しの途中で切れるうえ、機種名が
  先頭チャンクにしか入らず、後続は「どの製品の話か分からない断片」になる。
- **製品サマリーチャンクを別途生成する。** 横断比較のヒット率を上げる狙いだが、
  `## 機種概要` と `## こんなお客様に最適` が既に要約の役割を果たしており冗長。
  実測で取りこぼしが確認されてから追加すればよい。

## 6. Markdownパーサーの設計

`ingest/parsers/md_parser.py` を新設し、`parse_md(path: Path) -> list[ParsedUnit]` を提供する。

### 分割規則

行頭の `## ` でユニットを区切る。`###` 以下では分割しない（実データに存在せず、
分割するとユニットが細かくなりすぎる）。

### ユニットのテキスト構成

「H1 → 見出し → 本文」を改行で連結する。`#` 記号は落とす。記号は検索に寄与せず
埋め込みのトークンを消費するだけだからである。見出し語（`設置情報`）自体は
検索語になるためテキストに含める。

```
UD-0900i IoTコンパクト
設置情報
- 外形寸法：幅598ミリメートル × 奥行き700ミリメートル × 高さ1000ミリメートル
（以下本文）
```

### H1の前置

各ユニットのテキスト先頭に、そのファイルのH1（例 `UD-0900i IoTコンパクト`）を
1行として付ける。**これが本設計の要である。** `## 設置情報` のチャンクを単独で
引いても機種が特定でき、「UD-0900iの設置寸法は」という質問がそのチャンクに直接
ヒットする。付加は約20字であり、最大セクション448字と合わせても800字に届かない。

H1が存在しないファイルでは前置を行わない（空行を挿入しない）。

### フロントマターの扱い

索引に含めない。`model_id` と `product_name` はH1前置によって全チャンクに行き渡り、
`target_users` 相当の情報は `## こんなお客様に最適` が、数値スペックは
`## 基本スペック` `## 設置情報` が日本語の散文で保持している。YAMLの生テキスト
（`installation_depth_min_mm: 530`）を埋め込むより、散文のほうが日本語クエリとの
類似度が出やすいと判断した。実測で取りこぼしが出た場合に追加を再検討する。

### CRLFの正規化

全30ファイルがCRLF改行である。行頭 `## ` で分割すると見出し文字列の末尾に `\r` が
残り、出典表示が `＞ 設置情報\r` のように壊れる。読み込み直後に改行を `\n` へ
正規化する。

### コードフェンス内の `##` を無視する

現在該当するファイルは0件だが、`.md` は汎用の拡張子として登録するため、将来
コードブロックを含む文書が入ると見出しでない行で誤分割する。しかも例外は発生せず
**静かに壊れる**。``` の開閉を追うガードを入れる。

### 退化ケース

本文とは、フロントマターとH1行を取り除いた残りを指す。

| 入力 | 出力 |
|---|---|
| `##` が1つもなく本文がある | 全体を1ユニット（H1があれば前置、`heading` は空文字、`location` は1） |
| `##` が1つもなく本文が空（H1のみ、またはフロントマターのみ） | `[]` |
| 空ファイル・空白のみ | `[]` |
| セクション見出しはあるが本文が空 | そのユニットを捨てる（見出しだけのチャンクを作らない） |

## 7. 再帰走査と source 識別子

### 走査

`_target_files` を `source_dir.iterdir()` から `source_dir.rglob("*")` に変える。
絞り込み条件（`is_file()` と `SUPPORTED_SUFFIXES`）は変えない。

### 識別子

チャンクのメタデータ `source` を、ファイル名から **`source/` を基準とした相対パス**へ
変更する。区切りは `as_posix()` でスラッシュに統一する。Windowsのバックスラッシュを
そのまま入れると、チャンクIDとメタデータに `\` が混ざり、環境をまたいだときに
一致しなくなるため。

| ファイル | これまでの `source` | 変更後の `source` |
|---|---|---|
| `source/モデル就業規則.pdf` | `モデル就業規則.pdf` | `モデル就業規則.pdf`（同一） |
| `source/家電製品/UD-0900i_spec_step3.md` | （対象外） | `家電製品/UD-0900i_spec_step3.md` |

**直下のファイルは相対パスがファイル名と一致するため、既存279チャンクの識別子は
変わらない。再取り込みは発生しない。**

同名ファイルが別フォルダに置かれても衝突しない設計になる（現時点で重複は0件だが、
識別子の一意性を運用に依存させない）。

### 孤児削除への影響

`ingest_directory` は `delete_orphans` に渡す既知ソース集合を
`{path.name for path in files}` から相対パスの集合に変える。ここを変え忘れると、
サブフォルダ内の資料が毎回「source/にありません」と判定されて削除される。

## 8. データモデルと出典表示

### `ParsedUnit` の拡張

- 位置種別に `SECTION = "section"` を追加する。
- `heading: str = ""` フィールドを追加する。見出し文字列を出典表示のために運ぶ。
- `location` は**セクションの通し番号（1始まりの整数）**とする。見出し文字列を
  `location` に入れるとチャンクIDが `...::section設置情報::0` となり、同一ファイル内に
  同じ見出しが2つあった場合にIDが衝突する。IDの一意性を文書構造に依存させない。

### メタデータ

`chunk_units` が生成するメタデータに `heading` を加える。PDF・PPTX・DOCX由来の
チャンクでは空文字になる。既存チャンクにはこのキー自体が存在しないが、
`Hit.citation` は `.get()` で読むため再取り込みは不要である。

### 出典表示

`Hit.citation` に section の分岐を追加する。

```
家電製品/UD-0900i_spec_step3.md ＞ 設置情報
```

### `ParsedUnit.label` の削除

`label` プロパティは本番コードから一度も呼ばれておらず、`tests/test_models.py` の
3テストだけが参照している。出典整形の実体は `Hit.citation` であり、同じ責務が
2箇所に存在している。位置種別を追加するたびに両方を直す必要が生じるため、
`label` と対応するテストを削除し、`Hit.citation` を唯一の整形箇所とする。

## 9. 関連度しきい値の再測定

コーパスが279チャンクから約460チャンクへ増え、性格も社内文書から製品カタログを
含むものへ変わる。`RELEVANCE_THRESHOLD = 0.50` はコーパス依存の実測値であるため、
`scripts/check_retrieval.py` で再測定する。

- `RELEVANT` に製品仕様への質問を追加する（特定機種の照会と条件による絞り込みの両方）。
- `OUT_OF_DOMAIN` と `GREETINGS` は現行のまま使う。
- 「関連の最大 < 圏外の最小」が保たれることを確認し、その間に新しいしきい値を置く。
- 分離が崩れた場合は、しきい値をいじらずチャンク設計を見直す。

具体的な値は実測後に確定する。

## 10. エラー処理

- **1ファイルの失敗が全体を止めない。** `ingest_directory` の既存のファイル単位
  `try/except` がそのまま効く。
- **文字コード。** BOMなしUTF-8であることを確認済みだが、`encoding="utf-8"` の指定を
  省略しない（Windowsの既定はCP932であり、指定しないと日本語で必ず失敗する）。
  デコードに失敗したファイルは `report.failed` に記録され、他のファイルの処理は続く。
- **未対応拡張子。** 再帰走査により `source/` 配下に雑多なファイルが増える可能性が
  高まるが、`SUPPORTED_SUFFIXES` による絞り込みが `_target_files` の段階で除外するため、
  `UnsupportedFormatError` には到達しない。

## 11. テスト方針

既存の方針を踏襲する。実データのバイナリはリポジトリに置かず、テスト内で生成する。
Markdownはテキストなので `tmp_path` に直接書き出す。

| ファイル | 内容 |
|---|---|
| `tests/test_parser_md.py`（新規） | 見出し分割、H1前置、フロントマター除外、CRLF正規化、コードフェンス、`##`なし、空ファイル、通し番号、`heading` の格納 |
| `tests/test_ingest_source.py`（追記） | サブフォルダの再帰走査、相対パス識別子、直下ファイルの識別子が不変であること、サブフォルダ資料が孤児削除されないこと |
| `tests/test_retrieval.py`（追記） | section形式の出典文字列 |
| `tests/test_chunker.py`（追記） | `heading` がメタデータに載ること |
| `tests/test_models.py`（修正） | `label` のテストを削除し、`heading` の既定値を確認 |

`ingest/parsers/__init__.py` のディスパッチが `.md` を振り分けることも既存の
ディスパッチテストに倣って確認する。

## 12. 想定される影響

- **チャンク数**: 279 → 約460（181件増）。
- **取り込み時間**: OCRが発生しないため埋め込みのみ。初回13分の大半はOCRが占めていた
  ので、今回の追加は数分程度で終わる見込み。実測して README を更新する。
- **既存データ**: 再取り込みなし。既存279チャンクは識別子もメタデータも有効なまま。
- **UI**: 変更なし。「差分を取り込む」ボタンが新しい30ファイルを検出する。

## 13. 今回やらないこと

- フロントマターの索引化（第6節のとおり、実測で必要性が確認されてから）
- 製品サマリーチャンクの生成（第5節のとおり）
- `SEARCH_RESULT_COUNT = 4` の変更。横断比較では不足する可能性があるが、推測で
  増やさない。しきい値の再測定と実際の会話で不足が確認されてから調整する
- メタデータによる絞り込み検索（容量や価格帯での構造化フィルタ）
- `###` 以下の見出しでの分割
- 教材ファイル `udemy1.py`〜`udemy3.py` および `local_docs` コレクションへの変更
