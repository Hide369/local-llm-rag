# 非構造化データ取り込み機能 設計書

作成日: 2026-08-11
対象: 完全ローカル環境でのPDF / PPTX / DOCX のベクトルDB取り込み

## 1. 目的と背景

現行の `udemy3.py` は Word (.docx) のみを対象とし、固定200文字でのぶつ切り分割、出典メタデータなしという構成である。ここに PDF と PowerPoint を加え、出典を提示できる実用的な社内文書検索にする。

外部サービスへの送信は一切行わない。埋め込み・生成・OCR のすべてをこのPC上で完結させる。

## 2. 実行環境（実測値）

| 項目 | 値 |
|---|---|
| CPU | Intel Core i5-1240P (12コア / 16スレッド) |
| メモリ | 16 GB |
| GPU | Intel Iris Xe（内蔵、CUDA非対応のため**すべてCPU実行**） |
| ディスク空き | 192 GB |
| OS / Python | Windows 11 Home / Python 3.13.3 (`myvenv313`) |
| Ollama | v0.32.8、ポート **12000** で待ち受け |

## 3. 対象資料の実測結果

`source/` 配下の3ファイルを PyMuPDF / python-pptx で解析した結果。

| ファイル | 実測 |
|---|---|
| `モデル就業規則.pdf` | 94ページ / 79,107文字。テキスト抽出可。最少ページでも66文字。15ページで表を検出 |
| `生成AI活用セミナー.pptx` | 43スライド / 13,080文字。画像76枚。ノート欄は未使用、表なし |
| `Claude_Code_法人導入ガイド_スライド.pdf` | 23ページ / **抽出テキスト0文字**。全ページが画像1枚のみの画像PDF |

3ファイル中1ファイルがテキストを一切持たないため、**OCRは必須要件**である。

## 4. 技術スタック

| レイヤ | 採用 | 根拠 |
|---|---|---|
| PDF抽出 | PyMuPDF 1.28.2 | 高速。ページ単位でテキスト・画像・表を取得できる |
| PPTX抽出 | python-pptx 1.0.2 | スライド単位で図形テキストとノートを取得できる |
| DOCX抽出 | python-docx | 既存実装からの移設 |
| OCR | RapidOCR 3.9.2 (`japan_PP-OCRv4_rec_mobile`, onnxruntime) | pipで完結。実測で平均信頼度0.92 |
| チャンク分割 | langchain-text-splitters (`RecursiveCharacterTextSplitter`) | 800字超のページのみ再分割 |
| 埋め込み | **bge-m3**（Ollama、1024次元） | 日本語性能。nomic比のコスト増は取り込みで約17%のみ |
| ベクトルDB | ChromaDB 1.0.16（cosine） | 既存資産の継続 |
| 生成LLM | llama3.1:8b（Ollama） | 既存資産の継続 |
| UI | Streamlit | 既存資産の継続 |
| テスト | pytest | 新規導入 |

Python 3.13 / Windows での依存解決は `uv pip compile` で検証済み。

### 採用しなかった選択肢

- **Docling**: PDFのレイアウト・表の抽出精度は高いが、依存が339パッケージ（torch + torchvision + transformers + opencv）に及び約4〜5GB。GPUなしのCPU実行では1ページ1〜3秒かかり、torch常駐によりLLMとのメモリ競合も起きる。就業規則PDFの表はPyMuPDFの `find_tables()` で足りるため見送る。
- **VLMによる図解の説明生成**: 精度は最も高いが、GPUなし16GBでは1ページ数十秒となり実用的な処理時間にならない。

## 5. アーキテクチャ

取り込みパイプラインを Streamlit から完全に分離する。UIに依存しない純粋な関数群にすることで、CLIとUIの双方から同じコードを呼べ、テストもStreamlitなしで実行できる。

```
local_llm/
├── rag_chat_app.py            # Streamlit UI（チャット + 取り込みボタン）
├── ingest/
│   ├── models.py              # ParsedUnit / Chunk（dataclass）
│   ├── parsers/
│   │   ├── __init__.py        # 拡張子 → パーサーのディスパッチ
│   │   ├── pdf_parser.py      # PyMuPDF。テキストなしページはOCRへ委譲
│   │   ├── pptx_parser.py     # python-pptx（スライド単位、ノート欄も取得）
│   │   └── docx_parser.py     # python-docx
│   ├── ocr.py                 # RapidOCRラッパー（遅延初期化・200dpi固定）
│   ├── chunker.py             # ページ単位 + 800字超のみ再分割
│   ├── embedder.py            # Ollama /api/embed（bge-m3、バッチ + リトライ）
│   └── store.py               # ChromaDBへのupsert、ハッシュ差分判定
├── scripts/
│   ├── ingest_source.py       # CLI: source/ を一括取り込み
│   └── check_retrieval.py     # しきい値調整のため距離を実測する
└── tests/
```

### 設計上の要点

**共通中間表現 `ParsedUnit`**
各パーサーは「テキスト + 出典位置」のリストを返すだけとする。チャンカー・埋め込み・保存の各段は元の形式を一切知らない。新形式の追加はパーサーを1つ足すだけで済む。

```python
@dataclass(frozen=True)
class ParsedUnit:
    text: str
    location_type: str   # "page" | "slide" | "document"
    location: int        # 1始まり。document の場合は 0
    ocr: bool            # OCR由来かどうか
```

**OCRの遅延初期化**
RapidOCRのエンジン生成に実測4.8秒かかり、生成後はメモリに常駐する。画像ページに実際に遭遇するまでロードしないことで、テキストPDFのみの場合のコストをゼロにする。

**コレクションの新設**
`local_docs_v2` を新規作成する。既存の `local_docs`（nomic-embed-text、768次元、21チャンク）はそのまま残すため、教材である `udemy3.py` は今後も動作し続ける。同一コレクションを再利用すると次元不一致で既存の学習成果が壊れる。

## 6. データフロー

```
source/*.{pdf,pptx,docx}
   ↓ ① SHA-256 を計算
   ↓ ② Chroma上の同名sourceのfile_hashと比較 → 一致ならスキップ
   ↓ ③ 不一致なら該当sourceの旧チャンクを削除してから再構築
   ↓ ④ パース → ParsedUnit[]
   ↓ ⑤ チャンク化（800字超のみ再分割、overlap 100）
   ↓ ⑥ bge-m3 で8件ずつバッチ埋め込み
   ↓ ⑦ ChromaDB local_docs_v2 へ upsert
```

### 差分取り込み

差分判定の情報は**Chromaのメタデータ自体に持たせ、別途マニフェストファイルを作らない**。管理ファイルを別に置くとDBとファイルで状態が二重管理になり、必ず食い違う。`file_hash` を各チャンクのメタデータに入れておけば、信頼できる情報源は常にDBひとつである。

### 削除されたファイルの扱い

`source/` を唯一の入力とする以上、DBの内容もそれに追従させる。取り込みの最後に、DB上に存在するが `source/` には存在しない `source` のチャンクを削除する。これを行わないと、資料を削除・改名したときに古いチャンクが残り続け、検索結果に幽霊の出典が現れる。

削除件数はログとUIに明示し、意図しない削除に気付けるようにする。

### OCRフォールバック判定

PDFの各ページについて、抽出テキストが **30文字未満**なら画像ページとみなしてOCRに回す。実測では就業規則PDFの最少ページが66文字、画像PDFが全ページ0文字であり、この境界で実データ上は完全に分離できている。

OCRのレンダリング解像度は **200dpi 固定**とする。150 / 200 / 300 dpi を比較したが、精度も速度もほぼ変わらなかった（RapidOCRが内部で `limit_side_len` に合わせて縮小するため）。高解像度化は処理時間を増やすだけで効果がない。

### チャンク分割

1ページ・1スライドを基本単位とし、**800文字を超えるものだけ** `RecursiveCharacterTextSplitter`（chunk_size=800, chunk_overlap=100）で再分割する。

実測の平均文字数は就業規則841字/ページ、PPTX 304字/スライド、画像PDF 約1,100字/ページであり、この基本単位がそのまま適切なチャンクサイズに収まる。全チャンクがページ番号を一意に保持するため、出典表示が正確になる。

## 7. メタデータ設計

| キー | 型 | 例 | 用途 |
|---|---|---|---|
| `source` | str | `モデル就業規則.pdf` | 出典表示・差分削除の単位 |
| `file_hash` | str | `a3f1c8d2e4b60917` | SHA-256の先頭16桁。再取り込みの要否判定 |
| `location_type` | str | `page` | 表示ラベルの出し分け |
| `location` | int | `48` | ページ・スライド番号 |
| `ocr` | bool | `true` | OCR由来の低信頼テキストである旨をUIに表示 |
| `chunk_index` | int | `0` | 同一ページ内の連番 |
| `indexed_at` | str | `2026-08-11` | 鮮度確認 |

チャンクIDは `{source}::{location_type}{location}::{chunk_index}` の形式で決定的に生成する（例: `モデル就業規則.pdf::page48::0`）。同じ資料を再取り込みしても同じIDになるため、重複登録が原理的に発生しない。

出典の表示形式:

- `モデル就業規則.pdf p.48`
- `生成AI活用セミナー.pptx スライド12`
- `Claude_Code_法人導入ガイド_スライド.pdf p.5（OCR）`

## 8. Ollama接続の方針

### localhost の2秒問題

計測により、Windows上で `http://localhost:12000` に毎回新規接続すると1リクエストあたり約2.1秒を浪費することが判明した。`localhost` がIPv6の `::1` に先に解決され、OllamaがIPv4でのみ待ち受けているため、タイムアウト待ちの後にIPv4へフォールバックしている。

| 接続方法 | 実測（3回中最速） | Ollama内部の処理時間 |
|---|---|---|
| `localhost` + 毎回新規接続（現行 `udemy3.py`） | 2,151 ms | 100 ms |
| `127.0.0.1` + 毎回新規接続 | 79 ms | 76 ms |
| `localhost` + Session再利用 | 77 ms | 76 ms |
| `127.0.0.1` + Session再利用 | 82 ms | 81 ms |

**対策として `127.0.0.1` の使用と `requests.Session` による接続再利用の両方を採用する。** 接続再利用は取り込み時のバッチ呼び出しでも効く。

接続先は環境変数 `OLLAMA_HOST` で上書き可能とし、既定値を `http://127.0.0.1:12000` とする。

### 埋め込み性能（実測）

| | bge-m3 | nomic-embed-text |
|---|---|---|
| 次元数 | 1024 | 768 |
| クエリ埋め込み（短文） | 458 ms | 73 ms |
| 800字チャンク batch=8 | 1,197 ms/件 | 1,024 ms/件 |
| 800字チャンク batch=32 | 1,311 ms/件 | 1,050 ms/件 |

batch=32 は batch=8 より1件あたり遅い。16GBのメモリでは大きなバッチが不利になるため、**バッチサイズは8**とする。

| 資料 | 想定チャンク数 |

| Claude_Code_法人導入ガイド.pdf | 約35 |

## 10. エラー処理

| 事象 | 挙動 |
|---|---|
| Ollama未起動 | 取り込み開始前に1回疎通確認し、「Ollamaが起動していません」と明示する。250チャンクの処理途中で落ちるのを防ぐ |
| 埋め込みAPIの一時失敗 | 指数バックオフで3回まで再試行（1秒 → 2秒 → 4秒）。それでも失敗した場合はそのファイルのみ中断し、他のファイルは継続する |
| 破損・パース不能ファイル | そのファイルをスキップしてエラー内容を記録し、残りの処理を続行する |
| 次元不一致のコレクション | 起動時に検出し、UIに再構築を促す（`udemy3.py` の既存パターンを踏襲） |
| OCRモデル未取得かつオフライン | 「初回のみネット接続が必要」と明示して該当ファイルをスキップする |
| 未対応拡張子 | スキップしてログに残す |

## 11. テスト方針

実装詳細ではなく振る舞いをテストする。

- **chunker**: 800字以下は分割されない / 超過分のみ分割される / 出典位置が全チャンクに引き継がれる
- **store**: 同一ハッシュなら再取り込みがスキップされる / ハッシュ変更時に旧チャンクが消えて新チャンクだけが残る / IDが決定的である。`chromadb.EphemeralClient()` を使いディスクに触れない
- **parsers**: PyMuPDF と python-pptx でテスト用ファイルをその場で生成して検証する（バイナリをリポジトリに置かない）。PDFはテキストページとOCR対象ページの判定分岐を確認する
- **embedder**: HTTPをモックし、バッチ分割とリトライの挙動を検証する
- **OCR実機テスト**: 7〜9秒/ページと遅いため既定の実行から除外し、`-m integration` を指定したときのみ実行する

## 12. 関連度しきい値の再調整

現行の `RELEVANCE_THRESHOLD = 0.34` は nomic-embed-text と議事録の組み合わせで得た値であり、bge-m3 では**必ず外れる**。放置すると足切りが機能せず、無関係な文書が回答に混入する。

`scripts/check_retrieval.py` で以下を実測し、その中間値を新しいしきい値として採用する。

- **関連する質問**（例:「懲戒解雇の要件は」「コンテキスト使用率の危険ラインは」）→ 正しい資料との距離の**最大値**
- **無関係な質問**（例:「今日の天気は」）→ 最も近いチャンクとの距離の**最小値**

この2つが分離していれば足切りが成立する。分離しない場合はチャンクサイズまたは埋め込みモデルの見直しが必要という判断材料になる。

しきい値は暫定値のまま放置せず、**実装作業の一環として実測を行い、確定した数値をコードに書き込む**。根拠となる実測値は `udemy3.py` の16〜24行目と同じ形式でコードのコメントに残し、後から資料を入れ替えた人が再調整できるようにする。

## 13. 事前準備

ネット接続が必要なのは以下のみで、以降は完全オフラインで動作する。

1. `ollama pull bge-m3`（約1.1GB） — **完了済み**
2. RapidOCRの日本語モデルの初回ダウンロード（数十MB、初回実行時に自動取得）
3. Pythonパッケージの導入: `pymupdf` / `python-pptx` / `python-docx` / `rapidocr` / `onnxruntime` / `langchain-text-splitters` / `pytest`

### 利用者による作業

**議事録の .docx 5件を `source/` に配置する必要がある。** 現在 `source/` にはPDF 2件とPPTX 1件しか存在せず、既存コレクション `local_docs` に登録済みの議事録は元ファイルなしには再構築できない（DBにはチャンク済みテキストしか残っていない）。

配置されない場合、議事録は新コレクションに含まれない。取り込み対象が0件の形式があってもエラーとはせず、処理件数のログで分かるようにする。

## 14. 既知の制約

- **OCRテキストの小書き仮名が崩れる**: 実測で `ナレッジ` → `ナレツヅ`、`チャット` → `チヤツ卜` の誤認識を確認した。ベクトル検索では吸収できるが、完全一致のキーワード検索には使えない。UIでは `ocr` メタデータによりOCR由来である旨を表示する。
- **画像PDFの図解の意味は取り込めない**: OCRは画像中の文字を読むだけであり、図の構造や矢印が示す関係は失われる。
- **生成速度**: llama3.1:8b をCPUで動かすため、回答生成は4〜7トークン/秒程度になる。取り込み機能の範囲外だが体感速度を左右する。
