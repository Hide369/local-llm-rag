# Reranker（bge-reranker-v2-m3）の導入 設計書

作成日: 2026-08-30

## 1. 目的

ハイブリッド検索（[2026-08-15-hybrid-retrieval-design.md](2026-08-15-hybrid-retrieval-design.md)）で
導入したRRF融合の後段に、クロスエンコーダによる再ランキングを1段加える。

RRFは**順位の数字しか見ない**。ベクトル側とBM25側の双方が上位に挙げたかという
多数決以上のことはできず、「4位のチャンクが実は1位より的確」という判断は原理的に
下せない。質問とチャンクの中身を突き合わせて関連度を測るのがリランカーの役割であり、
RRFの代替ではなく後段の精密化である。

前回の設計（2026-08-15）でリランカーは**却下されていた**。

> **リランカー（bge-reranker-v2-m3）の導入**: 効果は見込めるが、モデルの
> ダウンロードと1問あたり数秒の追加コストが発生する。このPCは
> `llama3.1:8b` で8トークン毎秒しか出ない環境であり、まずコストゼロの
> BM25で足りるかを確認する

BM25とRRFは導入済みで効果も確認できた。本設計は「その次」にあたる。却下理由だった
コストが実際にいくらなのかを実測し（3節）、許容できる範囲だったため導入する。

## 2. 前提と制約

- 対象コーパスは全て日本語。456チャンク（PDF除く実測値）
- ローカルPCは **Intel Core i5-1240P**（Pコア4＋Eコア8、28W）、メモリ16GB、**GPUなし**
- 連続負荷で熱により約2.5倍遅くなる（README「既知の制約」）
- Colab L4への接続経路は既存（`OLLAMA_HOST` の差し替え）だが、後述4.3のとおり
  リランカーはこの経路に乗らない
- 1問あたりの追加コストの目標は**1秒以内**

## 3. 実測（2026-08-30、spike）

### 3.1 計測条件

- モデル: `onnx-community/bge-reranker-v2-m3-ONNX` の `onnx/model_int8.onnx`（570.7MB）
- 実行: `onnxruntime` 1.28.0 / CPUExecutionProvider
- データ: `source/` 配下を本番と同じ `parsers` → `chunker` に通した456チャンク
  （OCRが走るPDFは除外）
- クエリ: 「ファインチューニングについて教えてほしい」（前回設計の回帰ケース）

### 3.2 チャンクは想定よりはるかに短い

これが速度を決めた最大の要因である。

| 指標 | トークン数 |
|---|---|
| 最小 | 17 |
| 中央値 | 111 |
| p90 | 175 |
| 最大 | 380 |

**512トークンを超えるチャンクは1件も無い。** `CHUNK_SIZE = 800`（文字）は
日本語で概ね300トークン程度にしかならないためである。

固定512パディングは計算の6割以上を無駄にしていた。バッチ内最長に合わせる
動的パディングで **3.6倍** 速くなる（候補10件: 8.73秒 → 2.43秒）。

### 3.3 スレッド数は8が最適

`intra_op_num_threads` を振った実測（最長30チャンク・seq_len 297固定の最悪ケース）。

| スレッド数 | 候補10件 | 1ペアあたり |
|---|---|---|
| 既定（16論理コア） | 4.74 秒 | 474 ms |
| 4 | 6.41 秒 | 641 ms |
| **8** | **3.76 秒** | **376 ms** |
| 12 | 4.68 秒 | 468 ms |

i5-1240PはPコア4（HTで8スレッド）＋Eコア8という構成で、既定の16スレッドは
Eコアを巻き込んで遅くなる。**8 = Pコアだけを使い切る値**である。

> CPUを変えたらこの値は変わる。実測せずに引き継がないこと。

### 3.4 現実的な分布での所要時間

456チャンクから無作為抽出、10回試行（動的パディング / 8スレッド）。

| 候補数 | 中央値 | 最小 | 最大 |
|---|---|---|---|
| 4件 | **0.89 秒** | 0.68 | 2.01 |
| 8件 | **1.34 秒** | 1.02 | 3.89 |
| 10件 | 2.43 秒 | 1.15 | 5.58 |
| 30件（`CANDIDATE_COUNT` 全部） | 8.13 秒 | 5.24 | 15.86 |

ばらつきが大きいのは、バッチ内に長いチャンクが1つでも混ざると
そのseq_lenに全体が引きずられるためである。最大値は最悪ケースとして許容する。

### 3.5 依存パッケージの追加はゼロ

`myvenv313` に必要なものが既に揃っていた。

| 必要なもの | 状態 |
|---|---|
| `onnxruntime` 1.28.0 | RapidOCR（`ingest/ocr.py`）が導入済み |
| `tokenizers` 0.23.1 | 導入済み |
| `huggingface_hub` 1.27.0 | 導入済み |
| PyTorch | **不要** |
| `transformers` | **不要**（`tokenizers` だけでtokenizer.jsonを読める） |

ONNX版を選ぶ決め手はここにある。`FlagEmbedding` や `sentence-transformers` を
使う一般的な導入手順ではPyTorch（約2.5GB）が必要になり、
「依存パッケージを増やさない」という本プロジェクトの方針
（[2026-08-15設計書 5.1節](2026-08-15-hybrid-retrieval-design.md)）に反する。

## 4. 採用する方針

### 4.1 RRFの後段に1段挟む

```
ベクトル検索30件 ─┐
                  ├─ RRF融合 ─ 採否判定 ─ RRFソート
BM25検索30件 ─────┘                          │
                                              ├─ 上位8件 ──→ Reranker ──→ 再ソート ─┐
                                              │                                      ├→ 上位4件
                                              └─ 9件目以降は捨てる ──────────────────┘
```

| 定数 | 値 | 根拠 |
|---|---|---|
| `CANDIDATE_COUNT` | 30（変更なし） | 各アームから取る候補数 |
| `RERANK_CANDIDATE_COUNT` | **8**（新規） | 3.4節の実測。1.34秒で目標1秒に最も近い |
| `SEARCH_RESULT_COUNT` | 4（変更なし） | LLMへ渡す件数 |

### 4.2 圏内判定（ゲート）には触らない

採否は従来どおり `RELEVANCE_THRESHOLD = 0.50` のベクトル距離が単独で担う。
リランカーは**並べ替えだけ**を行う。

リランカースコアを採否に使えば、ベクトル距離の
「関連最大0.456 / 圏外最小0.522」という0.066しかない隙間への依存を減らせる。
効果は見込めるが、それには圏内・圏外を分けるスコアのしきい値を新たに実測して
決める必要がある。**本設計はそこまで踏み込まない。** 段階を分け、まず並べ替えの
効果を測ってから、スコア分布を見て判断する（13節）。

### 4.3 GPU（Colab L4）は今回やらない

Colab L4上のOllama（0.33.2）に実際に接続して確認した結果、
**リランク用エンドポイントは存在しない**。

```
POST /api/rerank -> 404 page not found
POST /v1/rerank  -> 404 page not found
```

したがって「`OLLAMA_HOST` を差し替えれば生成も埋め込みもGPUに寄る」という
既存の仕組み（README「ColabのL4 GPUに接続する」）にリランカーは乗らない。
GPU化するには [colab/run_ollama_server.ipynb](../../../colab/run_ollama_server.ipynb)
のリバースプロキシ（セル6）に `/rerank` ルートを追加し、そこでモデルを常駐させる
必要がある。

今回やらない理由:

- CPUで1.34秒という実測値が、その複雑さ（ノートブックのセル追加、Colab起動ごとの
  1.1GB追加ダウンロード、クライアント側の2経路化、疎通確認とフォールバック）を
  正当化しない
- Colabのランタイムは「常時稼働のAPIとしてではなく、使う時だけ起動するもの」
  （README）である。常用パスをColab依存にすべきではない
- RRFで既に上位8件に絞れている以上、GPUで30件全部を回せるようになっても
  伸びしろは小さい

将来導入する場合の配線だけ14節に記録する。

### 4.4 ソートはリランカースコア単独

RRFスコアとの加重和は取らない。異なる尺度の合成は
[2026-08-15設計書 6.2節](2026-08-15-hybrid-retrieval-design.md) が
「cosine距離とBM25スコアは互いに正規化できず、重み付き和は意味を持たない」として
既に退けた考え方であり、RRFスコアとリランカースコアの関係にも同じ理由が当てはまる。

RRFは「どの8件をリランカーに見せるか」を決める前段に徹する。

### 却下した案

- **候補30件すべてをリランキングする**: 8.13秒（最悪15.86秒）かかる。
  RRFが上位8件に絞る役目を果たしている以上、割に合わない
- **`bge-reranker-base`（278M）に落として高速化**: v2-m3が1.34秒で収まった以上、
  多言語性能を落としてまで小型化する理由がない。v2-m3は日本語を含む
  多言語で学習されており、本コーパスは全て日本語である
- **`hotchpotch/japanese-bge-reranker-v2-m3-v1` を使う**: 同じv2-m3を日本語で
  追加学習したもので効果は見込めるが、ONNX版が提供されておらず（safetensorsのみ）、
  自前変換にPyTorchが必要になる。3.5節の「依存を増やさない」方針と衝突するため
  今回は見送る。13節に将来の選択肢として記録する
- **リランカースコアで採否も判定する**: 4.2節のとおり段階を分ける
- **GPU（Colab L4）対応を同時に入れる**: 4.3節のとおり
- **固定512パディング**: 3.2節のとおり計算の6割以上が無駄になる。
  実チャンクは最大380トークンで、動的パディングで3.6倍速い

## 5. リランカーの実装（`ingest/reranker.py`・新規）

### 5.1 公開する関数

```python
MODEL_REPO = "onnx-community/bge-reranker-v2-m3-ONNX"
MODEL_FILE = "onnx/model_int8.onnx"
TOKENIZER_FILE = "tokenizer.json"
MAX_LENGTH = 512
INTRA_OP_THREADS = 8
PAD_ID = 1  # XLM-RoBERTa

class RerankError(Exception): ...

def rerank(query: str, texts: list[str]) -> list[float]: ...
def reset_session() -> None: ...
def check_reranker() -> None: ...
```

`rerank()` は **`texts` と同じ並びでスコアを返すだけ**である。並べ替えも件数の
絞り込みもしない。順位の決定は `ingest/retrieval.py` に集約したままにする
（`ingest/lexical.py` が `(id, score)` を返すだけで採否に関与しないのと同じ分担）。

### 5.2 モデルの置き場所

`huggingface_hub` の既定キャッシュ（`~/.cache/huggingface`）を使う。
プロジェクト配下に `models/` を作ると `.gitignore` の管理が増え、570MBを
誤ってコミットする事故の余地が生まれる。既定キャッシュは再開可能ダウンロードと
整合性検証も備えている。

### 5.3 セッションの遅延生成

```python
_session = None  # ingest/ocr.py の _engine と同じ方針
```

リランカーを使わない経路（取り込みCLI、条件絞り込みで答える質問）で
570MBのロードコストを払わないため、最初に必要になるまで生成しない。
`reset_session()` はテストのために置く（`ocr.reset_engine()` と同じ）。

### 5.4 動的パディング

バッチ内の最長シーケンスに合わせてパディングする。3.2節のとおり、これが
3.6倍の差を生む。

```python
longest = max(len(ids) for ids in batch)
```

`MAX_LENGTH = 512` は切り詰めの上限として残す。実データは最大380トークンで
発動しないが、将来 `CHUNK_SIZE` を上げたときの安全弁になる。

### 5.5 スコアの形式

モデルの出力は `logits` shape `[batch, 1]` の生のロジットである。

- **並べ替えには生のロジットを使う**（シグモイドは単調増加なので順位は変わらない）
- **画面表示にはシグモイドで0〜1に正規化する**（BAAIが正規化スコアとして案内する形式。
  桁の直感が効く）

## 6. 検索への組み込み（`ingest/retrieval.py`・改修）

### 6.1 シグネチャ

```python
def search(collection, query, index=None, session=None,
           threshold=None, n_results=SEARCH_RESULT_COUNT,
           rerank=None):
```

`rerank` を省略すると現行どおりRRF順で返る。`ocr_page` / `caption_image` と同じ
注入パターンで、テストから実モデル無しで差し替えられる。

### 6.2 `Hit` への追加

```python
rerank_score: float | None = None
```

`bm25_score` と同じ扱い。リランカーを通っていないヒットは `None` のままになる。

### 6.3 失敗したら黙って劣化させない

リランカーは検索の**増幅器であって関門ではない**。埋め込みが失敗すれば検索そのものが
成立しないが、リランカーが失敗してもRRF順の妥当な結果は残る。したがって
`EmbeddingError` とは扱いを変え、`search()` が `RerankError` を捕まえてRRF順のまま返す。

ただし**失敗を隠さない**。捕まえたヒットは `rerank_score=None` のままになり、
画面に「Reranker 未計測」と出る。

この規律には既存の前例がある。`ingest/prompting.py` の `format_hit_caption` は、
距離を測っていないヒットを「圏外」と書くことを明確に退けている。

> distance が None のヒットは「しきい値を超えた」のではなく、ベクトル側の
> CANDIDATE_COUNT件の候補に入らず距離を測っていない。（中略）「圏外」と書くと
> 測定していない事実を測定した事実であるかのように誤って伝える。

`None` は「スコアが低い」ではなく「**測っていない**」として表示する。

## 7. UI（`rag_chat_app.py`・改修）

### 7.1 サイドバーのチェックボックス

```
☑ Rerankerで並べ替える（+約1.3秒）
```

**既定ON**。VLMが既定OFFなのは画像1枚ごとに同期のAPI呼び出しが挟まり取り込みが
大幅に遅くなるためだが、リランカーは1.34秒であり常用に耐える。

### 7.2 初回の570MBダウンロード

質問の途中で無言で止まるのを避けるため、チェックボックスを有効にした時点で
`check_reranker()` を `st.spinner` 付きで呼ぶ。`vlm.check_vlm()` を
取り込みボタンで呼んでいるのと同じ配線である。

### 7.3 出典の表示

`format_hit_caption` に1項目足す。

```
生成AI活用セミナー.pptx スライド11
cosine距離 0.456（しきい値 0.5） / BM25 35.93 / Reranker 0.87
```

未適用時は `Reranker 未計測`。

## 8. 効果の実測（`scripts/check_retrieval.py`・拡張）

`--with-reranker` を追加し、既存の回帰ケースで**RRF順とリランカー順を並べて出力**する。

本プロジェクトは検索の変更を必ず実測で検証してきた（2026-08-15設計書の全体が
その記録である）。リランカーも例外にしない。これが無いと
「入れたが効いたか分からない」状態になる。

出力にはリランカースコアの分布も含める。13節の「採否への適用」を将来判断するとき、
圏内・圏外のスコアがどれだけ離れているかがそのまま材料になるためである。

## 10. テスト方針

**単体テストは実モデルを使わない。** `rerank` は注入されるので、固定値を返す
偽の関数で十分に検証できる。

| テスト | 確認内容 |
|---|---|
| `rerank=None` でRRF順が保たれる | 既存挙動の回帰 |
| リランカーが並びを変える | RRF 3位が1位になる |
| 上位8件しか渡らない | 9件目以降はリランカーに渡らない |
| `RerankError` でRRF順に戻る | 劣化が正しく働く |
| 失敗時 `rerank_score` は `None` | 「未計測」が伝わる |
| スコアと `texts` の並びが対応する | 取り違えの検出 |
| 空リストを渡しても落ちない | 境界 |

実モデルを使うテストは1本だけ、`integration` マーカーを付ける
（`pytest.ini` の既定では実行されない）。OCRやOllamaを要するテストと同じ扱い。

## 11. 想定される影響

- 1問あたり **約1.3秒**（中央値）の増加。最悪3.9秒
- 初回のみ570MBのダウンロード（実測65秒）
- ONNXセッションの常駐メモリ増（INT8で概ね600MB前後）。16GBのPCで
  Ollamaと同時に動かすため、メモリ逼迫の兆候が出たら15節のリスクとして再評価する
- 既存チャンクの再取り込みは**不要**。検索時のみの変更であり、DBのスキーマも
  埋め込みも変わらない

## 12. 既存の挙動で維持しなければならないもの

- `rerank` を渡さない呼び出しは1件も結果が変わらないこと
- 圏外の質問が空を返すこと（4.2節、ゲートは不変）
- 同点の並びが決定的であること（`retrieval.py` の既存のソートキー）。
  リランカースコアが同点のときは、その下のRRFスコア以下の既存キーで決める
- `catalog` 経路（条件絞り込み）はリランカーを一切通らないこと

## 13. 今回やらないこと

- リランカースコアによる**採否の判定**（4.2節）
- **GPU（Colab L4）対応**（4.3節）
- 日本語チューニング版への差し替え（却下した案）
- リランカー結果のキャッシュ。同じ質問が繰り返される想定が無く、
  キャッシュの無効化条件（チャンクの再取り込み）を管理する複雑さに見合わない

## 14. 将来GPU対応する場合の配線（記録のみ）

実装しないが、調べた結果を残す。

- Colabの `ollama_proxy.py`（ノートブックのセル6）で、catch-allの**手前**に
  `/rerank` ルートを追加する。catch-allは `@app.api_route("/{path:path}")` なので、
  先に定義した具体的なパスが優先される
- Colab側でモデルを常駐させる。fp16版（`onnx/model_fp16.onnx`、1.1GB）または
  PyTorch版
- クライアント側は環境変数 `RERANKER_HOST` を見て、あれば HTTP、無ければローカル
  ONNXにフォールバックする。`X-API-Key` は既存の `OLLAMA_API_KEY` を流用できる
- L4はFP16で約120 TFLOPS。候補30件×300トークンでも0.5秒を大きく下回る見込み
  （未実測）

## 15. 残るリスク

- **RRF上位8件の外にある正解は救えない。** リランカーは並べ替えしかせず、
  RRFが9位に置いたチャンクは見られない。8→10件に上げれば緩和できるが
  2.43秒になる。8節の実測でこのケースが観測されたら見直す
- **INT8量子化による精度劣化を測っていない。** 再ランキング用途では許容範囲と
  されるが、本コーパスでfp32と比較はしていない。8節の実測で期待した順位が
  出ない場合、量子化を疑う前にまず `hotchpotch/japanese-bge-reranker-v2-m3-v1`
  （日本語追加学習版）を検討するほうが筋が良い
- **スレッド数8はこのCPU固有の値。** 別のマシンでは最適値が変わる。
  3.3節の実測手順を残してあるので、環境が変わったら測り直すこと
- **熱によるスロットリング。** README「既知の制約」のとおり、この機体は連続負荷で
  約2.5倍遅くなる。会話を続けたときの実効速度は3.4節の値より悪化しうる
- **メモリ。** Ollama（生成モデル）とONNXセッションが同居する。16GBで
  `qwen3:32b` のような大きなモデルを使う場合は特に注意が要る
