# ハイブリッド検索とPPTXチャンク分割の見直し 設計書

作成日: 2026-08-15

## 1. 目的

固有の専門用語で質問したときに、その語を実際に含む資料が検索結果に入らない問題を
解消する。

発端となった質問（実際に誤答した）:

- 「ファインチューニングについて教えてほしい」
  - 期待: `生成AI活用セミナー.pptx` スライド11（ファインチューニングへの言及と、
    「事前学習済モデルに追加学習させ、LLMを再生成する」という定義がある）
  - 実際: `Claude_Code_法人導入ガイド_スライド.pdf` p.13 の1件だけを根拠に
    「この社内文書ではファインチューニングについては言及されていません」と回答した

## 2. 現状なぜ答えられないのか（実測）

### 2.1 OCRは原因ではない

当初はPPTX内の画像に対してOCRが効いていないことを疑ったが、**そうではなかった**。

`ingest/parsers/pptx_parser.py` はOCRを経由しない。スライド11のテキストは
364文字が正常に抽出され、`ocr: False` としてChromaDBに格納済みである。
「ファインチューニング」の語も本文中に存在する。

```
'1-6. 生成AI活用のポイント\n11\nプロンプト（指示文）の質が、AIの出力品質を…
 ➡ RAG（Retrieval-Augmented Generation：検索拡張生成）やファインチューニングを
 活用することで、ある程度回避することが可能…
 事前学習済モデルに追加学習させ、LLMを再生成する'
```

したがってVLM（Vision Language Model）への置き換えは、この症状の解決策にならない。
テキストは既に100%取れており、置き換えても同じ文字列が得られるだけで距離は変わらない。

### 2.2 4位まで来ていたが、しきい値で切られた

「ファインチューニングについて教えてほしい」で実測した距離:

| 順位 | 距離 | 出典 | 採否 |
|---|---|---|---|
| 1 | 0.478 | Claude_Code_法人導入ガイド p.13（OCR） | 採用 |
| 2 | 0.508 | 同 p.14（OCR） | 足切り |
| 3 | 0.511 | 同 p.16（OCR） | 足切り |
| **4** | **0.514** | **生成AI活用セミナー.pptx スライド11** | **足切り** |

`RELEVANCE_THRESHOLD = 0.50` により2位以下がすべて落ち、1位だけが残った。
画面の「参考にした情報（1件）」はこの結果と一致する。欲しかったスライドは
**0.014差で切られていた**。

### 2.3 語を含まないチャンクが、含むチャンクに勝っている

DB全460チャンクのうち「ファインチューニング」を実際に含むのは
スライド11とスライド40の**2件だけ**である。それにもかかわらず、この語を1度も
含まない導入ガイド p.13 が1位を取った。

p.13 は「RAG・精度・データ整形・Embedding・チャンク」といったAI一般語が
750字ぎっしり詰まったOCRテキストであり、AI系の質問全般に対して近い位置に
埋め込まれている。**密ベクトルは語の完全一致を評価できない**ため、
語を含まない汎用チャンクに負ける。

質問の言い回しを変えると、順位はさらに悪化する。

| 質問 | スライド11の順位 | 距離 |
|---|---|---|
| ファインチューニングについて教えてほしい | 4位 | 0.514 |
| ファインチューニング | 7位 | 0.561 |
| ファインチューニングとは | 9位 | 0.622 |

### 2.4 1スライド1チャンクによる話題の希釈

スライド11は364字に7つの話題が同居している（プロンプト品質／レビューの必要性／
ハルシネーション／RAGとファインチューニング／ベクトルDB／ハイブリッド検索／
ファインチューニングの定義）。「ファインチューニング」はそのうちの1語にすぎず、
チャンクのベクトルはスライド全体の平均に薄まる。

希釈の証拠として、スライドのタイトルそのままの質問で引くと順位が一変する。

| 質問 | スライド11の順位 | 距離 |
|---|---|---|
| 生成AI活用のポイントを教えてください | **1位** | **0.303** |

同じチャンクが、話題を丸ごと指す質問には 0.303 で1位、その中の1話題を指す質問には
0.514 で4位になる。これがチャンク粒度の問題である。

## 3. 前提と制約

- 利用者は自然文で質問する。検索方式を選ばせるUIは作らない
- コーパスは `source/` 配下の38ファイル・460チャンク。社内文書（PDF/PPTX/DOCX）と
  製品仕様書（Markdown）が混在する
- 追加の依存パッケージは増やさない方針を優先する
- 既存の「絞り込み経路」（`ingest/conditions.py` / `ingest/catalog.py`）は
  ベクトル検索を通らないため、本設計の影響を受けない
- OCRを含む全量再取り込み（約24分）は避ける

## 4. 採用する方針

ベクトル検索とBM25（全文検索）を並行して実行し、RRF（Reciprocal Rank Fusion）で
融合する。あわせてPPTXのチャンクをシェイプ単位に分割し、話題の希釈を緩和する。

```
質問
 ├─ ベクトル検索 (Chroma, 上位30件) ──┐
 │      → distance                    ├─ RRF融合で並べ替え
 └─ BM25検索 (メモリ上, 上位30件) ────┘      → OR条件で足切り → 上位4件
        → bm25_score
```

皮肉なことに、この方針はスライド11自身が記述している内容と一致する。

> ベクトルデータベース（ベクトル検索）
> ➡ 全文検索（キーワード検索）機能と組み合わせることによって、回答精度を
> 向上させることができる（ハイブリッド検索）

### 却下した案

- **`RELEVANCE_THRESHOLD` を 0.50 から 0.52 へ緩める**: スライド11（0.514）は
  通るが、圏外質問の最小 0.549 に肉薄し、無関係な文書の混入が増える。
  かつ「ファインチューニング」単体（0.561）は依然として救えない。対症療法である
- **`SEARCH_RESULT_COUNT` を増やす**: 足切りが距離で行われている以上、件数を
  増やしても 0.50 を超えるチャンクは1件も採用されない。効果がない
- **VLMへの置き換え**: 2.1 のとおり、テキストは既に取れているため効果がない
- **リランカー（bge-reranker-v2-m3）の導入**: 効果は見込めるが、モデルの
  ダウンロードと1問あたり数秒の追加コストが発生する。このPCは
  `llama3.1:8b` で8トークン毎秒しか出ない環境であり、まずコストゼロの
  BM25で足りるかを確認する
- **全形式で `CHUNK_SIZE` を 800 → 400 に下げる**: PPTXの本文は平均265字で
  400未満のスライドが34/43枚を占め、スライド11（本文約330字）も分割されない。
  効果がないうえ、就業規則やOCR PDFの既存挙動を広範囲に変え、
  OCRを含む約24分の全量再取り込みが必要になる

## 5. BM25の実装（`ingest/lexical.py`・新規）

### 5.1 依存パッケージを増やさない理由

現在の環境にはBM25ライブラリも形態素解析器も入っていない。追加候補は
`janome`（純Pythonの形態素解析器・辞書約50MB）と `rank_bm25` だが、いずれも
採用しない。

- BM25本体は約80行で書ける。460チャンク規模では速度・メモリとも問題にならない
- 形態素解析は**辞書に無い語で分割位置が変わる**。`UD-0900i` のような型番や
  新しい専門用語は、まさに本設計が救おうとしている対象である
- `rank_bm25` は毎回全文書を走査する実装で、永続化機構を持たない。
  結局インデックス管理は自前になり、依存を増やす見返りが小さい

### 5.2 トークン化

文字bigram（2文字組）を採る。辞書に依存せず、未知の専門用語と型番の
どちらも確実に一致する。

1. NFKC正規化 + 小文字化（全角/半角・大文字/小文字の揺れを吸収）
2. `\W+` で区切る（Pythonの `\W` はUnicode対応で、漢字・かなは語構成文字として残る）
3. 各セグメント内で文字bigramを生成する。**1文字のセグメントはそのまま1トークンとする**
   （bigramが作れず消滅するのを防ぐ）

```
"ファインチューニング"
  → ファ|ァイ|イン|ンチ|チュ|ュー|ーニ|ニン|ング

"UD-0900i"
  → セグメント "ud", "0900i"
  → ud | 09|90|00|0i
```

部分一致がノイズになる懸念はあるが、頻出するbigramはBM25のIDFが自動的に
押さえるため、追加の対策は置かない。

### 5.3 スコア計算

標準的なOkapi BM25を用いる。

```
k1 = 1.2, b = 0.75
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(d, q) = Σ idf(t) · tf(t,d)·(k1+1) / (tf(t,d) + k1·(1 - b + b·|d|/avgdl))
```

### 5.4 公開する関数

| 関数 | 役割 |
|---|---|
| `tokenize(text) -> list[str]` | 正規化と文字bigram化 |
| `build(ids, texts) -> BM25Index` | インデックス構築 |
| `search(index, query, limit) -> list[tuple[str, float]]` | ID とスコアの降順リスト |

`BM25Index` は `ids` / 転置索引 / 文書長 / 平均文書長 / 文書数 を持つ凍結データ構造とする。

### 5.5 永続化しない

**インデックスファイルはディスクに置かない。** 起動時にChromaDBの全チャンクから
メモリ上に構築する。

`ingest/store.py` の「信頼できる情報源は常にDBひとつにする」という既存方針を
そのまま踏襲する。インデックスファイルを置くと、差分取り込みのたびにDBとファイルの
同期が必要になり、食い違ったときに**検索結果が静かに古くなる**——例外が出ないため
気づけない種類の障害である。

構築コストは460チャンクで1秒未満と見込む。実測してコードのコメントに記録する。

## 6. RRF融合と足切り（`ingest/retrieval.py`・改修）

### 6.1 定数

```python
CANDIDATE_COUNT = 30        # 各アームから取る候補数
RRF_K = 60                  # RRFの標準的な定数
RELEVANCE_THRESHOLD = 0.50  # 据え置き（ベクトル側）
BM25_FLOOR = ?              # 実測で決定（9節）
```

### 6.2 融合

各アームの順位から `score(d) = Σ 1/(RRF_K + rank_i(d))` を計算し、降順に並べる。
`rank_i(d)` はアーム `i` における1始まりの順位とする。片方のアームにしか
現れない文書は、その1項だけで計算する。同点の場合はベクトル距離の昇順、
それも無ければBM25スコアの降順で決める（並びを決定的にするため）。

RRFを採る理由は、cosine距離とBM25スコアが**互いに正規化不能**だからである。
BM25スコアはコーパスのIDFに依存する絶対値を持たない量であり、距離との
重み付き和は意味を持たない。順位だけを使うRRFはこの問題を回避する。

### 6.3 足切りはOR条件

```
採用 ⟺ (distance is not None and distance <= RELEVANCE_THRESHOLD)
        or (bm25_score is not None and bm25_score >= BM25_FLOOR)
```

**RRFスコアそのものを足切りに使うことはできない。** RRFスコアは順位のみに依存し、
圏外の質問であっても1位の文書は必ず `1/(60+1)` を得る。関連度の絶対値を
表さないためである。したがって足切りは各アームの生の指標で行う。

OR条件にする理由は、AND や「ベクトルのみ」では今回の症状が残るからである。
「ファインチューニング」単体の質問はベクトル最良が 0.523 で全滅するが、
この語を含むチャンクはDB中2件しかないためBM25側が確実に拾う。

### 6.4 データ構造と後方互換

`Hit` を次のように変更する。`citation` プロパティは無変更。

| フィールド | 変更 |
|---|---|
| `distance: float \| None` | BM25のみでヒットした場合 `None` |
| `bm25_score: float \| None` | ベクトルのみでヒットした場合 `None`（追加） |

`search(collection, query, index=None, ...)` とし、`index=None` のときは
ベクトル単独の現行動作を保つ。既存テストと、BM25を必要としない呼び出しの
互換のためである。

BM25だけで当たったチャンクの本文とメタデータは、`collection.get(ids=[...])` で
取得する。

## 7. PPTXのチャンク分割（`ingest/parsers/pptx_parser.py`・改修）

### 7.1 シェイプを意味単位とする

PowerPointのテキストボックスは、作成者が視覚的に区切った意味のまとまりである。
スライド11を実測すると、話題がシェイプ単位で綺麗に分かれている。

| シェイプ | 文字数 | 内容 |
|---|---|---|
| 1 | 16 | `1-6. 生成AI活用のポイント`（タイトル） |
| 2 | 214 | プロンプト品質／レビュー／ハルシネーション／**RAGとファインチューニング** |
| 3 | 76 | ベクトルDB／ハイブリッド検索 |
| 4 | 25 | 事前学習済モデルに追加学習させ、LLMを再生成する |

### 7.2 読み順への整列

シェイプのXML上の並び順は視覚的な読み順と一致しない（スライド11では
タイトルの次にページ番号が来る）。`(top を 0.25インチ単位で丸めた値, left)` で
ソートし、行優先の読み順に直す。丸めるのは、同じ行に並ぶ図表の要素を
左から右へ並べるためである。python-pptx の単位はEMUで、0.25インチ = 228600 EMU
にあたる。

`top` が `None` のシェイプは 0 として扱う。

### 7.3 タイトルの決定

`slide.shapes.title` は**43枚すべてで `None`** だった。この資料はタイトル
プレースホルダではなく通常のテキストボックスで作られている。したがって
**読み順の先頭シェイプの1行目**をタイトルとする。

実測では妥当な値が得られる（スライド11「1-6. 生成AI活用のポイント」、
スライド40「事前質問への回答」、スライド1「生成AI活用セミナー」）。

### 7.4 ノイズ行の除去

| 対象 | 出現 | 理由 |
|---|---|---|
| `©` で始まる行 | 43/43枚 | 全スライド共通のフッタで、内容を持たない |
| スライド番号だけの行 | 38/43枚 | 位置情報は `location` メタデータが持っている |

全スライドに同じ文字列が入ることは、ベクトルを一様に濁らせる。BM25側では
IDFが押さえるが、ベクトル側には効かないため取り込み時に落とす。

### 7.5 グルーピング

タイトル以外のシェイプを読み順に積む。**シェイプは分割しない**（意味のまとまりを
壊さないため）。区切りの規則は次のとおりとする。

- 現在のグループにシェイプを足すと累計が目標 **200字** を超える場合、
  **足す前に**グループを閉じる
- ただしグループが空のときは閉じない。200字を単独で超えるシェイプ
  （実測で最大538字）はそれ1つで1グループになる
- 閉じたグループの文字数は結果として200字を下回ることも上回ることもある。
  目標であって上限ではない

この規則により、シェイプの並びとグループの対応が一意に決まる。

各グループを1つの `ParsedUnit` として返し、テキストの先頭にタイトルを複写する。

```
ParsedUnit(text=f"{タイトル}\n{グループ本文}",
           location_type=SLIDE, location=スライド番号)
```

タイトルを全チャンクに複写するのは、分割後のチャンクが単独で何の話か
分かるようにするためである。スライド11の4番目のシェイプ
「事前学習済モデルに追加学習させ、LLMを再生成する」は、単独では何の定義か
分からない。

スライド11への適用結果:

| チャンク | 内容 | 文字数 |
|---|---|---|
| 0 | タイトル + シェイプ2 | 231 |
| 1 | タイトル + シェイプ3 + シェイプ4 | 119 |

7話題が4話題に減り、ベクトルDB／ハイブリッド検索の話題が分離される。

### 7.6 維持しなければならない既存の挙動

既存テストから、7.5の規則だけでは壊れる挙動が2つある。

**発表者ノート。** 現行の `_slide_text` はノート欄を本文に連結している
（「ノート欄には本文に書かれていない補足や発表意図が入るため」）。
`tests/test_parsers_office.py::test_pptx_includes_speaker_notes` がこれを
守っている。ノートは位置情報を持たないため、**読み順の最後尾に置く1つの
ブロックとして扱う**。実データの43枚はいずれもノートが空だが、挙動は維持する。

**タイトルだけのスライド。** タイトルを本文から取り除く設計のため、
タイトル以外にシェイプが無いスライドは本文が空になり、ユニットが1つも
生成されない。`test_pptx_produces_one_unit_per_slide` はこの形の
スライドを含む。**本文が空のときはタイトルだけで1ユニットを生成する。**

あわせて、先頭シェイプが複数行を持つ場合（タイトルと副題が同じテキストボックスに
入っている場合）、1行目をタイトルとし、**残りの行は最初の本文ブロックとして扱う**。
捨てない。

### 7.7 併せて修正する既知の欠陥: GROUPシェイプの取りこぼし

現行の `_slide_text` はトップレベルのシェイプしか見ておらず、**グループ化された
シェイプの中のテキストを無言で捨てている**。実測ではスライド26の
「Step 1」〜「Step 4」の24字が該当する。

量としては小さいが、例外も警告も出ずにデータが消える種類の欠陥であり、
パーサーを書き換える機会に併せて直す。シェイプの走査を再帰させるだけで済む。

## 8. チャンクIDの衝突（`ingest/chunker.py`・必須のバグ修正）

現行のチャンクIDは次の形である。

```python
id = f"{source}::{unit.location_type}{unit.location}::{index}"
```

`index` は `_split()` の結果に対してユニットごとに0から振り直される。
**7節でPPTXが1スライド複数ユニットになると、同一スライドの各ユニットが
いずれも `index=0` を生成し、IDが衝突する。** ChromaDBの `add` は同一IDを
上書きするため、例外を出さずにチャンクが消える。

`index` を「`(location_type, location)` ごとの通し番号」に変更する。

既存形式は影響を受けない。

| 形式 | ユニットとlocationの関係 | 変更後のindex |
|---|---|---|
| PDF | 1ページ = 1ユニット | 0,1,2…（ページ内・現行と同一） |
| Markdown | 1セクション = 1ユニット、locationは通し番号で一意 | 0（現行と同一） |
| DOCX | 文書全体 = 1ユニット、location=0 | 0（現行と同一） |
| PPTX | **1スライド = 複数ユニット**（新規） | 0,1,2…（スライド内） |

したがってPPTX以外のチャンクIDは1件も変わらず、再取り込みも不要である。

## 9. しきい値の実測（`scripts/check_retrieval.py`・拡張）

既存の「実測して閾値を決める」やり方を踏襲する。各質問についてベクトル距離と
BM25スコアの両方を出力し、次が成り立つ値を `BM25_FLOOR` に採る。

```
圏外質問のBM25最大 < BM25_FLOOR ≤ 救済したい関連チャンクのBM25
```

回帰ケースとして `RELEVANT` に追加する。

- `"ファインチューニングについて教えてほしい"` → 期待: 生成AI活用セミナー.pptx スライド11
- `"ファインチューニング"` → 同上

**BM25スコアはコーパス依存で正規化されていない。** 資料を入れ替えたら
`RELEVANCE_THRESHOLD` と同様に再実測が必要である。この制約を
`ingest/retrieval.py` の定数定義にコメントとして明記する。

判定は既存と同じく、関連と圏外が分離できているかで行う。挨拶は従来どおり
参考値として記録するだけで合否には使わない。

## 10. UI（`rag_chat_app.py`・改修）

- BM25インデックスを `@st.cache_resource` で構築する。ChromaDBのコレクションは
  ハッシュ化できないため、引数名の先頭にアンダースコアを付ける既存の作法に従う
- 差分取り込みの直後にこのキャッシュをクリアする。忘れると、取り込んだ資料が
  ベクトル検索でだけ引ける状態になる
- 出典表示（現行は `cosine距離 {hit.distance:.3f}`）を `distance=None` に
  対応させ、cosine距離とBM25スコアの両方を表示する

## 16. 残るリスク

- **`BM25_FLOOR` が新しい調整点になる。** コーパス依存で、資料を入れ替えると
  再実測が必要になる。関連と圏外が分離する値が得られない場合は、
  **ベクトル側を圏内判定のゲートに使う構成**へ縮退させる——すなわち
  「ベクトル側に `RELEVANCE_THRESHOLD` を通過した文書が1件でもあれば、
  その質問を圏内とみなし、BM25側のヒットもスコアを問わず採用する」。
  この縮退では、圏外判定を既に実測済みの1つのしきい値だけで行える。
  救える範囲は次のとおりで、OR条件より狭い。

  | 質問 | ベクトル最良 | 縮退構成での結果 |
  |---|---|---|
  | ファインチューニングについて教えてほしい | 0.478 | 圏内 → スライド11を採用 ✓ |
  | ファインチューニング（単体） | 0.523 | 圏外と判定され0件 ✗ |
  | 今日の東京の天気を教えてください | 0.549以上 | 圏外 → 0件 ✓ |
- **文字bigramの部分一致がノイズを生む可能性。** IDFで押さえられる想定だが、
  実測で圏外質問のBM25スコアが高く出るようなら、セグメント長に応じて
  トークンを絞るなどの調整を検討する
- **タイトル推定が「読み順の先頭シェイプの1行目」というヒューリスティクスである。**
  この資料の43枚では妥当だったが、レイアウトの異なる資料では外れうる。
  外れてもチャンクの先頭に無関係な短い行が付くだけで、検索が壊れるわけではない
