# 重複チャンクを取り込み時に畳む設計書

作成日: 2026-09-06

## 1. 目的

同じ本文が複数の資料に現れ、そのすべてが独立したチャンクとして索引されている。
検索の上位枠を同一本文が占め、**中身の違う根拠が押し出される**。

本文を1つにまとめ、出典を複数持てるようにする。

## 2. 実測

### 2.1 重複の量と正体

608チャンク中、21種類の本文が91行を占める。畳むと **70行（11.5%）減る**。

| 同一本文の行数 | グループ数 |
|---|---|
| 7行 | 4 |
| 5行 | 8 |
| 4行 | 2 |
| 3行 | 1 |
| 2行 | 6 |

すべて**資料をまたぐ定型スライド**である。同一資料内の重複はゼロだった。

- 「事前質問への回答」（7資料が共有）
- 「ご清聴ありがとうございました」（7資料）
- 「おすすめの学習リソース」（5資料）
- 「講師プロフィール」（4資料）
- 章扉スライド（2〜3資料）

### 2.2 検索への影響

「ファインチューニングについて教えてほしい」の BM25 上位。

```
1.  41.32  CNN画像認識セミナー.pptx slide15
2.  39.14  CNN画像認識セミナー.pptx slide25   ← 事前質問への回答
3.  39.14  RAGセミナー.pptx slide23           ← 同一本文
4.  39.14  ローカルLLMセミナー.pptx slide24    ← 同一本文
5.  39.14  画像認識AIセミナー.pptx slide22     ← 同一本文
6.  39.14  組み込みセミナー.pptx slide34       ← 同一本文
```

2〜6位が同一本文5件で、スコアまで一致している。

### 2.3 畳んだ場合（実データで模擬）

索引を組み直して測った。BM25 は idf と平均文書長が変わるため、畳んだ538件で
再構築している。

| 質問 | 畳む前 | 畳んだ後 |
|---|---|---|
| ファインチューニングについて教えてほしい | 10位 | **4位** |
| ファインチューニング | 3位 | 3位 |

**回帰ケースの判定は NG のまま残る。** 基準は上位3件だが、空いた枠を目次スライドが
埋めるためである。畳んだ後の上位3件は次のとおり。

```
1. 転移学習とファインチューニング   ← 章扉（本文なし）
2. 事前質問への回答 [出典7件]
3. － 目次 －                      ← 目次スライド
```

3件とも中身のないナビゲーション用スライドである。短くキーワード密度が高いため
BM25 が好む。**これは重複とは別の問題であり、本設計の範囲外**とする（第7節）。

### 2.4 正規化は不要

NFKC 正規化・空白畳み・小文字化を施しても、21グループ / 70行で**結果は変わらない**。
完全一致で足りる。

「講師プロフィール」は2グループに分かれているが、年齢の記載有無や資格行の分離
という実際の内容差である。畳めば情報が失われる。

## 3. 設計

### 3.1 データモデル

メタデータは `source` `file_hash` `location` `heading` `chunk_index` `indexed_at`、
Markdown の製品属性に至るまで**すべて資料固有**である。複数の資料で共有できるのは
**本文とベクトルだけ**である。これがテーブルを分ける根拠になる。

```sql
CREATE TABLE chunks (
    id        TEXT PRIMARY KEY,   -- 本文のSHA-256
    text      TEXT NOT NULL,
    embedding BLOB NOT NULL
);
CREATE TABLE occurrences (
    id       TEXT PRIMARY KEY,    -- 従来と同じ source::location::index
    chunk_id TEXT NOT NULL REFERENCES chunks(id),
    source   TEXT NOT NULL,
    metadata TEXT NOT NULL
);
CREATE INDEX occurrences_source ON occurrences(source);
CREATE INDEX occurrences_chunk  ON occurrences(chunk_id);
```

**出現のIDを従来の `source::location::index` に保つ。** `get()` は出現単位で608件を
同じIDで返し続けるため、`ingest/catalog.py`・`store.indexed_sources`・
`store.stored_file_hash` は変更しない。畳み込みは検索側だけに現れる。

**`add()` の引数は変えない。** 呼び出し側は従来どおり出現のID・本文・メタデータ・
ベクトルを渡す。ストアが内部で本文のハッシュを取り、`chunks` を upsert して
`occurrences` を差し込む。取り込み側のコードは変更しない。

**IDは本文のSHA-256全長（64文字）とする。** 短縮しない。衝突すると別々の本文が
黙って融合し、片方が消える。例外は出ない。これは本設計が解消しようとしている
`INSERT OR REPLACE` の事故と同じ形である。

**`count()` は出現数を返す。** 「入れた件数が返る」という既存の意味を変えない。
本文の種類数は `chunk_count()` を別に設け、取り込みの要約で
「608件（本文538種）」と両方を出す。

### 3.2 取り込みと削除

`replace()` の構造は変えない。1つの `with` で囲う原子性がこの設計の要である。

```
with self._write_lock, self._connection:
    1. DELETE FROM occurrences WHERE source = ?
    2. chunks を upsert
    3. occurrences を INSERT
    4. DELETE FROM chunks WHERE id NOT IN (SELECT chunk_id FROM occurrences)
    5. revision を進める
```

**手順4が本設計の肝である。** 共有されている本文は、他の資料が使っている限り
消えない。`CNN画像認識セミナー.pptx` だけを取り込み直しても、7資料が共有する
「事前質問への回答」は残る。最後の1資料からその記述が消えたときだけ行も消える。

**手順2は `INSERT OR IGNORE` ではなく upsert とし、ベクトルを更新する。**

```sql
INSERT INTO chunks (id, text, embedding) VALUES (?, ?, ?)
    ON CONFLICT(id) DO UPDATE SET embedding = excluded.embedding
```

本文が同じならベクトルも同じなので、通常は無駄な更新である。しかし埋め込み
モデルを差し替えて `--force` で入れ直したとき、`INSERT OR IGNORE` では**古い
モデルのベクトルが残る**。件数は正しく、例外も出ず、距離だけが静かに狂う。
1回の UPDATE で構造的に防げるなら、そちらを取る。

`delete(where=...)` も同じ形にする。条件に合う出現を消し、孤児になった本文を
消す。`store.delete_orphans` は `delete(where={"source": ...})` を呼ぶだけなので
変更しない。差分取り込みの `stored_file_hash` も出現を1件引くだけなので変更しない。

### 3.3 検索と出典

BM25 と ベクトルは `chunk_id` で突き合わせている。**検索側は本文空間で統一する。**
BM25索引もベクトル行列も `chunks` の538件から作り、融合のキーは本文ハッシュになる。

| 追加・変更 | 返すもの | 使う場所 |
|---|---|---|
| `chunks()` | `(chunk_id, text)` の全件 | BM25索引の構築（`store.all_documents`） |
| `chunks_by_ids(ids)` | `chunk_id → (text, [metadata, ...])` | BM25だけで当たったヒットの補完 |
| `search()` | `(chunk_id, distance, text, metadatas)` | ベクトル検索 |

`search` の4番目が単数のメタデータからリストに変わる。これが唯一の非互換で、
`ingest/retrieval.py`・`scripts/check_retrieval.py`・テストの偽コレクションが追随する。

**`get()` は出現でアドレスされるままとする。** `get(ids=...)` に渡すのは従来どおり
`source::location::index` である。本文ハッシュを引くのは `chunks_by_ids` の役目で、
2つを1つの入口に混ぜない。`ingest/retrieval.py` が BM25 だけで当たったヒットを
補完する箇所は、`get` から `chunks_by_ids` に移る。

出現の並びは `(source, location)` の昇順に固定する。取り込み順に左右されない
代表を選ぶためである。

```python
@dataclass
class Hit:
    text: str
    distance: float | None
    occurrences: list[dict]      # (source, location) 昇順

    @property
    def metadata(self) -> dict:
        """代表の出現。既存の読み手はここを見ているだけなので変えない。"""
        return self.occurrences[0]
```

`metadata` をフィールドではなく**代表を指すプロパティ**にする。フィールドとして
残して `occurrences` を別に足すと、同じ事実に2つの帳簿ができる。`replace()` が
列とJSONの食い違いを戒めているのと同じ理由である。

変更点だけを示した。`bm25_score` `rrf_score` `rerank_score` は現状のまま残る。
`metadata=` を渡している構築箇所（`ingest/retrieval.py`、`scripts/check_retrieval.py`、
テスト）は `occurrences=` に書き換える。

出典の文字列は次の形とする。

```
CNN画像認識セミナー.pptx スライド25 ほか6資料
```

出現が2件以上のときだけ「ほか N 資料」を足す。出現1件のチャンク（大半）は
**現在と完全に同じ文字列**になる。

画面の詳細表示では出現をすべて並べる。プロンプトに入るのは短い形だけとする。
モデルに7つのファイル名を読ませても、どれを引くかの判断を増やすだけで精度に
寄与しない。

### 3.4 エラー処理と移行

`open_store` は旧スキーマ（`chunks` に `source` 列がある）を見つけたら停止する。

```
VectorStoreError: 旧スキーマのDBです。次を実行して変換してください:
    python scripts/migrate_store.py vector_store.sqlite3
```

黙って書き換えない。移行が途中で失敗したとき、何が起きたか分からないDBだけが残る。

`scripts/migrate_store.py` の手順。**再埋め込みは不要**で、必要なものはすべて
旧DBに揃っている。

1. `vector_store.sqlite3.bak-YYYYMMDD` に複製する
2. 新スキーマを作り、本文ごとに `chunks`、旧行ごとに `occurrences` を作る
3. 検証してから確定する — 出現数が旧行数と一致、本文の種類数が一致、孤児ゼロ
4. 1つでも失敗したら書き戻さず、退避先を示して終了する

新スキーマのDBに対して実行された場合は、何もせず終了する。

**外部キーを有効にする。** `sqlite3` は既定で外部キーを検査しない。接続時に
`PRAGMA foreign_keys = ON` を立て、本文の無い出現が生まれないようにする。削除は
「出現 → 孤児の本文」の順なので、正しい手順なら制約に触れない。**間違った手順を
書いたときだけ例外が出る。** それが目的である。

既存の防御は残す。

- `replace()` の source 不一致検査
- ノルム0のベクトルの拒否と、拒否した書き込みが両方のテーブルに何も残さないこと
- `_write_lock` による同一接続の書き込み直列化

取り込み後の検証に整合性の確認を足す。孤児の本文がゼロであること、本文を持たない
出現がゼロであること。どちらも1回の SELECT で済む。破損が次回起動まで露見しなかった
事故を繰り返さないための関門である。

## 4. 採らなかった案

### 4.1 1テーブルのまま、出現をJSONの配列で持つ

`chunks(id, text, embedding, occurrences)` の1テーブルに保つ案。スキーマ移行は
軽いが、`source` 列が消えるため `DELETE ... WHERE source = ?` が使えない。削除の
たびに全行を Python で走査して書き戻すことになる。538行なら速度は問題にならないが、
**「1つの事実に2つの帳簿を持たせない」という `replace()` の戒めに反する**。
この形で一度データ消失を起こしている。

### 4.2 検索時に重複を落とす

スキーマを触らず、索引構築時と結果整形時に畳む案。変更は最小だが、**ベクトル検索の
候補30枠を重複が先に食う**ため、畳む前に取りこぼしが起きる。取り込み時に畳めば
これが起きない。

## 5. テスト戦略

振る舞いを書く。SQL は書かない。

### 5.1 畳み込み

- 同じ本文を2つの資料から入れると `count()` は2、`chunk_count()` は1
- その本文の検索は1件だけ返り、出現を2件持つ
- 本文が1文字でも違えば畳まれない

### 5.2 共有チャンクの生死

例外を出さずにデータが変わる形であり、テストが唯一の防波堤になる。

- A と B が共有する本文があるとき、A だけを取り込み直しても B の根拠が残る
- A からその記述が消えても、B が使っている限り本文は消えない
- 最後の資料から消えたとき、本文も消える
- 同一資料内に同じ本文が2回あるとき、出現は2件作られる

### 5.3 原子性

- `replace()` が書き込み途中で失敗したとき、両方のテーブルが元のまま
- 失敗した書き込みが、同時に走った別の書き込みによって確定されない
- ノルム0を弾いたとき、両方のテーブルに何も残らない

### 5.4 出典

- 出現1件のチャンクの `citation` は現在と完全に同じ文字列
- 出現7件なら「代表 ほか6資料」
- 代表は `(source, location)` の昇順で、取り込み順を変えても変わらない

### 5.5 移行

- 旧スキーマを `open_store` が開こうとしたら、変換方法を示して停止する
- 移行後、出現数・本文の種類数が旧DBと一致する
- 検証に失敗したら書き戻さない
- 新スキーマに対して実行しても壊さない

### 5.6 実データでの確認

単体テストとは別に、取り込み前後の順位を記録する。第2.3節の測定値が基準になる。
ゲートの距離（関連 0.420 / 圏外 0.522）が動かないことも確認する。

## 6. 影響範囲

| ファイル | 変更 |
|---|---|
| `ingest/vector_store.py` | スキーマ、`add`/`replace`/`delete`、`search`、`chunks()`、`chunk_count()` |
| `ingest/retrieval.py` | `Hit.occurrences` と `citation`、`search` の返り値への追随 |
| `ingest/store.py` | `all_documents` を本文単位にする |
| `scripts/migrate_store.py` | 新規 |
| `scripts/ingest_source.py` | 取り込み後の整合性検証、要約の件数表示 |
| `scripts/check_retrieval.py` | `search` の返り値への追随 |
| `rag_chat_app.py` | 詳細表示で出現をすべて並べる |
| `ingest/catalog.py` | **変更しない**（出現単位の `get()` を見ているため） |

## 7. 範囲外

**目次・章扉・定型スライドが上位に来る問題**（第2.3節）は本設計では扱わない。
畳み込みでは解決せず、「中身のないスライドをどう見分けるか」という別種の判断
（取り込み時に落とすか、スコアを下げるか、章扉を本文に結合するか）を要する。
別ブランチで設計する。

回帰ケースの判定は本ブランチでも NG のまま残る。ここで「直った」ことにはしない。
