# ベクトルストアを ChromaDB から SQLite + numpy へ置き換える設計書

作成日: 2026-09-05

## 1. 目的

`chroma_db` が同日中に2度、**取り込み直後には正常に見えるのに、次にプロセスを
開くと読めなくなる**という壊れ方をした。復旧には全量24分の再取り込みが要る。

ChromaDB をやめ、SQLite のトランザクションと numpy の総当たり検索に置き換えて、
**この壊れ方を原理的に起こせなくする**。

## 2. 前提と制約

### 2.1 障害の経緯と根本原因（実測）

2026-09-05 に2回発生し、2回目は差分取り込み1回で再現した。

| | 1回目 | 2回目 |
|---|---|---|
| METADATA セグメントの `max_seq_id` | 1094 | 1069 |
| VECTOR セグメントの `max_seq_id` | 1040 | 1025 |
| 未適用の `embeddings_queue` | 55 | 45 |

破損時のセグメントディレクトリには `index_metadata.pickle` だけが残り、HNSW 本体
（`data_level0.bin` / `header.bin` / `length.bin` / `link_lists.bin`）が存在しなかった。

**帳簿（`max_seq_id`）は「圧縮済み」と記録しているのに、実体が書かれていない。**
次に開くと ChromaDB は 1025 件目までを HNSW から読もうとし、ファイルが無いため
`Error loading hnsw index` になる。WAL はその分が刈られており、**ベクトルは復元
できない**（ChromaDB 1.0.x は `embeddings` テーブルに ID と系列番号しか持たない）。

ChromaDB の既知の不具合クラスであり、同種の症状が private-gpt・open-webui 等でも
報告されている。**利用側のコードの誤りではない。**

合成データでの最小再現は試みたが成功しなかった（30ファイル分の delete+add では
壊れない）。したがって**発生条件を特定できておらず、予防はできない**。これが
「検知して直す」ではなく「その仕組みごと持たない」を選ぶ根拠である。

### 2.2 規模の実測

現在 686 チャンク・1024 次元。総当たりの cosine 検索（上位30件）を実測した。

| 件数 | 所要 | メモリ |
|---|---|---|
| **686（現状）** | **0.19 ms** | 2.8 MB |
| 6,860（10倍） | 0.68 ms | 28 MB |
| 68,600（100倍） | 8.93 ms | 281 MB |
| 686,000（1000倍） | 85.55 ms | 2.8 GB |

**現状の100倍でも9ミリ秒である。**近似最近傍探索（HNSW）を置く技術的必然が無い。
今回壊れたのは、そもそも要らない部品だった。

破綻するのは数十万件規模で、そのときはメモリが先に限界になる（9節）。

### 2.3 既存の呼び出し面

ChromaDB 固有 API の使用は 24 箇所・9 種類しかない。

| API | 箇所 | 用途 |
|---|---|---|
| `collection.get` | 11 | メタデータ読み出し、`where` 絞り込み、ID指定取得 |
| `collection.count` | 8 | 件数 |
| **`collection.query`** | **2** | **ベクトル検索** |
| `collection.delete` | 2 | 資料単位の削除 |
| `collection.add` | 1 | 追加 |

`ingest/store.py` が既に「`chroma_db` への出入りを集約する」境界として設計されて
おり、置き換えはこの設計を活かす。

`where` で使う演算子は `$eq` / `$gte` / `$lte` / `$and` の4つだけである。

### 2.4 `udemy3.py` との共存

`udemy3.py`（`.gitignore` 対象のローカル専用スクリプト）が同じ `chroma_db/` の
別コレクション `local_docs`（nomic-embed-text / 768次元）を使っている。

**`chroma_db/` には一切触れない。**新ストアは別ファイルに置き、講座教材を無傷で
残す。`requirements.txt` からは `chromadb` を外すが、venv には残るため
`udemy3.py` は動き続ける（同ファイルの方針は「本システムが直接 import する
パッケージだけを挙げる」であり、`udemy3.py` はシステムの一部ではない）。

### 2.5 テスト基盤への既存の負担

`tests/conftest.py` は、`chromadb.EphemeralClient()` が Windows で非致命的な
access violation を起こし pytest の出力を数百行のノイズで埋める問題への回避策
として存在する。ChromaDB を外せば**このファイルごと不要になる**。

## 3. 検討した選択肢と却下理由

### 3.1 ChromaDB を維持し、取り込み後に健全性を検証する（却下）

別プロセスでDBを開き直し、`count()` と1件検索が通ることを確認して、失敗したら
ジョブを落とす案。

却下理由は、**対症療法にとどまる**ため。破損の発生自体は防げず、検知するたびに
全量24分の再取り込みが必要になる。2.1 のとおり発生条件が特定できていないので、
頻度の見積りもできない。

なお「壊れたら必ず気づく」こと自体には価値があるため、**この検証は新ストアでも
別途入れる**（7節）。置き換えの代わりにはならないが、併用はする。

### 3.2 chromadb を新しい版へ上げる（却下）

既知の不具合クラスなので修正済みの可能性はある。

却下理由は2つ。修正されている保証が無く、**外れた場合に失うのは再検証の工数だけ
ではなく、もう一度DBを壊すリスクそのもの**であること。そして直ったとしても、
686 件のために HNSW という不要な機構を抱え続ける構図は変わらないこと。

### 3.3 Qdrant サーバー（却下）

製品としては ChromaDB より堅牢で、フィルタリングも強力である。

却下理由は運用コスト。本機は 16GB で、`2026-09-05-ci-ingest-design.md` 2.3 節の
とおり GitLab（実測3.7GB）と Ollama が既にメモリを取り合っており、GitLab は
「必要なときだけ起動する」運用になっている。**686 チャンクのために常駐コンテナを
もう1つ増やす**判断は、この制約と釣り合わない。導入先環境の移植手順にも Docker が
加わる。

### 3.4 Qdrant ローカルモード（却下）

`QdrantClient(path=...)` はサーバー不要で SQLite に永続化する。

却下理由は、公式が**開発・試作・CI・Colab 向け**と位置づけており、本番向けとは
していないこと。「メンテナが本番用と考えていない実装に依存する」のは、今回
ChromaDB で踏んだのと同じ種類のリスクである。

### 3.5 sqlite-vec / LanceDB（却下）

いずれも新規依存が増え、**別の索引実装の不具合を引き受ける**ことになる。2.2 の
実測どおり索引そのものが不要な規模なので、依存を増やす理由が無い。

### 3.6 消費側まで含めた全面的な新API（却下）

`store.search(vector, limit) -> list[Hit]` のように全面的に書き直す案。読みやすく
なるが、**ストレージの載せ替えと呼び出し側の変更が同時に起きる**ため、問題が出た
ときの切り分けが難しくなる。既存345テストを「新エンジンの検証」として使える利点も
失われる。

### 3.7 全面的な Chroma 互換アダプタ（却下）

消費側を1行も変えない案。最小リスクだが、`results["ids"][0]` という入れ子リスト
形式と、意味を失った `include=[...]` 引数が恒久的に残る。

**採用するのは 3.6 と 3.7 の中間**（4.6節）。変更コストが高い `get` / `add` /
`delete` / `count` は互換のまま残し、最も形の悪い `query` だけを新 API にする。
`query` の消費箇所は 2 つしかないため、ここだけは安く綺麗にできる。

## 4. 設計

### 4.1 保存形式

保存先は `vector_store.sqlite3`（リポジトリ直下・`.gitignore` 対象）。
`chroma_db/` とは別ファイルにする（2.4節）。

```sql
CREATE TABLE chunks (
    id        TEXT PRIMARY KEY,
    source    TEXT NOT NULL,
    text      TEXT NOT NULL,
    metadata  TEXT NOT NULL,   -- JSON
    embedding BLOB NOT NULL    -- float32 リトルエンディアン × 1024
);
CREATE INDEX chunks_source ON chunks(source);

CREATE TABLE meta (key TEXT PRIMARY KEY, value INTEGER);
-- meta('revision') は書き込みのたびに +1 する（4.5節）
```

スキーマはファイルが無ければ生成時に作り、`meta('revision')` を 0 で初期化する。
ベクトルの次元は `ingest/embedder.py` の `EMBED_DIM` を唯一の情報源とし、
このファイルには固定値として書かない（BLOB の長さから復元する）。

`source` だけを列に出すのは、資料単位の削除と差分判定で最も頻繁に使うためである。
残りの属性は JSON にまとめる。属性キーは資料によって変わり、列に固定すると
`ingest/conditions.py` の `available_keys`（キー一覧をコードに固定しないという
方針）と衝突する。

### 4.2 書き込みの原子性（本設計の核心）

1つの資料の入れ替えを、1つのトランザクションで行う。

```sql
BEGIN IMMEDIATE;
  DELETE FROM chunks WHERE source = ?;
  INSERT INTO chunks (id, source, text, metadata, embedding) VALUES (?,?,?,?,?);  -- executemany
  UPDATE meta SET value = value + 1 WHERE key = 'revision';
COMMIT;
```

**全部入るか、1件も入らないかのどちらかにしかならない。**2.1 の「帳簿だけが進んで
実体が無い」状態は、この構造では表現できない。プロセスが途中で落ちても、SQLite が
ロールバックする。

これが検知（3.1）ではなく置き換えを選んだ理由そのものである。

### 4.3 ベクトル検索

プロセス内に numpy 配列として一度だけ読み込み、総当たりで計算する。

```python
scores = matrix @ query          # (N, 1024) @ (1024,) → (N,)
top = np.argpartition(-scores, k)[:k]
```

2.2 の実測どおり 686 件で 0.19ms。近似ではなく**厳密検索**になるため、検索精度は
下がらない（HNSW が取りこぼしていた候補を拾う可能性はある）。

### 4.4 cosine 距離の定義（最も慎重に扱う箇所）

**距離は `1 - 内積`（両者を L2 正規化したうえで）と定義する。** ChromaDB の
`hnsw:space = "cosine"` と同一である。

ここを取り違えると、`RELEVANCE_THRESHOLD = 0.50` をはじめ、
`scripts/check_retrieval.py` で積み上げてきた実測値が**すべて意味を失う**。しかも
**例外は出ない**。値の範囲が似ているため、テストも素通りしうる。

正規化は**明示的に行う**。埋め込みが正規化されて返る保証は無い（`udemy3.py` が
nomic-embed-text のノルムが約23であると記録している）。`add()` は保存時に正規化して
書き、`search()` は受け取ったベクトルを内部で正規化する。**呼び出し側に正規化の
責任を持たせない。**片方だけ正規化された状態は、例外を出さずに距離だけを狂わせる。

ゼロベクトル（ノルム0）はゼロ除算になるため、`add()` で例外を投げて弾く。
埋め込みが空を返した事故を、静かに通さないためである。

### 4.5 キャッシュの鮮度

`matrix` はプロセス内キャッシュなので、他プロセスの取り込みで古くなる。
`meta('revision')` を毎リクエスト読み、変化していれば読み直す。

`revision` は 4.2 のトランザクション内で更新されるため、**書き込みと不可分**である。
ファイルの mtime やチャンク数で代用しない。mtime は書き込み以外でも動きうるし、
チャンク数は「同数の差し替え」を取りこぼす。

### 4.6 インターフェース（3.6 と 3.7 の中間）

生成の入口は `store.open_store(path)` とする。既存の `open_collection(client)` は
ChromaDB のクライアントを受け取る形なので残せない。**変わるのは生成の1行だけ**で、
`scripts/ingest_source.py` / `rag_chat_app.py` / `scripts/check_retrieval.py` の
`chromadb.PersistentClient(path=...)` + `store.open_collection(client)` の2行が
`store.open_store(path)` の1行になる。

返るオブジェクトが持つメソッド。

| メソッド | 形 | 消費側 |
|---|---|---|
| `count()` | Chroma互換 | 変更なし |
| `get(ids=, where=, limit=, include=)` | Chroma互換（**平たい dict**） | 変更なし |
| `add(ids, documents, metadatas, embeddings)` | Chroma互換 | 変更なし |
| `delete(where={"source": ...})` | Chroma互換 | 変更なし |
| **`search(vector, limit)`** | **新API** | `retrieval.py` と `check_retrieval.py` の2箇所 |

`search()` は `(id, distance, text, metadata)` のリストを返す。Chroma の
`results["ids"][0]` のような入れ子は作らない。入れ子は「複数クエリを一度に投げる」
ための形だが、この system は常に1件しか投げない。

`get()` の `include=` 引数は互換のために受け取るが、**無視する**（常に全項目を
返す）。686 件では取捨選択に意味が無く、引数を見て分岐するほうがバグを生む。
この引数は後続のリファクタで消す（8節）。

### 4.7 メタデータの絞り込み

`where` の評価は **SQL ではなく Python で**行う。全行を読み、辞書に対して条件を
評価する。

SQL に翻訳しないのは、演算子の対応付けと文字列の組み立てが**静かに間違える**
種類のコードだからである。`$lte` を `>=` と書いても例外は出ず、誤った一覧が根拠と
して使われる（`ingest/conditions.py` が「モデルが不等号の向きを取り違える」危険を
既に記録しているのと同じ構図を、自分のコードで作らない）。

対応するのは既存の4演算子のみ。それ以外が来たら**例外を投げる**。黙って無視すると、
条件が消えたまま全件が返る。

686 件の総当たり評価は数マイクロ秒であり、性能上の理由は無い。

## 6. 移行

ベクトルは復元できない（2.1節）ので、**`source/` からの全量再取り込み**を行う。
Ollama が必要で、実測約24分。

`chroma_db/` は削除しない。`udemy3.py` が使い続ける。

## 7. テスト方針

既存345テストが新ストアで通ることを、置き換えの主たる検証とする。加えて次を足す。

| 対象 | 内容 |
|---|---|
| **中断耐性** | 書き込みの途中で例外を起こし、DBが一貫していること（今回の障害の回帰テスト） |
| **cosine距離** | 既知のベクトル対で `1 - 内積` に一致すること。正規化されていない入力でも正しいこと |
| **鮮度** | `revision` が変わったときだけ行列を読み直すこと。変わらなければ読み直さないこと |
| `where` | 4演算子それぞれ。未対応演算子で例外が出ること |
| 空DB | 0件のときに `count()` / `search()` / `get()` が壊れないこと |
| 健全性検証 | 取り込み後、別プロセスで開いて読めることを確認する（3.1節を併用として実装） |

「変わらなければ読み直さない」を確認するのは、判定を誤って常に真にしても**例外が
出ず、遅くなるだけ**だからである。

## 8. スコープ外（YAGNI）

- **`include=` 引数の除去**と、`get()` の完全な新API化。置き換えが安定してから別途
- **配列属性（`tags`）での絞り込み**。SQLite なら実装可能だが、本設計の目的では
  ない。`feat/md-tag-search` の「本文に載せる」対応とは独立に判断する
- **`udemy3.py` の移行**。講座教材であり、システムの一部ではない
- **近似最近傍探索の導入**。2.2 の実測により当面不要
- **ChromaDB からのデータ移行**。ベクトルが復元できないため不可能

## 9. 未確定事項

- **破綻する規模**。2.2 の実測では 686,000 件で 85ms・2.8GB となり、16GB 機では
  メモリが先に限界になる。現状の 1000 倍であり、当面は問題にならない。資料が
  10万件規模に向かうことが分かった時点で、3.3（Qdrant サーバー）を再検討する
- **`feat/md-tag-search` の扱い**。タグを本文へ載せる変更は未検証のまま残っている
  （検証中にDBが壊れたため）。本置き換えの完了後に、あらためて `check_retrieval` で
  測る
- **`feat/ci-ingest` への影響**。CI は差分取り込みを前提としており、本設計はその
  差分取り込みを安全にする。順序としては本設計を先に完了させる
