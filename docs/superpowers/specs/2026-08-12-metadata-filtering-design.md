# 数値メタデータによる絞り込み検索 設計書

作成日: 2026-08-12

## 1. 目的

「条件で絞り込んで比較する」種類の質問に、事実に基づいて回答できるようにする。
現行のベクトル検索のみの構成では、この種の質問で必ずハルシネーションが起きる。

対象とする質問の例（いずれも実際に誤答した）:

- 「防水パン内寸奥行きが510mmしかありません。設置できる機種の中で最大の洗濯容量は
  何kgで、該当する型番をすべて教えてください」
- 「運転音（洗い）が26dB以下で、かつ防水パン奥行き510mmに設置できる機種をすべて
  教えてください。また同じ26dBでも設置できない機種がある場合、その型番と理由も
  答えてください」

## 2. 現状なぜ答えられないのか（実測）

`scripts/check_retrieval.py` と同じ経路で、実際にモデルへ渡るチャンクを実測した。

### 2.1 容量の質問

モデルに渡った4チャンクは次のとおりで、**洗濯容量の数値は1件も含まれていなかった**。

| 順位 | 距離 | 出典 | 容量の記載 | 防水パンの記載 |
|---|---|---|---|---|
| 1 | 0.287 | UD-1000S ＞ こんなお客様に最適 | なし | なし |
| 2 | 0.338 | UD-1100TW ＞ 設置情報 | なし | 535mm（設置不可の機種） |
| 3 | 0.353 | UD-1100S ＞ こんなお客様に最適 | なし | なし |
| 4 | 0.353 | UD-0900S ＞ こんなお客様に最適 | なし | なし |

正解機種 UD-1100S は3位に入っているが、引かれたのは数値を持たない
「こんなお客様に最適」であり、製品名しか届いていない。回答中の「11キログラム」
「9キログラム」はすべて型番からの推測であった。

### 2.2 運転音の質問

上位20件がすべて「設置情報」で、dBの記載はゼロ件。正解機種 UD-1100iS は20位圏外。

根本原因は、**運転音が索引に存在しないこと**である。`noise_wash_db` は
フロントマターにしかなく、本文に運転音を明記しているのは30製品中6製品だけである。

```
デシベルを含む本文（6件のみ）
  UD-0700B 洗い35 / UD-1000S 洗い28 / UD-1000X 洗い25
  UD-1100i 洗濯26 / UD-1100T 洗い32 / UD-1200X 洗い25
```

`docs/superpowers/specs/2026-08-12-markdown-ingestion-design.md` 第6節の
「その他の属性は本文の散文が保持している」という前提は、`noise_wash_db` については
成り立っていなかった。`washing_capacity_kg` と `installation_depth_min_mm` は
30/30で本文にあるため、この前提が崩れているのは運転音だけである。

### 2.3 距離が識別力を失っている

両ケースとも上位20件が狭い帯に密集していた（容量: 0.287〜0.397、運転音:
0.375〜0.421）。30製品がほぼ同一構造のため、距離は製品を区別しない。しかも順位は
質問の制約と無相関で、設置不可の UD-1400X（545mm必要）が容量の質問で6位に入る。
**埋め込みベクトルは「510以下」という数値条件を表現できない。** これは
`RELEVANCE_THRESHOLD` の調整では直らない構造的な限界である。

## 3. 前提と用途

- 利用者は自然文で質問する。条件を入力欄で指定させるUIは作らない
- 想定する条件は数値の大小比較（以下・以上）と一致
- コーパスは `source/家電製品/` の30製品。フロントマターに構造化された属性を持つ
- 既存の社内文書（PDF/PPTX/DOCX）はフロントマターを持たない。これらに対する
  絞り込みは行わず、従来どおりベクトル検索で扱う

## 4. 採用する方針

フロントマターをChromaDBのメタデータとして保持し、`where` で機械的に絞り込む。

元データが既に構造化されているため、散文からの数値抽出は不要である。既存の設計は
「YAMLの生テキストを埋め込まない」と判断していたが、**埋め込みに入れないことと、
捨てることは別**であった。埋め込みテキストに入れない判断は妥当なので維持し、
メタデータとしてのみ保持する。

### 却下した案

- **`SEARCH_RESULT_COUNT` を増やす**: 181チャンクの比較を llama3.1:8b にさせることに
  なり非現実的。かつ運転音は索引に無いため、いくら増やしても2.2は解決しない
- **1製品1チャンク化**: 容量の質問は「最大11kg」まで正答できるが、UD-1100iS が
  検索圏外である事実は変わらず「すべて」を落とす。運転音も解決しない
- **集約（最大・件数）をコード側で計算する**: 数値の誤りは原理的に消えるが、抽出
  すべき意図が増えて抽出側の失敗率が上がる。仕様表で足りるかをまず確認する
- **サイドバーで条件を指定するUI**: 決定的だがチャットの体験と別の操作になる

## 5. データ層

### 5.1 フロントマターの採用規則

`ingest/parsers/md_parser.py` の `_drop_frontmatter` を `_split_frontmatter` に
置き換え、捨てずに返す。**埋め込みテキストには含めない**（現行の判断を維持）。

`key: value` 形式のスカラー値のみを採用する。

| 元の値 | 採用する型 | 理由 |
|---|---|---|
| `noise_wash_db: 26` | `int` 26 | `where` の数値比較に必要 |
| `washing_capacity_kg: 11.0` | `float` 11.0 | 同上 |
| `price_tier: ハイグレード` | `str` | 一致比較に使える |
| `tags: [IoT, スリム]` | 採用しない | ChromaDBの `where` が部分一致を扱えず実用にならない |

型の判定は値の見た目で行う。整数に見えれば `int`、小数点を含み数値に見えれば
`float`、それ以外は前後の空白を除いた `str` とする。

### 5.2 予約キーとの衝突

既存のチャンクメタデータは次のキーを使っている。

```
source / file_hash / location_type / location / ocr / heading / chunk_index / indexed_at
```

同名の属性がフロントマターにあった場合は**採用しない**。黙って上書きすると出典表示や
差分取り込みのハッシュ判定が壊れるためである。現在の実データに衝突はないが、
資料を入れ替えたときに静かに壊れることを防ぐ。

### 5.3 データ構造の変更

`ParsedUnit` に `attributes: dict` を追加する。`chunk_units` がこれをチャンクの
メタデータへ展開する。1製品6セクションのすべてに同じ属性が乗るため、どのチャンクが
ヒットしても絞り込みが効く。

Markdown以外のパーサーは `attributes` を空のまま返すので、既存の取り込みは影響を
受けない。

## 6. 問い合わせの流れ

```
質問
 ├─ 条件抽出（ingest/conditions.py・LLM・JSON強制）
 │
 ├─ 条件あり ─→ 絞り込み（ingest/catalog.py）
 │               collection.get(where=...) で該当チャンクを取得
 │               ※ ベクトル検索ではないため取りこぼしが原理的に無い
 │               製品単位に集約して仕様表を生成
 │                 ├ 全条件に合致（主）
 │                 └ 条件を1つ外すと合致（参考・外した条件を明記）
 │               → 仕様表用プロンプトで回答
 │
 └─ 条件なし ─→ 現行のベクトル検索 → 現行のプロンプト（変更なし）
```

分類器は置かない。条件が1つ以上取れたかどうかで分岐する。判定基準が
「数値条件があるか」と明確で、分類の誤りという失敗点を増やさずに済む。

### 6.1 抽出に渡すスキーマ

利用可能なキーと型は、コレクションのメタデータから実際に存在するものを集めて
抽出プロンプトに渡す。キー一覧をコードに固定しないため、資料を入れ替えても
コードを直さずに追従する。

収集は起動時に1回だけ行い、結果をキャッシュする。460件のメタデータをすべて読む。
件数を絞ると、属性を持たないPDF由来のチャンクばかりを引いてスキーマが空になり得る
（ChromaDBの取得順は資料の並びを保証しない）。全件でも数十ミリ秒で、起動時の
1回だけである。予約キー（5.2）はスキーマから除外する。

### 6.2 抽出の出力形式

LLMには次の形のJSONだけを返させる。キーは属性名、値は演算子と数値の対にする。

```json
{"noise_wash_db": {"$lte": 26}, "installation_depth_min_mm": {"$lte": 510}}
```

許可する演算子は `$lte` / `$gte` / `$eq` の3つに限る。これはChromaDBの `where` が
そのまま受け取れる形であり、変換層を挟まずに済む。`$lte` と `$gte` は数値のみ、
`$eq` は数値と文字列の両方を受け付ける（`price_tier` のような文字列属性を
一致で絞れるようにするため）。

スキーマに無いキー、許可外の演算子、型の合わない値を含む条件は**個別に**捨て、
残った条件で絞り込む。1つでも壊れていたら全部捨てる作りにはしない。2条件のうち
片方だけが壊れている場合、残った条件で絞り込めるほうが利用者にとって有益だからである。
すべて捨てられた場合は「条件なし」としてベクトル検索へ回す。

条件が空であることと、抽出に失敗したことは区別する。前者は通常の質問であり、
後者は利用者に伝える必要がある（9節）。

### 6.3 「条件を1つ外すと合致」

条件が2つ以上あるときだけ、各条件を1つずつ外したクエリを追加で実行する。
運転音の質問の後半「同じ26dBでも設置できない機種がある場合、その型番と理由」に
答えるために必要である。`get` は埋め込み計算を伴わないため追加コストはほぼゼロ。

### 6.4 仕様表の形

```
条件: 運転音 ≤ 26dB / 防水パン ≤ 510mm

■ 全条件に合致（1件）
型番        洗濯容量  防水パン  運転音  出典
UD-1100iS   11.0kg   510mm    26dB   家電製品/UD-1100iS_spec_step3.md

■ 「防水パン ≤ 510mm」を外すと合致（3件）
UD-1100i    11.0kg   540mm    26dB   家電製品/UD-1100i_spec_step3.md
UD-1100iE   11.0kg   540mm    26dB   家電製品/UD-1100iE_spec_step3.md
UD-1100iP   11.0kg   540mm    26dB   家電製品/UD-1100iP_spec_step3.md
```

欠落がなく並びも揃っているため、モデルは読み取るだけで済む。散文チャンクを渡す
場合と違い、数値比較の負荷が大きく下がる。各行に出典を持たせ、現行の出典表示の
方針を維持する。

## 7. モジュール構成

| ファイル | 責務 | 変更 |
|---|---|---|
| `ingest/parsers/md_parser.py` | Markdown抽出 | `_drop_frontmatter` → `_split_frontmatter` |
| `ingest/models.py` | データ構造 | `ParsedUnit.attributes` を追加 |
| `ingest/chunker.py` | ユニット→チャンク | 属性の展開・予約キー衝突の回避 |
| `ingest/conditions.py` | **新規** 質問→条件（LLM抽出） | — |
| `ingest/catalog.py` | **新規** 条件→仕様表 | — |
| `ingest/prompting.py` | プロンプト組み立て | 仕様表用を追加・空ヒット時の欠陥を修正 |
| `scripts/ingest_source.py` | 取り込みCLI | `--only-suffix` |
| `rag_chat_app.py` | UI | 2経路の結線と経路の表示 |

`conditions.py`（LLMに依存）と `catalog.py`（純粋な計算）を分けるのは、後者を
LLMなしでテストできるようにするためである。

## 8. 既存チャンクへの反映

メタデータの追加は取り込み経路を通す必要があるが、ファイル内容が変わらないため
ハッシュ判定でスキップされる。`--force` を使うと OCR 23ページを含む全38ファイルが
再処理され約24分かかる。

`scripts/ingest_source.py` に `--only-suffix` を追加し、対象を拡張子で絞れるように
する。拡張子を1つ受け取り、先頭のドットの有無は問わない。**このオプションを
指定したときは孤児削除を行わない。** 対象外のファイルがすべて孤児と判定され、
他形式の279チャンクが消えるためである。

```powershell
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --force --only-suffix .md
```

Markdown 30ファイルのみが再処理され、OCRを伴わないため数十秒で終わる。

**実行前に `chroma_db` を開く他のプロセスが無いことを必ず確認する。** 同時アクセスに
よるHNSWインデックス破損の実績があるため（README「既知の制約」参照）。

## 9. エラー処理

| 事象 | 振る舞い |
|---|---|
| 抽出JSONが壊れている / 未知のキー・演算子 | 条件なし扱いでベクトル検索へフォールバック。UIに「条件を解釈できませんでした」と表示し、黙って劣化させない |
| 抽出のLLM呼び出しが失敗 | 同上 |
| 絞り込み結果が0件 | 空の表を渡さず「条件に合う機種はありません」という専用メッセージで回答させる |

### 9.1 併せて修正する既知の欠陥

現行の `build_prompt` は `if not hits: return question` であり、根拠が1件も無いときに
「根拠がなければ答えない」という指示ごと外れる。残るのは「あなたは有能な
アシスタントです」という、むしろ知識で答えることを促す指示だけになる。

**最もハルシネーションが起きやすい場面で歯止めが消えている**ため、根拠ゼロ専用の
プロンプトに差し替える。今回の調査で見つかった、絞り込みとは別経路の
ハルシネーション源である。

## 10. テスト方針

LLMに依存しない部分を通常テストで網羅する。

- フロントマターのパース: スカラー・配列の除外・型変換・予約キー衝突・
  フロントマター無し・閉じられていないフロントマター
- チャンクメタデータへの属性展開（分割されても全チャンクが属性を持つこと）
- 条件から `where` への変換、および不正な入力（壊れたJSON・未知キー・未知演算子）の扱い
- 仕様表の生成: 並び順、全条件合致と一部合致の分離、0件の扱い

抽出はLLM応答をフェイクして検証する。実LLMを使う確認は `integration` マークに置き、
通常のテスト実行を遅くしない。

受け入れ確認として、本設計書 第1節の2つの質問が正答することを実データで確かめる。

- 容量: 最大11.0kg、該当は UD-1100S と UD-1100iS
- 運転音: 該当は UD-1100iS のみ。同じ26dBの UD-1100i / UD-1100iE / UD-1100iP は
  防水パン540mm以上が必要なため設置不可

## 11. 想定される影響

- チャンク数は変わらない（460のまま）。メタデータのキーが増えるだけである
- Markdown 30ファイルの再取り込みが必要（数十秒）
- 絞り込み経路ではLLM呼び出しが1回増える（抽出）。回答生成と合わせて2回になる
- 通常の質問の経路は一切変わらない

## 12. 今回やらないこと

- 配列属性（`tags` / `target_users`）での絞り込み。`where` が部分一致を扱えないため
- 集約（最大・件数）のコード側計算。仕様表で足りるかをまず確認する
- サイドバーでの手動フィルタUI
- PDF/PPTX/DOCX へのメタデータ付与。フロントマターを持たないため対象外
- 抽出専用モデルの導入。`llama3.1:8b` にJSON強制で行わせ、不安定なら改めて検討する

## 13. 残るリスク

条件抽出が新しい失敗点になる。`llama3.1:8b` は本調査で「535mm以上」を510mmが
満たすと解釈する誤りを示しており、条件の向き（以上・以下）を取り違える可能性がある。
実装順序を「データ層 → 再取り込み → 抽出」とし、抽出の段階でこの不安定さが
測定できるようにする。不安定なら正規表現による補助か、抽出専用の小さいモデルを
検討する。
