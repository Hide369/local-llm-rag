# コーディングエージェントから社内資料を引く MCP サーバ設計書

作成日: 2026-09-05

## 1. 目的

ベクトルDB `chroma_db` に取り込み済みの社内資料を、**コーディングエージェント
（Codex / gpt-oss:20b）から検索できるようにする**。

現状、`chroma_db` を引ける経路は Streamlit の `rag_chat_app.py` だけである。
資料の内容を踏まえてコードや設定を書きたいとき、利用者はチャット画面で質問し、
得られた回答を手でエディタ側へ運んでいる。この転記が、エージェントに資料を
参照させられない唯一の理由になっている。

本設計は `chroma_db` を MCP サーバとして公開し、**エージェントが自分の判断で
社内資料を引ける**状態にする。

## 2. 前提と制約

### 2.1 導入先環境

本設計の成果物は、開発機だけでなく導入先の環境でも動く必要がある。

| 項目 | 状態 |
|---|---|
| Ollama サーバ | 設置済み。`gpt-oss:20b` が導入済み |
| `bge-m3` | **未導入。本設計の前提として `ollama pull bge-m3` が必須** |
| Codex | `gpt-oss` で動作する状態で設置済み |
| インターネット | 到達可能（LLM をローカルに置く方針であり、通信そのものは禁じられていない） |
| 資料 | 先方が保有するものを使う。開発機の `source/` および `chroma_db/` は移植しない |
| 取り込み経路 | **未定**。GitLab CI か手動 CLI かは決まっていない |

`bge-m3` が必須なのは、質問文のベクトル化に使うためである（`ingest/embedder.py`
の `EMBED_MODEL`）。`gpt-oss:20b` では代替できない。埋め込みモデルが取り込み時と
検索時で食い違うと、例外は出ないまま検索結果だけが無意味になる。

取り込み経路が未定である以上、**CI がある環境とない環境の両方で壊れない設計**が
要求される。これが 5 節の排他制御を決める制約になっている。

### 2.2 既存の検索パイプラインの性質（本設計で変更しない）

- `ingest/retrieval.py` の `search()` が、ベクトル検索と BM25 を RRF で融合し、
  上位 `RERANK_CANDIDATE_COUNT` 件をクロスエンコーダで測り直して返す。
- 圏内判定はベクトル側の `RELEVANCE_THRESHOLD`（0.50）が受け持つ。
  圏外なら 0 件が返る。
- `Hit.citation` が出典整形の唯一の置き場所である
  （「ファイル名 p.48（OCR）」形式）。
- BM25 インデックスはディスクに持たず、`build_index()` が起動時に DB から組む。
  DB を唯一の情報源に保つための設計であり、本設計もこれに従う。
- `search()` はインデックスに残る削除済みチャンクIDに対して既に耐性を持つ
  （`vector_rows` に無い行はスキップする）。**実害があるのは追加分が BM25 に
  入らないケースだけである。**

### 2.3 Codex の MCP 対応

Codex は `~/.codex/config.toml` の `mcp_servers` で 2 通りの接続に対応する。

- **stdio**: `command` / `args` / `cwd` / `env` を指定し、子プロセスとして起動する。
- **streamable HTTP**: `url` を指定する。`http_headers` でヘッダを付けられる。

本設計の RAG サーバは **stdio** を採る。ローカルの `chroma_db` を読むだけであり、
HTTP を挟む理由がない。

**stdio であることは排他制御に直接影響する。** MCP サーバはポートを持たないため、
`scripts/ci_ingest.ps1` が Streamlit に対して行っている「待ち受けポートの監視」
では検知できない。

### 2.4 外部通信するツールの併存

同じ Codex に context7（`https://mcp.context7.com/mcp`）を併設する。これは
**本構成で唯一、社外へ通信するツール**である。送信されるのは公開OSSライブラリに
関する問い合わせ文字列であり、`chroma_db` の内容が送られることはない。

ただしエージェントが問い合わせ文に社内固有の文脈を混ぜる経路は残るため、
7.2 節の `AGENTS.md` で明示的に禁じる。

## 3. 検討した選択肢と却下理由

### 3.1 `AGENTS.md` に ChromaDB の参照手順を書くだけ（却下）

「`chroma_db` を参照して回答せよ」と `AGENTS.md` に書く案。

却下理由は、**`AGENTS.md` は指示書であって接続手段ではない**ため。Codex に
`chroma_db` を開く道具が無い状態でいくら指示を書いても、エージェントは資料を
引けない。仮にエージェントが `chroma_db/chroma.sqlite3` を直接読もうとしても、
ベクトルは `bge-m3` で作られており、同じモデルで質問を埋め込まない限り検索は
成立しない。さらにハイブリッド検索・RRF・リランカー・圏内判定という既存の
積み上げがすべて無効になる。

`AGENTS.md` の役割は「用意されたツールを、いつ、どう使うか」である（7.2 節）。

### 3.2 回答文を返す（`ask_documents`・却下）

MCP サーバ内部で検索から生成まで行い、出典付きの回答文を返す案。
`ingest/prompting.py` の資産をそのまま使える利点がある。

却下理由は 2 つ。

1. **`gpt-oss:20b` が 1 問につき 2 回走る**（MCP 内部と Codex 側）。ローカル実行では
   体感が重く、リランカーの CPU 推論とも競合する。
2. Codex から見て中身が不透明な「相談窓口」になり、**取得した原文をコードや設定へ
   統合する余地が失われる**。コーディングエージェントに要るのは判断済みの答えでは
   なく根拠となる原文である。

なお圏内判定（`RELEVANCE_THRESHOLD`）は `search()` 自身が持つため、チャンクを
返す方式でもこの歯止めは失われない。

### 3.3 `search_documents` と `ask_documents` の両方を出す（却下）

用途で使い分けられるが、初手で 2 本持つ理由がない。3.2 の不足が実運用で
実証されてから足す。

### 3.4 リクエストごとに `PersistentClient` を開閉する（却下）

常駐しなければ競合も陳腐化も起きない、という案。

却下理由は、`PersistentClient` の生成が HNSW のロードを伴い、加えて
`build_index()` が全チャンクを DB から読み直すため、**1 リクエストごとに
数百ms〜秒のコストが乗る**こと。エージェントは 1 タスク中に何度も検索するため、
この方式は現実的でない。

### 3.5 読む側（MCP サーバ）がロックを取る（却下）

MCP サーバが起動時にロックを置き、取り込み側がそれを見て中止する案
（`ci_ingest.ps1` が Streamlit に対して行っていることの一般化）。

却下理由は、**読み手が増えるたびにロックの主体が増える**こと。現時点でも
Streamlit・MCP サーバの 2 つがあり、どちらかが異常終了するとロックが残り、
取り込みが永久に始まらなくなる。加えて MCP サーバは Codex がセッションごとに
起こす子プロセスであり、生存期間が利用者の操作に左右されて読みにくい。

**書き手は `ingest_source.py` ただ一つである。** ロックの主体を書き手側に置けば、
主体は 1 つに固定され、CI の有無にも左右されない（5.1 節）。

## 4. 構成

### 4.1 データフロー

```
[資料] --push--> GitLab --CI--> ci_ingest.ps1 ─┐
                                               ├─> ingest_source.py --bge-m3--> chroma_db
[資料] ------------ 手動 CLI ------------------┘        （.ingest.lock を保持）
                                                                   │
                                                                   │ 読み取り
                                                                   ▼
                                       Codex --stdio--> rag_mcp_server.py
                                         │                search_documents
                                         │                （search() をラップ）
                                         ├--HTTP--> context7（社外・OSSドキュメント）
                                         └--local--> playwright
```

### 4.2 ファイル配置

| ファイル | 区分 | 役割 |
|---|---|---|
| `scripts/rag_mcp_server.py` | 新規 | stdio MCP サーバ本体 |
| `tests/test_rag_mcp_server.py` | 新規 | テスト |
| `ingest/store.py` | 改修 | 取り込み中ロックの取得・解放（関数の置き場所） |
| `scripts/ingest_source.py` | 改修 | そのロックで取り込み全体を囲む |
| `requirements.txt` | 改修 | `mcp` を追加 |
| `docs/依存関係一覧.md` | 改修 | `mcp` の用途と使用箇所を表に追加 |
| `AGENTS.md` | 新規 | Codex へのツール使い分け指示 |
| `docs/mcp-server.md` | 新規 | 設定手順（導入先向け） |

`ingest/` の検索系モジュールは変更しない。サーバは `retrieval.search()` を
呼ぶだけである。

ロックの関数を `store.py` に置くのは、`chroma_db` への出入りをここに集約している
ためである。ロックを取る主体は `ingest_source.py` であり（5.1 節）、`store.py` は
その手段を提供するだけで自らは取らない。

`requirements.txt` は「本システムが直接 import するパッケージだけを実績のある
バージョンで固定する」方針であり、`mcp` も実測したバージョンで固定する。同ファイル
冒頭の指示どおり `docs/依存関係一覧.md` の表も同時に更新する。

DB のパスは `rag_chat_app.py` および `scripts/ingest_source.py` と同じく、
リポジトリルート直下の `chroma_db/` を指す。サーバは `__file__` から解決し、
引数や環境変数では受け取らない。パスが 3 か所で食い違うと、空の DB を黙って
検索する状態が生まれるためである。

### 4.3 ツール定義

```
search_documents(query: str, n_results: int = 4) -> str
```

- `query`: 検索したい内容。エージェントが組み立てた自然文。
- `n_results`: 返すチャンク数。既定は `SEARCH_RESULT_COUNT`（4）。

ツールは 1 本だけとする。会話履歴を踏まえたクエリ書き換え（`contextual_query`）は
Codex 側が文脈を持つため不要であり、属性による絞り込みは 10 節でスコープ外とする。

### 4.4 返却フォーマット

返り値は **Markdown テキスト**であり、構造化 JSON ではない。MCP のツール結果を
最終的に読むのは LLM であり、`ingest/prompting.py` の `format_hit_caption` を
そのまま再利用できて、Streamlit 画面と根拠の見え方が揃うためである。

```
社内資料から 2 件が見つかりました。

## [1] モデル就業規則.pdf p.12
cosine距離 0.412（しきい値 0.5） ／ BM25 12.34 ／ Reranker 0.87

第38条 年次有給休暇は…

## [2] 【第3回】RAG対象データ確定会議（議事録）.docx
cosine距離 未計測（BM25で採用） ／ BM25 9.87 ／ Reranker 0.61

…
```

出典行は `Hit.citation` が組み立てる。位置種別（ページ・スライド・見出し）の
整形をここで再実装してはならない。

### 4.5 `build_prompt` の歯止めを引き継ぐ

チャンクを返す方式（案A）を採ることで、`ingest/prompting.py` の `build_prompt` が
持っていた次の 2 つの歯止めが、そのままでは失われる。

1. **根拠が質問と無関係なら使わない。** しきい値 0.50 は関連度の高さまでは保証
   しない。挨拶のような意味的に空な入力はコーパスの重心付近（距離 0.349〜0.381）に
   落ち、しきい値では弾けない。
2. **資料にない主体を補わない。** 実測で `gpt-oss:20b` が、社内向け導入ガイドと
   いう文脈から誤って類推し「弊社が提供する」という資料に無い主語を補った。

これらは距離やフィルタでは解決できず、プロンプトが最後の砦である。案A では
その砦の位置が `build_prompt` から次の 2 か所へ移る。

- **ツール結果の末尾**に注意書きを添える（サーバが出力する）。
- **`AGENTS.md`** に恒久的な規範として書く（7.2 節）。

0 件のときは、`build_prompt` の 0 件分岐と同じ趣旨の文言を返す。

```
社内資料を検索しましたが、この質問に関連する記述は見つかりませんでした。
推測で答えず、社内資料からは回答できない旨を伝えてください。
```

ここで空文字や空配列を返してはならない。エージェントは根拠が無いときこそ、
自分の知識で答えにいくためである。

## 5. 排他制御とインデックスの鮮度

### 5.1 ロックファイル

書き手である `ingest_source.py` が、処理中だけロックファイルを置く。

```
chroma_db/.ingest.lock
```

- 中身は PID と開始時刻。異常終了時に人が判断できる材料を残す。
- MCP サーバは**リクエストのたびに**存在を確認し、有れば検索せずに
  「取り込み中です。完了後に再試行してください」を返す。
- ロックは `try` / `finally` で必ず解放する。

読み手ではなく書き手に主体を置く理由は 3.5 節に記した。この方式は
**CI がある環境でもない環境でも同じに働く**。`ci_ingest.ps1` は
`ingest_source.py` を呼ぶだけであり、ロックはその内側で取られるからである。

既存の Streamlit ポート監視（`ci_ingest.ps1` の第 3 ガード）はそのまま残す。
Streamlit は `@st.cache_resource` で `PersistentClient` をプロセス内に保持し、
再起動するまで更新を拾わないという別の問題を持つためで、ロックでは代替できない。

### 5.2 インデックスの再構築判定

MCP サーバは常駐するため、CI や手動 CLI が取り込みを行うと BM25 インデックスが
古くなる。リクエストごとに次の 2 つを見て、いずれかが変化していれば
`build_index()` を組み直す。

| 指標 | 取得方法 | 検知できるもの |
|---|---|---|
| チャンク数 | `collection.count()` | 資料の追加・削除 |
| DB の更新時刻 | `chroma.sqlite3` の mtime | **同数のままの差し替え** |

`count()` だけでは、1 ファイルを同じチャンク数の別内容に差し替えた場合を
取りこぼす。mtime はファイルシステムへの 1 コールで済むため併用する。

ベクトル検索側は毎回 DB へ問い合わせるため、この判定は BM25 のためだけにある。

## 6. エラーハンドリング

| 事象 | 挙動 |
|---|---|
| `.ingest.lock` が存在 | 「取り込み中」を返す。古い結果を返さない |
| Ollama 未疎通 | `embedder.check_ollama` の文言をそのまま返す |
| `bge-m3` 不在 | 同上（「`ollama pull bge-m3` を実行してください」） |
| `chroma_db/` 不在・0 チャンク | 「取り込みが未実行です」 |
| リランカーの取得失敗 | `rerank=None` で検索を続行する（既存の劣化運転方針） |
| 圏内 0 件 | 4.5 節の文言を返す |

サーバは起動時に Ollama へ疎通確認を行わない。Codex はセッション開始時に MCP
サーバを起こすため、そこで失敗させると Ollama を使わない作業まで巻き添えになる。
確認は最初の検索リクエスト時に行う。

## 7. Codex 側の設定

### 7.1 `~/.codex/config.toml`

```toml
[mcp_servers.local_docs]
command = "C:\\...\\local_llm\\myvenv313\\Scripts\\python.exe"
args = ["-m", "scripts.rag_mcp_server"]
cwd = "C:\\...\\local_llm"

[mcp_servers.context7]
url = "https://mcp.context7.com/mcp"
http_headers = { "CONTEXT7_API_KEY" = "YOUR_API_KEY" }

[mcp_servers.playwright]
command = "npx"
args = ["-y", "@playwright/mcp@latest"]
```

`cwd` の指定は必須である。`python scripts\rag_mcp_server.py` 形式の直接起動では
`sys.path` にリポジトリルートが入らず `from ingest import ...` が
`ModuleNotFoundError` になる（`ci_ingest.ps1` と同じ理由）。`-m` 起動と
`cwd` の組み合わせで解決する。

context7 に `npx` 方式ではなく `url` 方式を採るのは、Windows で `npx.cmd` の
絶対パス指定や `SystemRoot` / `APPDATA` の明示が必要になる既知の躓きがあり
（公式 README にトラブルシュート専用の設定例が置かれている）、`url` 方式なら
これを回避できるためである。playwright はブラウザを実際に起動する以上ローカル
実行が必須で、Node / npx は導入先に別途必要になる。

### 7.2 `AGENTS.md`

リポジトリルートに置く。**ツールの使い分けと、4.5 節の歯止めを書く場所である。**

```markdown
## 社内資料の参照

- 社内資料・規程・議事録・会議録に関する質問は、推測せず `search_documents` で
  検索し、返された出典を明記して回答すること。
- 検索結果が質問と無関係な場合は、それを根拠に使わず「資料からは回答できない」と
  答えること。距離が閾値内であることは関連性を保証しない。
- 資料に書かれていない主体（「弊社が」等）を補わないこと。

## 外部ドキュメントの参照

- OSS ライブラリ・フレームワークの API や設定は `context7` で調べること。
- 社内固有の情報を context7 のクエリ文に含めないこと。context7 は社外の
  サービスであり、本構成で唯一外部へ通信する経路である。
```

### 7.3 superpowers プラグイン

```sh
codex plugin add superpowers@openai-curated
```

`~/.codex/plugins/cache/` へ配置され、`config.toml` に有効化が追記される。
MCP サーバとは別系統であり、本設計の対象外（手順の記録のみ）。

## 8. 導入先環境への移植

`git clone` 後に必要な作業。データは移植しない。

1. `pip install -r requirements.txt`（`mcp` を含む）
2. **`ollama pull bge-m3`**（2.1 節。これを欠くと検索が一切成立しない）
3. 先方の資料を `source/` に配置し、`python -m scripts.ingest_source` で取り込む
4. `~/.codex/config.toml` に 7.1 節の 3 サーバを登録する
5. `codex plugin add superpowers@openai-curated`

リランカー（`bge-reranker-v2-m3` ONNX）と RapidOCR のモデルは、初回実行時に
HuggingFace Hub から自動取得される。導入先はインターネットに到達できるため
事前の持ち込みは不要である。

GitLab CI の移植は本設計の対象外とする（10 節）。

## 9. テスト方針

既存の `tests/` の流儀に従い、Ollama も ChromaDB も実物を使わずに検証する。

| 対象 | 内容 |
|---|---|
| 整形 | `Hit` の列から 4.4 節の Markdown が組めること。出典行が `Hit.citation` の値と一致すること（整形を再実装していないことの確認） |
| 0 件 | 4.5 節の文言が返り、空文字でないこと |
| ロック | `.ingest.lock` 在時に検索せず「取り込み中」を返すこと |
| 鮮度 | `count()` 変化時と mtime 変化時にそれぞれ `build_index()` が呼ばれること |
| 鮮度（逆） | どちらも変化していなければ `build_index()` が**呼ばれない**こと |
| エラー | Ollama 未疎通時に `check_ollama` の文言が返ること |

`build_index()` が呼ばれないことの確認を入れるのは、判定を誤って常に真にすると
毎リクエストで全チャンクを読み直し、例外が出ないまま遅くなるだけになるためである。

## 10. スコープ外（YAGNI）

- **`ask_documents`**（3.2 節で却下）
- **会話履歴に基づくクエリ書き換え**（`contextual_query`）。Codex 側が文脈を持つ
- **属性による絞り込み**（`ingest/conditions.py` / `catalog.py`）。まず全文検索で
  運用し、不足が実証されてから足す
- **MCP の HTTP 版**。ローカルの DB を読むだけであり HTTP を挟む理由がない
- **導入先への GitLab / Runner の移植**。`2026-09-05-ci-ingest-design.md` の
  完了後に別途判断する
- **Streamlit 側のロック対応**。既存のポート監視を維持する（5.1 節）

## 11. 未確定事項

- **導入先の取り込み経路**（CI か手動 CLI か）。本設計はどちらでも動くため、
  実装の着手を妨げない。
- **context7 の API キー**。無くても動作するが、レート制限が厳しくなる。
  先方で取得するかは運用判断。

  よる自動無効化は、実際に残留が起きてから検討する（先に作ると、生きている
  取り込みを誤って無効と判断する経路が増える）。
