# コーディングエージェントから社内資料を引く MCP サーバ設計書

作成日: 2026-09-05
改訂日: 2026-09-08

## 0. 改訂履歴

初版はベクトルDBが ChromaDB だった時代に書かれた。その後 master に3つの変更が入り、
本設計の前提が変わった。

| 変更 | 本設計への影響 |
| --- | --- |
| ベクトルストアを SQLite + numpy へ置き換え | DBを開くコストが消えた（下記） |
| 重複チャンクの畳み込み（`revision()` 導入） | 鮮度判定の機構が手に入った。出典が複数資料を持つようになった |
| ナビゲーション用スライドの除外 | 影響なし |

**実測により3つの節が不要になった**（2026-09-08、570出現・本文512種）。

| 初版の節 | 根拠だったもの | 実測 | 改訂後 |
| --- | --- | --- | --- |
| 3.4 毎回開き直す案の却下 | `PersistentClient` 生成が HNSW ロードを伴い数百ms〜秒 | `open_store()` は **0.40ms** | 却下理由を差し替え。結論（常駐する）は維持 |
| 5.1 ロックファイル | ChromaDB の同時アクセス制約 | 書き込み中の読み取りは**待ち0ms**で一貫スナップショットを得る | **削除** |
| 5.2 count + mtime | 同数差し替えを mtime で拾う苦肉の策 | `revision()` が **0.02ms** | **`revision()` 一本に置換** |

常駐する結論は変わらないが、理由が変わった。**開くのが重いからではなく、BM25索引の
構築に57msかかるから**である（実測、本文512種）。エージェントは1タスク中に何度も
検索するため、毎回組み直すと積み上がる。

ロックを廃止したことで、初版4.2節にあった `ingest/store.py` と
`scripts/ingest_source.py` への改修も消えた。**取り込み側は一切変更しない。**

## 1. 目的

ベクトルDB `vector_store.sqlite3` に取り込み済みの社内資料を、**コーディング
エージェント（Codex / gpt-oss:20b）から検索できるようにする**。

現状、このDBを引ける経路は Streamlit の `rag_chat_app.py` だけである。資料の内容を
踏まえてコードや設定を書きたいとき、利用者はチャット画面で質問し、得られた回答を
手でエディタ側へ運んでいる。この転記が、エージェントに資料を参照させられない唯一の
理由になっている。

本設計はこのDBを MCP サーバとして公開し、**エージェントが自分の判断で社内資料を
引ける**状態にする。

## 2. 前提と制約

### 2.1 導入先環境

本設計の成果物は、開発機だけでなく導入先の環境でも動く必要がある。

| 項目 | 状態 |
| --- | --- |
| Ollama サーバ | 設置済み。`gpt-oss:20b` が導入済み |
| `bge-m3` | **未導入。本設計の前提として `ollama pull bge-m3` が必須** |
| Codex | `gpt-oss` で動作する状態で設置済み |
| インターネット | 到達可能（LLM をローカルに置く方針であり、通信そのものは禁じられていない） |
| 資料 | 先方が保有するものを使う。開発機の `source/` および `vector_store.sqlite3` は移植しない |
| 取り込み経路 | **未定**。GitLab CI か手動 CLI かは決まっていない |

`bge-m3` が必須なのは、質問文のベクトル化に使うためである（`ingest/embedder.py`
の `EMBED_MODEL`）。`gpt-oss:20b` では代替できない。埋め込みモデルが取り込み時と
検索時で食い違うと、例外は出ないまま検索結果だけが無意味になる。

取り込み経路が未定である以上、**CI がある環境とない環境の両方で壊れない設計**が
要求される。初版ではこれが排他制御の制約になっていたが、ロックを廃止したため
（0節）、現在は取り込み側に手を入れないことでこの要求を満たしている。

### 2.2 既存の検索パイプラインの性質（本設計で変更しない）

- `ingest/retrieval.py` の `search()` が、ベクトル検索と BM25 を RRF で融合し、
  上位 `RERANK_CANDIDATE_COUNT` 件をクロスエンコーダで測り直して返す。
- 圏内判定はベクトル側の `RELEVANCE_THRESHOLD`（0.50）が受け持つ。
  圏外なら 0 件が返る。
- 出典の整形は `Hit.citation`（1件に丸めた表示）と `Hit.all_citations()`
  （全件のリスト）が持つ。重複チャンクの畳み込み以降、1つの本文が複数の資料に
  現れうるため、`citation` は「ファイル名 スライド25 ほか6資料」の形に丸める。
- BM25 インデックスはディスクに持たず、`build_index()` が DB から組む。
  DB を唯一の情報源に保つための設計であり、本設計もこれに従う。
- 書き込みは `replace_source()` が資料ごとに1トランザクションで行い、
  `revision()` がそのトランザクションの内側で加算される。**読み手はこの値だけを
  見れば鮮度を判定できる。**

### 2.3 Codex の MCP 対応

Codex は `~/.codex/config.toml` の `mcp_servers` で 2 通りの接続に対応する。

- **stdio**: `command` / `args` / `cwd` / `env` を指定し、子プロセスとして起動する。
- **streamable HTTP**: `url` を指定する。`http_headers` でヘッダを付けられる。

本設計の RAG サーバは **stdio** を採る。ローカルのDBを読むだけであり、HTTP を挟む
理由がない。

### 2.4 外部通信するツールの併存

同じ Codex に context7（`https://mcp.context7.com/mcp`）を併設する。これは
OSS ドキュメントに関する問い合わせ文字列であり、DBの内容が送られることはない。
この使い分けは `AGENTS.md` に規範として書く（8.2 節）。

## 3. 検討した選択肢と却下理由

### 3.1 `AGENTS.md` に参照手順を書くだけ（却下）

「`vector_store.sqlite3` を参照して回答せよ」と `AGENTS.md` に書く案。

却下理由は、**`AGENTS.md` は指示書であって接続手段ではない**ため。Codex にDBを開く
道具が無い状態でいくら指示を書いても、エージェントは資料を引けない。仮に
エージェントが sqlite を直接読もうとしても、ベクトルは `bge-m3` で作られており、
同じモデルで質問を埋め込まない限り検索は成立しない。さらにハイブリッド検索・RRF・
リランカー・圏内判定という既存の積み上げがすべて無効になる。

`AGENTS.md` の役割は「用意されたツールを、いつ、どう使うか」である（8.2 節）。

### 3.2 回答文を返す（`ask_documents`・却下）

MCP サーバ内部で検索から生成まで行い、出典付きの回答文を返す案。
`ingest/prompting.py` の資産をそのまま使える利点がある。

却下理由は 2 つ。

1. **`gpt-oss:20b` が 1 問につき 2 回走る**（MCP 内部と Codex 側）。ローカル実行では
   体感が重く、リランカーの CPU 推論とも競合する。
2. Codex から見て中身が不透明な「相談窓口」になり、**取得した原文をコードや設定へ
   統合する余地が失われる**。コーディングエージェントに要るのは判断済みの答えでは
   なく根拠となる原文である。

なお圏内判定（`RELEVANCE_THRESHOLD`）は `search()` 自身が持つため、チャンクを
返す方式でもこの歯止めは失われない。

### 3.3 `search_documents` と `ask_documents` の両方を出す（却下）

用途で使い分けられるが、初手で 2 本持つ理由がない。3.2 の不足が実運用で
実証されてから足す。

### 3.4 リクエストごとにDBを開閉する（却下・理由を改訂）

常駐しなければ陳腐化も起きない、という案。

**初版の却下理由（`PersistentClient` の生成が HNSW のロードを伴う）は、
ストアの置き換えにより無効になった。** 現在の実測は次のとおり。

| 操作 | 中央値 |
| --- | --- |
| `open_store()` | 0.40ms |
| `build_index()`（BM25索引を組む） | 57.15ms |
| 開く→索引（毎リクエストやり直す全部） | 59.02ms |
| `revision()` を読むだけ | 0.02ms |

（2026-09-08、570出現・本文512種）

**却下理由は残るが、中身が入れ替わった。** 開くコストは消えたが、BM25索引の構築が
57msかかる。エージェントは1タスク中に何度も検索するため、毎回組み直せば積み上がる。
常駐して `revision()`（0.02ms）で鮮度を見れば、変わっていない限り組み直さずに済む。

### 3.5 読む側（MCP サーバ）がロックを取る（却下・記録として残す）

MCP サーバが起動時にロックを置き、取り込み側がそれを見て中止する案。

却下理由は、**読み手が増えるたびにロックの主体が増える**こと。Streamlit・MCP
サーバの 2 つがあり、どちらかが異常終了するとロックが残り、取り込みが永久に
始まらなくなる。

**なお 0 節のとおり、書き手側のロックも廃止した。** この節は「ロックを置くなら
どちらの主体か」という検討の記録として残す。実測により、そもそもロックが要らない
ことが分かったためである（5 節）。

## 4. 構成

### 4.1 データフロー

```
[資料] --push--> GitLab --CI--> ci_ingest.ps1 ─┐
                                               ├─> ingest_source.py --bge-m3--> vector_store.sqlite3
[資料] ------------ 手動 CLI ------------------┘                    │
                                                                   │ 読み取り（ロックなし）
                                                                   ▼
                                       Codex --stdio--> rag_mcp_server.py
                                         │                search_documents
                                         │                （search() をラップ）
                                         ├--HTTP--> context7（社外・OSSドキュメント）
                                         └--local--> playwright
```

### 4.2 ファイル配置

| ファイル | 区分 | 役割 |
| --- | --- | --- |
| `scripts/rag_mcp_server.py` | 新規 | stdio MCP サーバ本体 |
| `tests/test_rag_mcp_server.py` | 新規 | テスト |
| `docs/mcp-server.md` | 新規 | 設定手順（導入先向け） |
| `requirements.txt` | 改修 | `mcp` を実測バージョンで固定 |
| `docs/依存関係一覧.md` | 改修 | `mcp` の用途と使用箇所 |
| `AGENTS.md` | 改修 | **既に存在する。** ツール使い分けの節を追記する |
| `docs/処理箇所マップ.md` | 改修 | `scripts/` を対象に含む索引。新規スクリプトの節を足す |

初版から2つ減り、2つ増えた。減ったのは `ingest/store.py` と
`scripts/ingest_source.py`（ロック廃止による）。増えたのは処理箇所マップと、
`AGENTS.md` の区分変更（新規→改修）である。

**`ingest/` は一切変更しない。** サーバは `retrieval.search()` を呼ぶだけである。

`requirements.txt` は「本システムが直接 import するパッケージだけを実績のある
バージョンで固定する」方針であり、`mcp` も実測したバージョンで固定する。同ファイル
冒頭の指示どおり `docs/依存関係一覧.md` の表も同時に更新する。

DB のパスは `rag_chat_app.py` および `scripts/ingest_source.py` と同じく、
リポジトリルート直下の `vector_store.sqlite3` を指す。サーバは `__file__` から
解決し、引数や環境変数では受け取らない。パスが 3 か所で食い違うと、空の DB を
黙って検索する状態が生まれるためである。

### 4.3 ツール定義

```
search_documents(query: str, n_results: int = 4) -> str
```

- `query`: 検索したい内容。エージェントが組み立てた自然文。
- `n_results`: 返すチャンク数。既定は `SEARCH_RESULT_COUNT`（4）。

ツールは 1 本だけとする。会話履歴を踏まえたクエリ書き換え（`contextual_query`）は
Codex 側が文脈を持つため不要であり、属性による絞り込みは 11 節でスコープ外とする。

### 4.4 サーバの生存期間と状態

Codex がセッションごとに子プロセスとして起こす。プロセス内に持つのは 3 つ。

| 状態 | いつ用意するか | コスト |
| --- | --- | --- |
| `VectorStore` | 起動時に1回 `open_store()` | 0.40ms |
| BM25索引と、組んだときの `revision` | 初回検索時、以降は `revision` 変化時のみ | 57ms |
| リランカーのモデル | **初回検索時に遅延ロード** | 3.3秒・約570MB |

リクエストごとに `revision()` を読み（0.02ms）、前回と違えば索引を組み直す。
`rag_chat_app.py` が `@st.cache_resource` の鍵に使っているのと同じ機構である。

リランカーを遅延ロードするのは、Codex がセッション開始時にサーバを起こすためで
ある。起動時にロードすると、**検索しないセッションが 3.3 秒と 570MB を払う。**
代償は初回検索が 4.75 秒になること（ウォームアップ込み、実測）。2 回目以降は
0.72 秒である。

同じ理由で、サーバは起動時に Ollama へ疎通確認を行わない。そこで失敗させると
Ollama を使わない作業まで巻き添えになる。確認は最初の検索リクエスト時に行う。

### 4.5 返却フォーマット

返り値は **Markdown テキスト**であり、構造化 JSON ではない。MCP のツール結果を
最終的に読むのは LLM であり、`ingest/prompting.py` の `format_hit_caption` を
そのまま再利用できて、Streamlit 画面と根拠の見え方が揃うためである。

```
社内資料から 2 件が見つかりました。

## [1] cosine距離 0.413（しきい値 0.5） ／ BM25 45.76 ／ Reranker 0.87
出典:
- セミナー資料/CNN画像認識セミナー.pptx スライド25
- セミナー資料/RAGセミナー.pptx スライド22
- ニューラルネットワーク基礎セミナー.pptx スライド19

（本文）

## [2] cosine距離 未計測（BM25で採用） ／ BM25 9.87 ／ Reranker 0.61
出典:
- モデル就業規則.pdf p.12

（本文）
```

**出典は `Hit.all_citations()` で全件を並べる。** 画面表示に使う `Hit.citation` は
「ファイル名 スライド25 ほか6資料」と丸めるが、エージェントは取得した原文をコードや
設定へ統合するのが仕事であり、そのとき出典ファイルを直接開く。丸めた表示はその経路を
塞ぐ。

位置種別（ページ・スライド・見出し）の整形をここで再実装してはならない。整形は
`Hit` 側が持つ。

### 4.6 `build_prompt` の歯止めを引き継ぐ

チャンクを返す方式を採ることで、`ingest/prompting.py` の `build_prompt` が持っていた
次の 2 つの歯止めが、そのままでは失われる。

1. **根拠が質問と無関係なら使わない。** しきい値 0.50 は関連度の高さまでは保証
   しない。挨拶のような意味的に空な入力はコーパスの重心付近に落ち、しきい値では
   弾けない。
2. **資料にない主体を補わない。** 実測で `gpt-oss:20b` が、社内向け導入ガイドと
   いう文脈から誤って類推し「弊社が提供する」という資料に無い主語を補った。

これらは距離やフィルタでは解決できず、プロンプトが最後の砦である。本方式では
その砦の位置が `build_prompt` から次の 2 か所へ移る。

- **ツール結果の末尾**に注意書きを添える（サーバが出力する）。
- **`AGENTS.md`** に恒久的な規範として書く（8.2 節）。

0 件のときは、`build_prompt` の 0 件分岐と同じ趣旨の文言を返す。

```
社内資料を検索しましたが、この質問に関連する記述は見つかりませんでした。
推測で答えず、社内資料からは回答できない旨を伝えてください。
```

ここで空文字や空配列を返してはならない。エージェントは根拠が無いときこそ、
自分の知識で答えにいくためである。

## 5. 取り込み中の振る舞い

**ロックは置かない。取り込み中でも検索を通す。**

初版は `.ingest.lock` を置き、取り込み中の検索を「取り込み中です」で断る設計だった。
これは ChromaDB の同時アクセス制約に合わせたものである。実測により、その制約が
現在のストアには存在しないことが分かった。

```
journal_mode: delete
書き込みトランザクション実行中の読み取り: 読めた（500件） 待ち 0ms
```

SQLite のロールバックジャーナル方式では、書き手が RESERVED ロックを保持している
間も読み手は進める。読み手はトランザクション前の一貫したスナップショットを見る。
`SQLITE_BUSY` は実用上起きない（`busy_timeout` は 5000ms に設定済み）。WAL への
変更も不要である。

取り込みの途中では「資料 A は新しく、資料 B はまだ古い」という混在した世代を返し
うる。これは壊れたデータではなく、一貫したスナップショットである。ロックを置いて
検索を止める代わりに、**異常終了でロックが残ると検索が永久に止まる**という故障
モードを抱えるほうが割に合わない。

`ingest_source.py` と `store.py` には手を入れない。Streamlit 側の既存のポート監視
（`ci_ingest.ps1` の第 3 ガード）は、`@st.cache_resource` が更新を拾わない別の問題に
対するものなのでそのまま残す。

## 6. インデックスの鮮度

MCP サーバは常駐するため、CI や手動 CLI が取り込みを行うと BM25 インデックスが
古くなる。リクエストごとに `revision()` を読み、前回組んだときと違えば
`build_index()` を組み直す。

```
collection.revision()   # 0.02ms
```

`revision` は `replace_source()` の書き込みトランザクションの内側で加算される。
チャンク数を鍵にすると「1ファイルを同じチャンク数の別内容に差し替えた場合」を
取りこぼし、消えた旧チャンクIDを持ったままの BM25 索引が理由の説明なくヒットを
落とす。初版はこれを避けるために mtime を併用していたが、`revision` はその2つを
1つの値で置き換える。

ベクトル検索側は `VectorStore` 内部で同じ `revision` を見て行列を読み直すため
（`_current()`）、この判定は BM25 のためだけにある。

## 7. エラーハンドリング

| 事象 | 挙動 |
| --- | --- |
| Ollama 未疎通 | `embedder.check_ollama` の文言をそのまま返す |
| `bge-m3` 不在 | 同上（「`ollama pull bge-m3` を実行してください」） |
| `vector_store.sqlite3` 不在・0 チャンク | 「取り込みが未実行です」 |
| リランカーの取得失敗 | `rerank=None` で検索を続行する（既存の劣化運転方針） |
| 圏内 0 件 | 4.6 節の文言を返す |

初版にあった「`.ingest.lock` が存在」の行は、ロック廃止により削除した。

## 8. Codex 側の設定

### 8.1 `~/.codex/config.toml`

```toml
[mcp_servers.local_docs]
command = "C:\\...\\local_llm\\myvenv313\\Scripts\\python.exe"
args = ["-m", "scripts.rag_mcp_server"]
cwd = "C:\\...\\local_llm"

[mcp_servers.context7]
url = "https://mcp.context7.com/mcp"
env_http_headers = { "CONTEXT7_API_KEY" = "CONTEXT7_API_KEY" }

[mcp_servers.playwright]
command = "npx"
args = ["-y", "@playwright/mcp@latest"]
```

`cwd` の指定は必須である。`python scripts\rag_mcp_server.py` 形式の直接起動では
`sys.path` にリポジトリルートが入らず `from ingest import ...` が
`ModuleNotFoundError` になる。`-m` 起動と `cwd` の組み合わせで解決する。

context7 の API キーは `http_headers` で直接書かず、`env_http_headers` で環境変数
から取る。左辺がヘッダ名、右辺が参照する環境変数名である。`config.toml` は
秘密情報の置き場所ではなく、`.env` と同じ扱いにはできない（`.gitignore` の対象は
リポジトリ内のファイルであり、`~/.codex/config.toml` はその外にある）。

キーは `ctx7sk-` で始まり、Context7 のダッシュボードから無償で取得できる。
未設定でも動作するがレート制限が厳しくなるため、先方環境ではまず未設定で運用し、
制限に当たってから取得する（12 節）。

context7 に `npx` 方式ではなく `url` 方式を採るのは、Windows で `npx.cmd` の
絶対パス指定や `SystemRoot` / `APPDATA` の明示が必要になる既知の躓きがあり
（公式 README にトラブルシュート専用の設定例が置かれている）、`url` 方式なら
これを回避できるためである。playwright はブラウザを実際に起動する以上ローカル
実行が必須で、Node / npx は導入先に別途必要になる。

### 8.2 `AGENTS.md`

書かれている。本設計はそこへ節を追記するのであって、新規作成ではない。**既存の

## 9. 導入先環境への移植

`git clone` 後に必要な作業。データは移植しない。

1. `pip install -r requirements.txt`（`mcp` を含む）
2. **`ollama pull bge-m3`**（2.1 節。これを欠くと検索が一切成立しない）
3. 先方の資料を `source/` に配置し、`python -m scripts.ingest_source` で取り込む
4. `~/.codex/config.toml` に 8.1 節の 3 サーバを登録する
5. `codex plugin add superpowers@openai-curated`

リランカー（`bge-reranker-v2-m3` ONNX）と RapidOCR のモデルは、初回実行時に
HuggingFace Hub から自動取得される。導入先はインターネットに到達できるため
事前の持ち込みは不要である。

GitLab CI の移植は本設計の対象外とする（11 節）。

## 10. テスト方針

既存の `tests/` の流儀に従い、Ollama もリランカーも実物を使わずに検証する。

| 対象 | 内容 |
| --- | --- |
| 整形 | `Hit` の列から 4.5 節の Markdown が組めること。出典が `all_citations()` の**全件**と一致すること（整形を再実装していないことの確認） |
| 0 件 | 4.6 節の文言が返り、空文字でないこと |
| 鮮度 | `revision()` が変化したとき `build_index()` が呼ばれること |
| **鮮度（逆）** | `revision()` が変化していなければ `build_index()` が**呼ばれない**こと |
| リランカー | 検索していないセッションではモデルをロードしないこと |
| エラー | Ollama 未疎通時に `check_ollama` の文言が返ること |

**「呼ばれないこと」の確認を 2 つ置く。** 鮮度判定を誤って常に真にすると毎
リクエストで 57ms の索引構築が走り、遅延ロードを誤って常にロードすると検索しない
セッションが 3.3 秒と 570MB を払う。どちらも**壊れても症状が出ない**種類の欠陥で
あり、テストで縛る以外に検知手段がない。

## 11. スコープ外（YAGNI）

- **`ask_documents`**（3.2 節で却下）
- **会話履歴に基づくクエリ書き換え**（`contextual_query`）。Codex 側が文脈を持つ
- **属性による絞り込み**（`ingest/conditions.py` / `catalog.py`）。まず全文検索で
  運用し、不足が実証されてから足す
- **MCP の HTTP 版**。ローカルの DB を読むだけであり HTTP を挟む理由がない
- **リランカーの有効・無効を設定で切り替える**。既定で使う。導入先が非力だと
  判明してから足す
- **導入先への GitLab / Runner の移植**。`2026-09-05-ci-ingest-design.md` の
  完了後に別途判断する

初版にあった「Streamlit 側のロック対応」は、ロック自体が無くなったため削除した。
