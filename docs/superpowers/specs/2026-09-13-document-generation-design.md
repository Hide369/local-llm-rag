# 雛形からの文書生成（Cowork相当）設計書

作成日: 2026-09-13

## 1. 何を作るか

利用者が登録した雛形ファイルの空欄を、社内資料の検索結果とその場で添付した
ファイルから埋めて、ファイルとして返す。

これまでこのシステムの出力はチャットの回答テキストだけだった。「議事録を
作って」と頼んでも、利用者は画面の文字を Word に貼り直し、書式を整え直す
必要があった。検索で答えが出ることと、使える成果物が手に入ることは別である。

対応する形式は **`.docx` / `.xlsx` / `.pptx` / `.md`** の4つ。

成果物は議事録だけではない。**Mermaid のシーケンス図などを含む設計書**も対象で
ある。`.md` では Mermaid をコードブロックのまま入れれば図として表示されるが、
Word・Excel・PowerPoint は図として描かないため、**PNG に変換して埋め込む**
（7節）。

## 2. 設計の前提（利用者との合意事項）

| 論点 | 決めたこと |
|---|---|
| 生成の仕方 | 雛形の空欄（印）を埋める。書式・レイアウト・ロゴは雛形のまま保つ |
| 対応形式 | docx / xlsx / pptx / md。**drawio・png・jpeg・PDF は対象外** |
| 雛形の出どころ | 利用者が登録する |
| 中身の出どころ | 検索結果と、その場で添付したファイルの**両方** |
| 検索対象 | 社内資料／技術ドキュメントを**利用者がその回ごとに選ぶ**（既定は社内資料のみ） |
| 雛形の選び方 | 利用者が一覧から選ぶ |
| 添付ファイル | **その場限り。DBには入れない** |
| 件数が変わる中身 | 1つの印に複数行を入れる（表の行を増やす機能は作らない） |
| 画面 | チャット／Cowork のトグルで切り替える |

### PDF を対象外にした理由

実測（`pymupdf 1.28.2`、2026-09-13）で次を確認した。

- PDFのフォーム欄（AcroForm）の作成・読み取り・値の書き込み・保存は**できる**
- 日本語テキストの描画も内蔵CJKフォントで**できる**
- しかし **`{{印}}` の文字列置換は事実上できない**。PDFは文字を「位置」で持つ
  形式であり、印より長い文字列を入れると溢れて重なる
- docx から PDF への変換には LibreOffice か Word が要る。現在の依存には無く、
  Colab でもなく利用者のPC側の話になる

フォーム欄付きのPDFを雛形として登録してもらえば同じ方式に乗るが、雛形を作る
手間が利用者側に増える。今回は見送る。

## 3. 構成

新しいパッケージ `docgen/` を作る。`rag_chat_app.py`（665行）には画面だけを
足す。生成の中身をアプリ側に書くと、このファイルがさらに膨らみ、テストも
Streamlit 経由でしか書けなくなる。

```
docgen/
  __init__.py          拡張子で振り分ける（ingest/parsers/__init__.py と同じ形）
  templates.py         雛形の登録・一覧・読み出し
  docx_template.py     .docx の印の抽出と差し込み
  xlsx_template.py     .xlsx の印の抽出と差し込み
  pptx_template.py     .pptx の印の抽出と差し込み
  md_template.py       .md の印の抽出と差し込み
  filling.py           検索＋添付＋LLMで、印ごとの値を決める
  mermaid.py           Mermaid のテキストを PNG にする（`mmdc` を呼ぶ）
```

`ingest/parsers/` が「拡張子ごとに1ファイル＋振り分け役の `__init__.py`」で
既にうまく動いているため、書く側も同じ形にする。形式ごとの違いは4つの
`*_template.py` の中だけに閉じ、`filling.py` は形式を知らない。

### 責務の切れ目

| 部品 | 何をするか | 何を知らないか |
|---|---|---|
| `templates.py` | 雛形の保管と一覧 | 印の記法、埋める中身 |
| `*_template.py` | 印を見つける／値を差し込む | 検索、LLM、値の作り方 |
| `filling.py` | 印の名前から値を決める | ファイル形式、保存先 |
| `mermaid.py` | Mermaid のテキストを PNG にする | 印、検索、LLM、どの形式に貼るか |
| `rag_chat_app.py` | 画面と受け渡し | 上の全部の中身 |

`filling.py` は `ingest/conditions.py` と同じく **`ask` を引数で受け取る**。
値を決める規則のテストに実機のOllamaが要らなくなる。

### 依存

**Python の依存は追加しない。** `python-docx 1.2.0` / `openpyxl 3.1.5` /
`python-pptx 1.0.2` はいずれも既に入っており、読むだけでなく書ける。画像の
埋め込みに要る `pillow` も入っている。

**Python の外に1つだけ増える。** Mermaid を描く `@mermaid-js/mermaid-cli`
（Node.js）である。7節に理由と、入っていないときの振る舞いを書いた。

## 4. 雛形の保管

リポジトリ直下の `templates/` に原本を置き、`.gitignore` に追加する。

既存のアップロード（`scripts/ingest_source.py` の `ingest_uploads`）は「原本を
残さず、DBのチャンクだけ残す」という設計判断を採っている。雛形はこれと異なる。
**埋めるために原本そのものが要る**ためファイルとして残す。

`templates.py` が持つ操作は3つだけである。

```python
def register(source: Path) -> Path   # 雛形を templates/ へ保存し、置いた場所を返す
def templates() -> list[Path]        # 登録済みの一覧（ファイル名の昇順）
def remove(name: str) -> None        # ファイル名で雛形を消す
```

雛形の名前は**ファイル名そのもの**である（`議事録.docx`）。別名を付ける仕組みは
作らない。同名を登録したら上書きする。利用者にとっては「差し替え」であり、
版管理の仕組みは作らない。

対応する拡張子は `.docx` / `.xlsx` / `.pptx` / `.md` の4つだけで、それ以外は
`register()` が拒む。

## 5. 印の記法と見つけ方

### 記法

`{{名前}}`。名前はそのまま LLM への指示と画面表示に使うため、利用者が読んで
分かる日本語を書いてもらう（`{{決定事項}}`）。

### 形式ごとの走査

| 形式 | 走査する場所 | 注意点 |
|---|---|---|
| `.docx` | 段落、表のセル、ヘッダー・フッター | **段落単位**で組み立てて置換する |
| `.pptx` | 各スライドの図形のテキストと表 | docx と同じく段落単位 |
| `.xlsx` | 各シートのセルの値 | セルは文字列1つなので分割の問題はない |
| `.md` | 本文全体 | 単純な文字列置換 |

### run に割れる問題（実測 2026-09-13）

人が編集した docx は、1つの段落が複数の run に割れていることが普通にある。
実測では次のようになった。

```
段落: text='会議名：{{会議名}}'
      runs=['会議名：{{会議', '名}}']
```

`run.text` を1つずつ見て置換すると**印が見つからない**。段落のテキストを
組み立ててから置換し、先頭の run に書き戻して残りの run を空にする。書式は
先頭 run のものになる。pptx も同じ構造を持つため同じ扱いにする。

### 複数行の値（実測 2026-09-13）

`run.text = "・A\n・B\n・C"` は `<w:br/>` 2個に変換される。docx・pptx とも
改行をそのまま入れられる。xlsx のセルに複数行を入れる場合は `wrap_text` を
立てる（立てないと改行が表示されない）。

## 6. 埋める処理（`filling.py`）

案A（検索してから1回のLLM呼び出しで全部の印を決める）を採る。

1. 利用者が選んだ検索対象を引く（既存の `ingest/retrieval.search()` をそのまま
   使う）
2. 添付ファイルがあれば既存の `ingest/parsers/` で本文を取り出す。**DBには
   入れない**
3. 検索結果＋添付本文＋**印の名前の一覧**を1つのプロンプトにして `ask_json` を
   1回呼ぶ
4. 返ってきた JSON を検証する

```python
def fill_values(placeholders, question, sources, attachments, ask) -> dict[str, str]
```

`sources` は `(資料の種類の名前, ヒットの並び)` の並びである。
`[("社内資料", hits), ("技術ドキュメント", docs_hits)]` のように渡す。

**`filling.py` はどのコーパスが存在するかを知らない。** 見出しの文字列とヒットを
受け取るだけにするのは、検索対象が増えてもこのモジュールを直さずに済ませる
ためである。プロンプトでは種類ごとに節を分ける。混ぜて並べると、どれが社内の
決定事項でどれが外部ライブラリの説明なのかをモデルが区別できない。

### 技術ドキュメントを引くときの追加処理

技術ドキュメントは英語で書かれており、日本語の指示文をそのまま投げても当たら
ない（PR #41 の実測）。この経路だけ次の2つが要る。

- `ingest/query_translation.translate_query()` で指示文を英語に訳す。LLM呼び出しが
  1回増える
- `search()` に `rerank_floor=DOCS_RERANK_FLOOR` を渡す。距離のしきい値は
  このコーパスでは関門にならない（PR #41）

社内資料側には**どちらも渡さない**。日本語のまま検索し、床も設けない。

### 印ごとに検索しない理由

印ごとに検索してLLMを呼ぶ案も検討した。印ごとの根拠を示せる利点はあるが、

- 議事録の雛形で印が8個あれば **LLM呼び出しが8回**になる。1回30〜60秒として
  数分かかる
- 印どうしの整合が保証されない。「会議名は第5回なのに決定事項は第4回」という
  食い違いが構造的に起こりうる

案Aは1回のプロンプトで全部を決めるため、この食い違いが起きない。印ごとの出典
表示は、実際に欲しくなってから足す。

### JSON の検証

`ingest/query_translation.py` と `ingest/conditions.py` と同じ防御を置く。

- 雛形に無いキーは捨てる
- 値が文字列でないものは捨てる
- JSON として壊れていれば全欄を「埋まらなかった」として扱い、**例外は投げない**

### 埋まらなかった印は、印のまま残す

値が得られなかった欄は `{{決定事項}}` の文字列をそのまま残す。空にすると、
利用者は「もともと空欄の書式なのか、埋め損ねたのか」を見分けられない。
`scripts/code_references.py` が解決できなかった `:::code` を元の行のまま残して
件数を数えているのと同じ判断である。画面にも埋まらなかった欄を一覧で出す。

## 7. Mermaid 図の埋め込み

### 記法は増やさない

`{{シーケンス図}}` のような印はそのままで、**LLM が返した値が ```` ```mermaid ````
で始まっていたら図として扱う**。利用者が覚える記法は増えない。

| 形式 | 扱い |
|---|---|
| `.md` | コードブロックのまま入れる。GitHub・VS Code・画面のプレビューで図として表示される |
| `.docx` | PNG に変換し、その段落を画像に差し替える（`run.add_picture()`） |
| `.pptx` | PNG に変換し、その図形の位置に画像を置く（`shapes.add_picture()`） |
| `.xlsx` | PNG に変換し、そのセルに画像を貼る（`ws.add_image()`） |

実測 2026-09-13 で、3形式とも既存の依存（`python-docx` / `python-pptx` /
`openpyxl` + `pillow`）で埋め込めることを確認した。

モデルにそう返させるために、`fill_values` のプロンプトへ1文だけ足す——**図が
要る印には ```` ```mermaid ```` のコードブロックで返してよい**。印の名前を見て
図かどうかを当てる仕組み（`図` で終わる名前を探す等）は作らない。名前の付け方は
雛形を書く人の自由であり、規則を決めると雛形の書き方に制約が生まれる。

### 描画は `mermaid-cli` で行う

実測 2026-09-13: `mmdc -i diagram.mmd -o diagram.png` が **3.5秒で21KBのPNG**を
生成し、日本語のラベル（利用者・画面・議事録_2026-09-13.docx）も化けずに描けた。

**外部サービスは使わない。** `mermaid.ink` や `kroki.io` に投げれば依存は増えない
が、社内設計書の図をそのまま外部へ送ることになり、`AGENTS.md` の「社内固有の
情報を外部サービスに送らない」に反する。`mermaid-cli` はローカルの Chromium で
描画するため、図の内容はマシンの外へ出ない。

### 境目（`docgen/mermaid.py`）

```python
class MermaidError(Exception): ...

def is_diagram(value: str) -> bool   # 値が ```mermaid で始まるか
def diagram_source(value: str) -> str  # フェンスを剥がした本文
def render(source: str) -> bytes     # PNG のバイト列。失敗は MermaidError
```

`render()` は `mmdc` に一時ディレクトリ経由で渡す。`mmdc` は標準入力を受け取らず、
入出力ともファイルで指定する作りだからである。一時ディレクトリは
`tempfile.TemporaryDirectory` で作り、成功しても失敗しても消す。

`mmdc` の場所は `shutil.which("mmdc")` で探す。見つからなければ **その場で
`MermaidError`** を出す。Windows では実体が `mmdc.cmd` のため、`shutil.which`
（`PATHEXT` を見る）を使わずに `subprocess` へ `"mmdc"` を直接渡すと
`FileNotFoundError` になる。

`subprocess.run` には **`timeout=30`** を付ける。Chromium の起動が刺さったまま
返らないと、画面が生成中のまま固まる。実測は3.5秒なので、30秒は十分な余裕が
ある。時間切れも `MermaidError` に包む。

### 増える依存

**Node.js と `@mermaid-js/mermaid-cli`**（Puppeteer + Chromium で約200MB）。
これは Python の依存ではないため `requirements.txt` では管理できない。README に
導入手順を書く。実測した環境には Node.js v24.18.0 が既に入っていた。

### 描けなかったときは黙って落とさない

`mmdc` が見つからない、描画が失敗する、記法が誤っている——いずれの場合も
**Mermaid のテキストをそのまま入れ、図にできなかったことを画面で伝える**。
黙って図が消えるのが最悪である。利用者は成果物を開くまで気づけない。

## 8. `NUM_CTX` の扱い

`ingest/chat.py` の `NUM_CTX = 8192` は、文字起こしを丸ごと渡すには足りない。
案Aは全部を1回のプロンプトに載せるため、ここが効く。

`ask_json` に `num_ctx` の引数を足す。**既定値は現行の 8192 のままとし、既存の
呼び出しは一切変わらない。** Cowork の経路だけ **32768** を渡す。
`coding_agent/connection.py` が 32768／65536 でやっているのと同じ手であり、
その小さいほうに合わせる。

それでも収まらない長さのときは、**黙って切らずに画面で伝えて止める**。切り
詰めると、議事録の後半が抜けたことに利用者が気づけない。

打ち切りの判定はプロンプト全体の**文字数**で行う。

```python
MAX_PROMPT_CHARS = 28000
```

日本語は1文字が1トークン以上になることがあるため、`1文字 = 1トークン` とみなす
安全側の見積もりを採る。32,768 から回答用に約4,000を残した値である。トークナイザ
を持ち込んで正確に数えることはしない。判定に使うだけの目的に対して依存が重く、
生成モデルを替えるたびに数え方が変わる。この値は上限の目安であって、超えたら
止めるという一点にしか使わない。

## 9. 画面

`st.segmented_control` で「チャット / Cowork」を切り替える。

```
  雛形： [ 議事録.docx ▾ ]     [ 雛形を登録・削除 ]
  参照： [x] 社内資料  [ ] 技術ドキュメント
  添付： [ + ファイルを選ぶ ]  （この回だけ使い、DBには入れません）
  ┌────────────────────────────────┐
  │ 第5回会議の議事録を作って        │
  └────────────────────────────────┘
   ［ チャット │ Cowork ］
```

**Streamlit の制約**: `st.chat_input` の中にウィジェットは置けない。トグルは
入力欄のすぐ上に置く。見た目は近づくが、入力欄の内側には入らない。

生成後に出すものは4つ。

1. **ダウンロードボタン**（`st.download_button`）。ファイル名は
   `<雛形名から拡張子を除いたもの>_<生成日 YYYY-MM-DD><元の拡張子>` とする。
   雛形 `議事録.docx` を 2026-09-13 に使えば `議事録_2026-09-13.docx` になる
2. **埋まらなかった欄の一覧**
3. **図にできなかった Mermaid の一覧**（1つも無ければ出さない）
4. **参考にした情報**（既存の `render_evidence` をそのまま使う）

雛形の登録・削除は、既存のアップロードと同じ `st.dialog` の形にする。画面の
作り方を2通りにしない。

**検索対象はその回ごとにチェックで選ぶ。既定は社内資料だけを入にする。**

議事録や報告書は社内資料だけで足りる。一方で「Streamlit の設計レビュー報告書」の
ような雛形なら技術ドキュメントが要る。どちらを引くかは雛形と依頼の内容で決まる
ので、利用者に選ばせる。

既定を社内資料だけにするのは、技術ドキュメントを引くと英訳のLLM呼び出しが1回と
検索が1本増え、生成が30〜60秒遅くなるためである。要らない回に払う理由がない。

両方とも外した状態も許す。添付ファイルだけを根拠に埋める使い方（「この文字起こし
から議事録を」）がそれにあたる。

## 10. エラー処理

| 起きること | どうするか |
|---|---|
| 雛形が1つも登録されていない | 生成ボタンを出さず、登録を促す |
| 雛形に `{{...}}` が1つも無い | 生成せずに伝える（埋める対象が無い） |
| LLM が落ちた（`ChatError`） | 既存のチャットと同じ見せ方で伝える。ファイルは作らない |
| JSON が壊れて返った | 止めない。全欄が「埋まらなかった」になり、雛形がそのまま出る |
| 添付が長すぎて `num_ctx` に収まらない | **切り詰めず、止めて伝える** |
| 検索が0件 | 止めない。添付だけで埋める。0件だったことは画面に出す |
| 検索対象を1つも選ばず、添付も無い | 生成せずに伝える（根拠が1つも無い） |
| 技術ドキュメントのDBが空 | その検索だけを飛ばし、画面に出す。生成は止めない |
| 埋め込み API が落ちた（`EmbeddingError`） | 既存のチャットと同じ見せ方で伝える |
| `mmdc` が入っていない | その図だけ Mermaid のテキストで入れ、画面で伝える。生成は止めない |
| Mermaid の記法が誤っていて描けない | 同上。どの印が図にならなかったかを名前で出す |

## 11. テスト

実機の Ollama にもネットワークにも触れずに書ける。

**`docgen/*_template.py`** — 実ファイルを `tmp_path` に作って読み書きする。

- run に割れた印が見つかること（`['会議名：{{会議', '名}}']`）
- 表のセル、ヘッダー・フッターの印
- 複数行の値が改行として入ること
- 埋まらなかった印が `{{名前}}` のまま残ること
- 印が1つも無い雛形で空の一覧が返ること

**`docgen/templates.py`** — 登録・一覧・削除、同名の上書き。

**`docgen/filling.py`** — `ask` を差し替える。

- 雛形に無いキーを捨てること
- 文字列でない値を捨てること
- 壊れた JSON で例外を投げないこと

**`docgen/mermaid.py`** — `mmdc` は呼ばない。`is_diagram` / `diagram_source` は
文字列だけの処理なのでそのまま測れる。`render` は `subprocess.run` を差し替えて、
`mmdc` が無いとき・戻り値が非0のとき・時間切れのときに `MermaidError` になること
だけを見る。実際に描けるかは実測（7節）で確かめた事実であり、テストで毎回
Chromium を起動すると遅く、CI では落ちる。

**図の差し込み** — `MermaidError` のときに **Mermaid のテキストがそのまま入り、
図にできなかった旨が呼び出し元へ返る**こと。成功時は、差し込んだ結果に画像が
1つ増えること（`doc.inline_shapes` / `ws._images` / 図形の `shape_type`）を、
PNG のバイト列を差し替えて測る。

**`rag_chat_app.py`** — `AppTest` で、トグルの切替、雛形0件の案内、生成後に
ダウンロードボタンが出ること、図にできなかったときにその旨が出ること。

## 12. 実装しないこと（YAGNI）

- 印ごとの出典表示（6節で見送った）
- 表の行を必要なだけ増やす機能
- PDF の生成（2節で見送った）
- 雛形の共有・権限管理・版管理
- 生成物のDBへの取り込み

## 13. 外部への通信

新しい経路は増えない。`AGENTS.md` が挙げている4本目（`OLLAMA_HOST`）を、
今までと同じ形で使うだけである。Mermaid の描画もローカルの Chromium で閉じて
おり、図の内容は外へ出ない（7節）。

- 検索: `ingest/embedder.py` の `/api/embed`（既存）
- 値の決定: `ingest/chat.py` の `/api/chat`（既存）

ただし**添付ファイルの本文がこの経路に乗る**。これは取り込み済みの資料が
乗るのと同じことだが、画面には「この回だけ使い、DBには入れません」と書く。
DBに残らないことと、外へ出ないことは別である。`AGENTS.md` の該当箇所に
1文を足す。
