# 最新ドキュメント取り込み 設計書

**日付:** 2026-09-12
**目的:** 公式ドキュメントを取り込み、モデルの古い知識ではなく取り込んだ最新の記法で
コード例・Markdown例・Mermaid を答えさせる。

## 1. 背景

`gpt-oss:20b` の知識は学習時点で止まっている。ライブラリの記法は変わるため、
「Streamlit でダイアログを出す書き方」を尋ねると、現在は存在しない API を
自信を持って答える余地がある。モデルの更新を待つのではなく、公式ドキュメントを
外から取り込んで文脈に入れる。

依頼者から参考として `test-docs/new_grammar.md` `new_grammar2.md`
`new_grammar3.md` の3つを受け取った。本設計はその方針（llms.txt の活用、
コード構造を意識した分割、メタデータ付与、ハッシュによる差分検知）に沿う。

ただし参考文書の記述には実測で誤りが1つ見つかっている。7節に記す。

## 2. 決定事項

依頼者との確認で以下が確定した。

| 論点 | 決定 | 却下した案 |
|---|---|---|
| 取得範囲 | `llms.txt` 系のみ | GitHub API、Web クローリング |
| 格納先 | 社内資料とは別の SQLite ファイル | 同一DBにメタデータで種別を持たせる |
| 振り分け | 画面のラジオで利用者が切り替える | 質問からの自動判定、両方検索してRRFで統合 |
| 更新の起動 | 手動（CLI＋サイドバーのボタン） | スケジューラによる定期実行 |
| 初期対象 | このリポジトリが実際に使うライブラリ | 任意指定 |

振り分けを画面にしたのは、誤判定が原理的に起きないことと、どちらを検索したかが
画面から読み取れることによる。自動判定は失敗が利用者から見えない。

DB を分けたのは、「社内資料に無ければ答えない」という既存の歯止め
（`ingest/prompting.py` の `build_prompt`）を壊さずに済ませるためである。
同じDBに入れると、社内規程の質問に Streamlit のドキュメントが混ざる。

## 3. 全体構成

```
[docs_sources.toml]  追跡するライブラリとURLの一覧
        │
        ▼  scripts/fetch_docs.py（新規・人が起動したときだけ走る）
   HTTP GET → SHA-256 を前回と比較 → 変わったものだけ書き出す
        │
        ▼  docs_source/streamlit.md   ただのMarkdownファイル
        │
        ▼  scripts/ingest_source.py --source-dir docs_source --db docs_store.sqlite3
   既存の parse_md → chunk_units → embedder → vector_store
        │
        ▼  docs_store.sqlite3   社内資料の vector_store.sqlite3 とは別ファイル
        │
   [サイドバーのラジオ] → 社内資料 か 技術ドキュメントの一方を検索
```

取得と取り込みを2段に分ける。取得は外部通信を伴い失敗しうるが、取り込みは
ローカルで閉じる。分けておけば、取得が落ちても手元のファイルから取り込み直せる。
取得したファイルはリポジトリに残るため、何を根拠に答えたかを後から確認できる。

## 4. 実測に基づく設計判断

本節の数値はすべて 2026-09-12 に実測した。推測は含まない。

### 4.1 取得するのは `llms.txt` ではなく `llms-full.txt`

`llms.txt` の中身を実際に取得して確認したところ、**リンクの目次**であった。
`https://docs.streamlit.io/llms.txt` は 66,927 バイトあるが、コードフェンスは
**0個**で、本文は各ページへのリンクと1行の説明だけである。これを取り込んでも
DB に入るのは目次であり、記法の質問には答えられない。

実体は `llms-full.txt` にある。

| URL | サイズ | コードフェンス | `## ` 見出し |
|---|---|---|---|
| `docs.streamlit.io/llms.txt` | 66 KB | 0 | — |
| `docs.streamlit.io/llms-full.txt` | 1,927,203 B | 1,877 | 659 |
| `python.langchain.com/llms-full.txt` | 1,003,477 B | — | — |
| `docs.ollama.com/llms-full.txt` | 234,018 B | — | — |

**したがって `fetch_docs.py` は `llms-full.txt` を優先して取りに行く。**
404 だった場合にかぎり `llms.txt` へ落とすが、そのときは「目次しか取れていない」
旨を警告として出す。黙って目次を取り込むと、検索は当たるのに答えが書けないという
診断しにくい状態になる。

### 4.2 対象ライブラリの `llms.txt` 実在状況

このリポジトリが `requirements.txt` で使っているものを調べた。

| ライブラリ | `llms.txt` | 初期対象 |
|---|---|---|
| streamlit | 200 | ○ |
| langchain (langchain-text-splitters の本体) | 200 | ○ |
| ollama | 200 | ○ |
| huggingface_hub | 200 | ○ |
| pymupdf | 200 | ○ |
| fastapi | **404** | × |
| pytest | **404** | × |
| numpy | **404** | × |

`llms.txt` を公開していないライブラリは、本設計の範囲では対象にできない。
GitHub API と Web クローリングを却下した以上、これは受け入れる制約である。

### 4.3 現在のチャンカーはコードブロックを割る

現在の `ingest/chunker.py` の区切りは `["\n\n", "\n", "。", "、", " ", ""]` で、
日本語の散文向けに決められている。Streamlit の `llms-full.txt` を既存の
`parse_md` → `chunk_units` にそのまま通すと、

- ユニット 483、チャンク 3,427
- **コードブロックが途中で割れたチャンク 284件（8.3%）**

割れたチャンクは、開きフェンスだけ、あるいは閉じフェンスだけを含む。検索で
当たっても、モデルに渡るのは不完全なコードになる。参考文書 `new_grammar.md` が
「関数定義の途中やサンプルコードの途中で分断され、文法エラーの原因になります」と
警告しているのはこの現象である。

### 4.4 区切りにフェンスを足す案は**悪化する**（採用しない）

参考文書 `new_grammar2.md` は `separators=["\n```", ...]` を薦めている。実際に
測ると逆効果だった。

| 分割方法 | チャンク数 | 割れ | 割合 |
|---|---|---|---|
| 現状（日本語散文向け） | 3,427 | 284 | 8.3% |
| フェンスを区切りの先頭に追加 | 3,601 | 613 | **17.0%** |
| 同上 + chunk_size 1600 | 1,880 | 366 | 19.5% |
| 同上 + chunk_size 2400 | 1,390 | 265 | 19.1% |

`RecursiveCharacterTextSplitter` は指定した区切りの手前で切る。`"\n```"` を
区切りにすると、**開きフェンスの手前だけでなく閉じフェンスの手前でも切る**ため、
コードブロックが「本体」と「閉じフェンス」に分断される。割れが増えるのはこのためである。

この結果を残すのは、「区切りを足せば直るはず」という一見もっともな案を
誰かが再び試すのを防ぐためである。

### 4.5 採用する分割：フェンスを丸ごと1片として扱う

章の本文を「コードブロック」と「地の文」に切り分け、**コードブロックは分割器に
通さずそのまま1チャンクにする**。地の文だけを既存の分割器に通す。

| 分割方法 | チャンク数 | 割れ | 割合 | 800字超 |
|---|---|---|---|---|
| 現状 | 3,427 | 284 | 8.3% | 0 |
| **フェンス丸ごと保持** | 4,240 | **4** | **0.1%** | 100 |

残る4件は元の文書のフェンスが対になっていない箇所であり、分割の問題ではない。

この 4,240 という数は 4.6 節の上限を入れる前の測定である。上限を入れると、
2,400字を超える33個のブロックが分割されるぶんだけ増える。

チャンク数が24%増えるのは、地の文とコードが同じチャンクを共有しなくなるためで、
意図した結果である。

### 4.6 巨大なコードブロックには上限を設ける

フェンスを丸ごと保持すると、`chunk_size` を超えるチャンクが100件生じる
（中央値 1,504字、**最大 24,864字**）。24,864字は bge-m3 の入力窓を超えるため、
埋め込みの時点で後ろが切り捨てられる。検索の粒度としても粗すぎる。

コードブロックの大きさの分布は次のとおりで、大半は小さい。

- ブロック数 938、中央値 **122字**、平均 465字、最大 24,864字
- 800字超 100個（10.7%）、1,600字超 47個（5.0%）、**2,400字超 33個（3.5%）**、
  3,200字超 25個（2.7%）

**上限を 2,400字（`CHUNK_SIZE` の3倍）とする。** これを超えるコードブロックは
地の文と同じ分割器に通す。割れるが、対象は 938個中33個（3.5%）であり、
そもそも入力窓を超えて後ろが失われるよりは良い。

### 4.7 規模

Streamlit 1ライブラリだけで 4,240チャンク。社内資料のコーパス全体が現在
826チャンクなので、**5倍を超える**。DB を分ける判断はこの規模からも正しい。
埋め込みには相応の時間がかかるため、初回は Colab の GPU で行うことを想定する
（全件取り込みを Colab で行う運用は既存と同じ）。

## 5. 作るもの

### 5.1 `docs_sources.toml`（新規）

```toml
[[source]]
name = "streamlit"
url = "https://docs.streamlit.io/llms-full.txt"
version = "1.61.1"

[[source]]
name = "langchain-text-splitters"
url = "https://python.langchain.com/llms-full.txt"
version = "1.1.2"
```

`version` は `requirements.txt` で固定している版を書く。取得先は常に最新版の
ドキュメントなので厳密には一致しないが、「どの版を使っている状態で取り込んだか」を
残すために持つ。書き出すファイルの front matter に入れ、既存の
`_split_frontmatter` がメタデータとして拾う（**この配線は既にある**）。

`name` は取り込み元を識別する名前であって、URL の持ち主とは限らない。上の例で
使っているのは `langchain-text-splitters` だが、ドキュメントは LangChain 本体の
サイトがまとめて公開している。

`tomllib` は Python 3.11 以降の標準ライブラリであり、依存は増えない。

### 5.2 `scripts/fetch_docs.py`（新規）

1. `docs_sources.toml` を読む。
2. 各 `url` を GET する（`requests`、タイムアウトあり）。
3. 本文の SHA-256 を計算し、既存の `docs_source/<name>.md` のハッシュと比べる。
   同じなら書かない。
4. 変わっていれば front matter（`name` `url` `version` `fetched_at`）を付けて
   `docs_source/<name>.md` に書く。
5. 1件が失敗しても残りを続ける。最後に取得・更新なし・失敗の件数を出す。

**設定に書かれた URL しか取りに行かない。** ページ内のリンクは辿らない。
クローラーにはしない。

`llms-full.txt` が 404 で `llms.txt` に落ちたときは、その旨を警告に出す（4.1節）。

### 5.3 コードブロックを保持する分割（`ingest/chunker.py`）

既存の `chunk_units` に `keep_code_blocks: bool = False` を足す。既定は False で、
**社内資料の取り込み結果は1バイトも変わらない**。技術ドキュメントの取り込みだけが
True を渡す。

```python
_CODE_BLOCK = re.compile(r"^```.*?^```", re.DOTALL | re.MULTILINE)
MAX_CODE_BLOCK_CHARS = CHUNK_SIZE * 3  # 2400字。4.6節の実測による
```

章の本文をブロックと地の文に切り分け、ブロックは `MAX_CODE_BLOCK_CHARS` 以下なら
そのまま1片にし、超えていれば既存の分割器に通す。地の文は常に既存の分割器に通す。

### 5.4 `scripts/ingest_source.py` に `--db` と `--keep-code-blocks`

`main()` は現在 DB パスを直書きしている（`store.open_store(str(DB_PATH))`）。

`--db` を足す際は注意が要る。`ingest/store.py` のコメントにあるとおり、
**`open_store` はパスを間違えても例外を出さず空のDBを新規作成する**。タイポは
「検索結果が全部空」という静かな失敗になり、テストも緑のまま通る。
そのため、取り込み後にDBの総チャンク数を必ず表示し、0件なら警告を出す。

### 5.5 画面の切り替えと専用プロンプト（`rag_chat_app.py` / `ingest/prompting.py`）

サイドバーに `社内資料 / 技術ドキュメント` のラジオを置く。選択に応じて開く
コレクションを変える。`get_collection` は既にパスを引数に取るキャッシュなので、
2つのDBが並行してキャッシュされる。

技術ドキュメント側では `build_prompt` を使えない。「社内文書からは回答できない旨を
伝えてください」という歯止めが文面ごと不適切になるためである。`build_docs_prompt`
を別に置く。指示の骨子は次の3つ。

- 取り込んだドキュメントに書かれている記法だけを使うこと。
- 知っている古い書き方を混ぜないこと。ドキュメントに無い API を補わないこと。
- ドキュメントに書かれていなければ、書かれていないと答えること。

2つめが「最新の文法で答える」の実体である。1つめだけでは、モデルは文脈を読んだ
うえで学習時の記法に戻る余地が残る。

本文に出典を書かせない扱いは社内資料側と揃える（2026-09-12 の変更）。

技術ドキュメント側は素の検索経路だけを使う。型番の絞り込み（`ingest/catalog.py`）は
社内の製品仕様書に固有の仕組みなので通さない。

### 5.6 触らないもの

埋め込みモデル、リランカー、ハイブリッド検索、RRF、しきい値、MCP サーバー、
`ingest/parsers/` のいずれも変更しない。`llms-full.txt` は Markdown であり、
既存の `parse_md` がそのまま読む（フェンスを認識して見出し分割を抑止する処理も
既にある）。

## 6. 外部通信の扱い

`AGENTS.md` は現在、外部へ出る経路を2つ挙げている（context7、リランカーの
huggingface.co への HEAD）。**3本目として `fetch_docs.py` を明記する。**

記す内容は次のとおり。

- 送るのは設定ファイルに書かれた URL への GET だけである。
- 社内資料の内容も検索語も含まない。こちらから送る情報は無い。
- 人が明示的に起動したときだけ走る。常駐プロセスもスケジューラも持たない。
- オフライン環境では実行できない。取得済みの `docs_source/` があれば取り込みは
  ローカルで完結する。

## 7. 参考文書の誤りについて

`test-docs/new_grammar2.md` は実行例の URL として
`https://fastapi.tiangolo.com/llms.txt` を挙げているが、これは **404 を返す**
（2026-09-12 実測）。FastAPI は `llms.txt` を公開していない。

また `new_grammar2.md` が薦める `separators=["\n```", ...]` は、実測では割れを
8.3% から 17.0% に**悪化させる**（4.4節）。

参考文書は方針としては妥当だが、個別の URL と分割パラメータはそのまま使えない。

## 8. テスト

| 対象 | 検証すること |
|---|---|
| `fetch_docs` | 同じ内容なら書かない／変わったら書く／1件が404でも残りを続ける／`llms-full.txt` が無ければ `llms.txt` に落ちて警告を出す |
| 分割 | コードブロックを含む章でフェンスが割れない／2,400字超のブロックは分割器に通る／`keep_code_blocks=False` のとき既存の結果と完全に一致する |
| `--db` | 指定したパスのDBが開く／0件のとき警告が出る |
| `build_docs_prompt` | 3つの指示がある／「社内文書」という語を含まない／本文に出典を書かせない |
| 画面の切り替え | ラジオの選択が検索対象のDBを変える（`AppTest`） |

HTTP はすべてスタブする。テストが実際にネットワークへ出てはならない。

**自動テストで測れないこと:** 「最新の文法で答えられるようになったか」。これは
実機で数問投げて記録するしかない。取り込み前後で同じ質問を投げ、結果を README に
残す。

## 9. 受け入れ条件

1. `python -m scripts.fetch_docs` が `docs_source/` に Markdown を書き出す。
   2回目の実行は「更新なし」と報告し、ファイルを書き換えない。
2. `python -m scripts.ingest_source --source-dir docs_source --db docs_store.sqlite3
   --keep-code-blocks` が完走し、総チャンク数を表示する。
3. 社内資料の `vector_store.sqlite3` は1バイトも変わらない。
4. 画面のラジオで技術ドキュメントを選ぶと、Streamlit の記法に関する質問に
   取り込んだドキュメントを出典として答える。
5. 社内資料を選んだときの挙動が変更前と変わらない。
6. `AGENTS.md` に3本目の外部通信経路が記載されている。

## 10. 範囲外

- GitHub API からの取得、Web クローリング（2節で却下）。
- 定期実行、スケジューラ、失敗通知（2節で却下）。
- 質問からの自動振り分け（2節で却下）。
- 2つのDBを横断した検索と統合。
- `llms.txt` を公開していないライブラリへの対応。
- MCP サーバー経由での技術ドキュメント検索。社内資料の検索とは用途が別で、
  必要になってから設計する。
