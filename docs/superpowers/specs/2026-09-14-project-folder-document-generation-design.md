# プロジェクトフォルダからの文書生成（雛形なし）設計書

作成日: 2026-09-14

## 1. 何を作るか

Cowork に2つを足す。

1. **プロジェクトフォルダ**を資料源として指定できるようにする。フォルダの中の
   ファイルを読み、依頼に関係するものを生成の根拠に使う。
2. **雛形を必須でなくする。** 雛形を選ばずに、依頼文だけから `.md` / `.docx` /
   `.xlsx` / `.pptx` を出せるようにする。

これまでの Cowork は「登録した雛形の空欄を埋める」ことしかできなかった
（[2026-09-13-document-generation-design.md](2026-09-13-document-generation-design.md)）。
成果物の形が先に決まっている場合はこれでよいが、**プロジェクトの設計書をゼロから
起こす**ような仕事では、先に雛形を作る手間のほうが大きい。また資料源は検索対象の
DBとその場の添付だけで、手元のフォルダを丸ごと根拠にする手段が無かった。

作りたい成果物として利用者が挙げたのは次の4つで、いずれも対象とする。

- 設計書・仕様書（文章中心）
- 一覧表（API一覧・ファイル一覧・課題表など）
- 手順書・README・引き継ぎ資料
- 報告・提案スライド

## 2. 設計の前提（利用者との合意事項）

| 論点 | 決めたこと |
|---|---|
| フォルダの指定方法 | **サーバー側のパスを文字列で入力する。** Streamlit のブラウザーからフォルダは選べない（`st.file_uploader` はファイル単位でディレクトリ選択に対応しない） |
| 運用形態 | **自分のマシンで自分だけが使う。** 読める根は限定しない（13節に、共有する場合にやることを記録する） |
| 想定規模 | このリポジトリ程度（数十〜200ファイル、数百KB〜数MB） |
| フォルダの渡し方 | **ツリーを見せて LLM に選ばせ、選ばれたファイルを丸ごと渡す**（3節） |
| 雛形なしの中間表現 | **Markdown 1本。** そこから4形式へ変換する（3節） |
| 雛形ありの経路 | **今のまま変えない。** プロジェクトフォルダだけが資料源として増える |
| 出力形式の選び方 | 雛形なしのとき、利用者がプルダウンで選ぶ |
| フォルダの中身 | DBには入れない。その回の生成に使うだけ（添付と同じ扱い） |

## 3. 中身の選び方（この設計の中心）

### 丸ごと渡す案は成立しない

プロンプトの上限は 28,000字である（`docgen/filling.py` の `MAX_PROMPT_CHARS`）。
このリポジトリを実測した（2026-09-14）。

| 対象 | ファイル数 | 文字数 | 上限に対して |
|---|---:|---:|---:|
| 取り込み可能な全形式 | 179 | 4,188,651 | 150倍 |
| `.py` `.md` `.ps1` `.toml` `.yml` `.txt` `.ini`（言語仕様の写しを除く） | 215 | 2,122,444 | 76倍 |
| `.py` だけ | 113 | 796,527 | 28倍 |

**`.py` だけでも28倍ある。** 選別は設計の一部ではなく前提である。

### 採った方法: ツリーを見せて選ばせ、選ばれたファイルを丸ごと渡す

1. フォルダを走査し、パスと文字数だけの一覧（ツリー）を作る
2. ツリーと依頼文を LLM に見せ、要るファイルのパスを JSON 配列で返させる
3. 選ばれたファイルの本文を、予算の範囲で読む
4. ツリーと本文をプロンプトへ載せ、本番の生成を行う

LLM 呼び出しは2回になる。

### 退けた案: 依頼文で絞る一時的なベクトル検索

フォルダをチャンク化して埋め込み、依頼文で検索してヒットだけを渡す案。既存の
取り込み・検索・リランカーをそのまま再利用でき、社内資料と同じ `(種類, ヒット)`
の形で `filling.py` に渡せるという利点がある。それでも採らない。

- **コードが 800字で割れる。** `ingest/chunker.py` の分割は日本語の文章向けの
  区切り（空行 → 改行 → 句読点）で行われ、構文を見ない。関数やクラスの途中で
  境界が落ちる。これは 2026-09-14 のコード取り込み対応で既知の制約として README
  に記録したばかりの問題であり、そのままここに出る。設計書・一覧表・手順書の
  いずれも、コードの構造を正しく読めていることが前提である
- **数千チャンクの埋め込みで生成が数分に伸びる。** 現在の Cowork は30〜60秒である

### この方法の利点: 既存の口にそのまま乗る

`docgen/filling.py` の `fill_values` は添付を `(名前, 本文)` の並びで受ける。
プロジェクトフォルダは **「添付の自動版」** として同じ形で渡せるため、
`filling.py` 側の変更は要らない。雛形ありの経路も、資料源が1つ増えるだけで
制御の流れは変わらない。

## 4. 構成

```
rag_chat_app.py            画面。フォルダのパス入力、雛形なしの選択、出力形式の選択
  docgen/project.py        [新規] フォルダの走査・ファイル選択・本文の読み取り
  docgen/freeform.py       [新規] 雛形なしのプロンプトと Markdown の取得
  docgen/markdown_document.py [新規] Markdown → md / docx / xlsx / pptx
  docgen/filling.py        既存。変更しない（プロジェクトの本文は添付として渡す）
  docgen/mermaid.py        既存。Mermaid → PNG。再利用する
  ingest/chat.py           ask_text を足す
```

既存の `docgen/*_template.py`（docx / xlsx / pptx / md）は **「印を埋める」役**
であり、`markdown_document.py` は **「ゼロから組む」役**である。責務が違うので
混ぜない。前者は原本の書式・レイアウト・ロゴを保つことが仕事で、後者に原本は
存在しない。

## 5. フォルダの読み取り（`docgen/project.py`）

### 走査の対象

`ingest.parsers.SUPPORTED_SUFFIXES` に限る。2026-09-14 のコード取り込み対応で
`.go` `.cs` `.sh` `.json` `.bat` `.yaml` `.yml` `.mod` `.sum` `.html` `.htm` が
入ったため、**ソースコードのプロジェクトがそのまま読める**。本文の取り出しは
`ingest.parsers.parse` を通す（PDF や docx が混ざったフォルダでも同じ経路で
扱える）。

### 除外

| 除外するもの | 理由 |
|---|---|
| 隠しディレクトリ（`.` で始まる） | `.git` `.venv` `.pytest_cache` などが一括で落ちる |
| `__pycache__` `node_modules` `myvenv*` `venv` `.venv` | 隠しでない生成物・依存物。中身は書いた人の資料ではない |

除外の一覧は定数として1箇所に置く。フォルダごとに `.gitignore` を読む仕組みは
作らない（YAGNI。12節）。

### 予算

```
PROJECT_BUDGET_CHARS = 16000
```

28,000字の上限のうち、検索結果・添付・依頼文・指示文に残す分を引いた値である。
選ばれたファイルを順に足していき、この値を超えたところで止める。**落とした
ファイルの名前は呼び出し元へ返し、画面が警告する。** 黙って捨てると、利用者は
根拠が足りないまま書かれた文書を、根拠があるものとして読む。

最終的な上限判定は `filling.py` の `PromptTooLongError` が引き続き行う。予算は
そこへ到達する前に大半を防ぐための値であって、保証ではない。

### パスの検証

**`root` の外を指すパスは拒む。** この経路は LLM が返した文字列でファイルを読む。
`docgen/templates.py` の `_checked` と `ingest/parsers/md_parser.py` の `_resolve`
が同じ理由で `..` を拒んでいるので、規則を揃える。

判定は解決後の絶対パスが `root` の下にあることで行う（文字列に `..` が含まれるか
ではなく）。シンボリックリンクで外へ出る場合もここで落ちる。

### 関数

| 関数 | すること |
|---|---|
| `tree(root)` | `(相対パス, 文字数)` の並びを返す。走査と除外はここだけが知る |
| `select(tree, question, ask)` | LLM に選ばせ、相対パスの並びを返す |
| `read(root, paths)` | `(相対パス, 本文)` の並びと、予算で落とした名前を返す |

`ask` を引数で受けるのは `docgen/filling.py` と `ingest/conditions.py` と同じ
理由である。モジュール内で Ollama クライアントに束縛すると、選択の規則を試す
テストに実機の Ollama が要るようになる。

### 選択が壊れて返ったとき

**止めない。** 「選択なし」として扱い、ツリーだけをプロンプトへ載せて警告を出す。
`fill_values` が壊れた JSON で止めず、`ingest/query_translation.py` が翻訳の失敗で
原文に落ちるのと同じ考え方である。ツリーだけでもファイル構成は伝わるので、
利用者は何も受け取れないよりはましな成果物を得る。

LLM そのものが落ちた場合（`chat.ChatError`）は投げ直す。こちらは伝えるべき失敗
である。

## 6. 雛形なしの生成（`docgen/freeform.py`）

### プロンプトに載るもの

雛形ありの経路（`filling.build_prompt`）と同じ材料を載せる。依頼文、検索結果
（社内資料・技術ドキュメント。利用者が選んだものだけ）、添付ファイルの本文、
プロジェクトフォルダのツリーと選ばれたファイルの本文である。違うのは、埋める欄の
一覧の代わりに**出力の形の指示**が入る点だけである。

「資料に書かれていないことは書かない」という既存の指示は引き継ぐ。根拠の無い
文書を作らないという方針は、雛形の有無で変わらない。

### 中間表現を Markdown 1本にする

LLM には常に「Markdown で文書を書け」と頼み、その1つの出力から4形式を組み立てる。

- LLM 呼び出しは1回で済む。印が8個あっても1回で決める既存の方針
  （2026-09-13 設計書6節）と揃う
- Markdown → 各形式の変換は決定的なコードであり、テストが書ける
- 形式ごとにプロンプトを分けると、プロンプトが4本になり、品質のばらつきも
  4箇所で別々に面倒を見ることになる

形式ごとの違いは、依頼文に足す一言だけにとどめる。**xlsx のときだけ**
「Markdown の表で答えること」を足す。一覧表が欲しいのに文章が返ってくると、
変換のしようがないためである。

### 平文を返す口を足す（`ingest/chat.py` の `ask_text`）

既存の `ask_json` は `format: "json"` を固定で送る。数千字の Markdown を JSON
文字列に押し込むと、改行・引用符・バックスラッシュのエスケープで壊れやすい。
`ask_text` は同じ要求から `format: "json"` を外しただけのものとする。`ask_json`
が `temperature: 0` を固定で送るのに対し、`ask_text` は `options` に
`temperature` を入れず、モデル側の既定に任せる。条件抽出は同じ質問で答えが揺れる
と再現性のない誤りになるが、文章生成にその要求はない。

## 7. Markdown から各形式へ（`docgen/markdown_document.py`）

Markdown を一度だけ解析して**共通の中間構造**（見出し・段落・箇条書き・表・
コードブロック・Mermaid）にし、そこから各形式を組む。形式ごとに Markdown を
読み直すと、記法の解釈が4箇所に分かれる。

| 形式 | 組み立て方 |
|---|---|
| md | そのまま UTF-8 の bytes にする |
| docx | 見出しは `Heading n`、段落、箇条書き、表、コードブロックは等幅の段落 |
| pptx | `#` をタイトルスライド、`##` ごとに1スライド、配下の箇条書きを本文へ |
| xlsx | **表1つにつき1シート。** シート名は直前の見出し（無ければ `表1`、`表2`…） |

`###` 以下の見出しは、pptx ではスライドを分けず本文の中の1行として扱う。1枚の
スライドに収まらない量になるが、見出しの深さでスライドを分けると、章立ての書き方
しだいでスライドが数十枚に膨らむ。

xlsx に表が1つも無いときは、見出しと本文の2列（A列に見出し、B列に本文）で1シート
を出し、警告する。空のブックを返さないのは、利用者が受け取るものを空にしない
ためである。警告と合わせて、書かれた内容そのものは必ず渡る。

シート名には Excel の制限がある（31文字以内、`: \ / ? * [ ]` を含められない、
同名不可）。見出しをそのまま使えない場合は切り詰めて連番を付ける。

### Mermaid

既存の `docgen/mermaid.py` を再利用する。`.md` はコードブロックのまま入れる
（GitHub・VS Code・画面のプレビューが図として表示するため。`md_template.py` と
同じ判断）。docx / pptx は PNG にする。xlsx は当面 PNG を入れず、コードブロックを
文字として入れる（表が主目的の形式であり、図の配置に置き場所の判断が要る。12節）。

図にできなかったものは、雛形ありの経路と同じく画面の警告に出す。

## 8. 画面（`rag_chat_app.py`）

### 雛形の選択

プルダウンの先頭に **「（雛形なし）」** を置く。選ぶと隣に**出力形式**
（md / docx / xlsx / pptx）のプルダウンが出る。

現在、雛形が0件のときは警告を出し、そのまま送信されたら
「雛形が登録されていません」で生成を止めている（`rag_chat_app.py` の 824-830行
付近）。雛形なしが正規の選択肢になるため、この分岐は次のように変わる。

- 雛形が0件でも画面は成立する（「（雛形なし）」が既定として選ばれる）
- 「雛形を登録・削除」ボタンは今のまま常に出す

### プロジェクトフォルダ

パスを入力する欄を1つ足す。空欄でよい。雛形あり・なしの両方で使える。

- 存在しない・ディレクトリでないパスは、LLM を呼ぶ前に画面で伝えて止める
- 走査して対象が0件だったときも、LLM を呼ぶ前に伝えて止める

### 生成を止める条件

現在は「社内資料も技術ドキュメントも添付も無ければ、根拠が無いので止める」と
している。**プロジェクトフォルダを数に入れる。** フォルダだけを指定した回は
正当な使い方であり、止めてはならない。

### 生成中の無効化

新しい入力欄（フォルダのパス、出力形式）も、既存の雛形プルダウンと同じく生成中は
無効化する。生成の最中に触ると再実行が走って生成が打ち切られ、入力が入れ替わった
状態のまま `generating` と `pending_question` だけが前回の依頼を抱えて残る。

### 出力ファイル名

雛形ありは今のまま（`{雛形名}_{日付}{拡張子}`）。雛形なしは
`{フォルダ名}_{日付}.{拡張子}` とし、フォルダを指定していない回は
`文書_{日付}.{拡張子}` とする。

## 9. データの流れ

```
依頼文 ─┬─→ [社内資料の検索]      ─→ (種類, ヒット)  ┐
        ├─→ [技術ドキュメントの検索] ─→ (種類, ヒット)  ├─→ プロンプト ─→ LLM
        ├─→ [添付ファイルの解析]     ─→ (名前, 本文)    │
        └─→ [プロジェクトフォルダ]   ─→ (名前, 本文)    ┘
                 tree → select(LLM 1回目) → read

            雛形あり → filling.fill_values → docgen.fill      → bytes
            雛形なし → freeform(LLM 2回目) → Markdown
                                           → markdown_document → bytes
```

## 10. エラー処理

| 起きること | どうするか |
|---|---|
| パスが存在しない／ディレクトリでない | LLM を呼ぶ前に画面で伝えて止める |
| 走査して対象が0件 | 同上 |
| ファイルが開けない（壊れている等） | そのファイルを飛ばし、名前を警告に出す。生成は続ける |
| 選択の JSON が壊れている | 選択なしとして扱い、ツリーだけを載せて警告（5節） |
| 予算を超えた | 超えた分を落とし、落とした名前を警告に出す |
| `chat.ChatError` | 投げ直して画面で伝える |
| `PromptTooLongError` | 既存どおり画面で伝えて止める |
| Markdown に表が無いのに xlsx を選んだ | 見出しと本文の2列で出し、警告 |
| Mermaid を図にできない | 既存どおり警告に出し、テキストのまま入れる |

画面で直接 `st.error` を呼ばず、`st.session_state.cowork_result` に積んで次の
実行で描くという既存の約束は変えない（`generating` を戻すための `st.rerun()` が
同じ実行の描画ごと消してしまうため）。

## 11. テスト

実機の Ollama にもネットワークにも触れない。`ask` は引数で受けるので差し替え
られる。

| 対象 | 確かめること |
|---|---|
| `project.tree` | 除外が効く（隠しディレクトリ・`__pycache__` 等）／対象拡張子だけ／相対パスで返る |
| `project.read` | 予算を超えたら落とし、落とした名前を返す |
| `project.read` | **`root` の外を指すパスを拒む**（`..`、絶対パス、シンボリックリンク） |
| `project.select` | 壊れた JSON で例外を出さず、選択なしを返す／`ChatError` は投げ直す |
| `freeform` | 依頼・検索結果・ツリー・本文がプロンプトに載る／xlsx のときだけ表の指示が入る |
| `markdown_document` | 4形式を python-docx / openpyxl / python-pptx で読み返して検証 |
| `markdown_document` | 表が無い Markdown で xlsx を作ると2列になり、警告が返る |
| `markdown_document` | シート名が31文字を超える／重なる／禁止文字を含むときに壊れない |
| `chat.ask_text` | `format` を送らない（`ask_json` との差がここだけであること） |
| 画面 | 雛形なしで md が出る／フォルダも添付も検索も無いと止まる／存在しないパスで止まる |

画面は既存の `tests/test_rag_chat_app_cowork.py`（AppTest、15件）に足す。

## 12. 実装しないこと（YAGNI）

- **`.gitignore` の解釈。** 除外は定数の一覧で足りる。想定規模では効果より
  複雑さが勝る
- **フォルダの内容のキャッシュ。** 2回目が速くなるが、フォルダは生成のたびに
  変わりうる。古い内容で書かれた文書のほうが害が大きい
- **フォルダの再帰的な深さ制限。** 除外一覧で生成物が落ちるため、想定規模では
  問題にならない
- **xlsx への図の埋め込み**（7節）
- **雛形なしの出力を DB に入れる。** 成果物であって資料ではない
- **複数フォルダの同時指定。** 1つで足りる

## 13. 外部への通信

新しい宛先は増えない。`OLLAMA_HOST` へ、依頼文・検索結果・添付の本文が乗る既存の
経路に、**プロジェクトフォルダのファイル本文とファイルパスの一覧が加わる**
（AGENTS.md「外部ドキュメントの参照」4本目）。

`OLLAMA_HOST` が既定値（`http://127.0.0.1:11434`）ならマシンの外へは出ない。
`.env` で ngrok 経由のリモート URL へ向けている場合は、**指定したフォルダの
ソースコードがその経路で外へ出る**。手元のコードを扱うときは `OLLAMA_HOST` が
ローカルを指していることを確かめること。

## 14. 共有する場合にやること（現時点では実装しない）

この設計は「自分のマシンで自分だけが使う」前提で、パスの入力を素通しする。
社内サーバーに置いて複数人が使う形にするなら、次が要る。

- **読める根を設定で限定する。** 現状のパス入力は、サーバー上の任意のファイルを
  読んで LLM へ送る手段になる
- 根の外を指すパスを画面の段階で拒む（5節の検証は `root` の外を防ぐもので、
  `root` 自体を利用者が自由に決められることは防がない）

README の「アップロードした資料は全利用者の検索対象になります」という記述が
示すとおり、このシステムは共有される可能性を持っている。前提が変わった時点で
ここへ戻ること。
