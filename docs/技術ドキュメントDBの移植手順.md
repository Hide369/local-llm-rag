# 技術ドキュメントDBの移植手順

別のマシンで `docs_store.sqlite3`（画面の「検索対象 → 技術ドキュメント」が引くDB）を
用意するための手順である。社内資料側の `vector_store.sqlite3` はこの手順では扱わない
（そちらは [Windowsサーバー配置手順](server-deployment-windows.md)）。

**所要**: 作り直すなら1時間前後、DBをコピーするなら数分。

## 0. どちらの方法を採るか

| | A. 移植先で取り込む | B. DBをコピーする |
|---|---|---|
| 所要 | 1時間前後 | 数分（273MBの転送） |
| 要るもの | Ollama + `bge-m3` | ファイルを運ぶ手段 |
| 向くとき | DBを運べない／資料を最新にしたい | 手元と同じ状態をすぐ再現したい |
| 注意 | 埋め込みの宛先だけは要る（`OLLAMA_HOST`） | `docs_store.sqlite3` は `.gitignore` 済みで git には乗らない |

**迷ったら B。** 取り込みは冪等なので、あとから A を走らせて更新できる。

**A に外部通信は要らない。** `docs_source/` を 2026-09-13 に追跡対象にしたので、
`git clone` すれば資料の本文も付いてくる。**`fetch_docs` を走らせるのは資料を
最新にしたいときだけ**で、そのときだけ外部へのHTTPSが要る。

### 何が付いてきて、何が付いてこないか

`git clone` で**付いてくる**もの:

| ファイル | 中身 |
|---|---|
| `docs_sources.toml` | 取り込む資料の一覧（13件）。これが唯一の設定である |
| `docs/pg_data/*.md` | `kind = "local"` の原本。公開Markdownが無い資料（Go・C#・Python の言語仕様）を人がmd化したもので、取り直す先が無いため追跡している |
| `docs_source/` | 取り込む資料の本文そのもの（27MB、767ファイル）。**2026-09-13 に追跡対象にした。** これがあれば `fetch_docs` を飛ばせる |

`docs_source/` は `fetch_docs` の**出力**である。原本を置く場所ではない。手で
置いたファイルは `docs_sources.toml` に記録が残らず、どの版を入れたのか追えなく
なるうえ、`fetch_docs` で作り直せば消える。足したい資料は `docs/pg_data/` に置いて
`docs_sources.toml` へ登録すること（[コーディング対応ライブラリ.md](コーディング対応ライブラリ.md) 5節）。

改行コードは `.gitattributes` で固定している。外すと、チェックアウトで LF が CRLF に
変わった時点で767ファイル全部が「変更あり」と判定される（`file_hash()` は生バイトを
数える）。

**付いてこない**もの（`.gitignore` 済み）:

| ファイル | 大きさ | 作り方 |
|---|---|---|
| `docs_store.sqlite3` | 273MB | `python -m scripts.ingest_source` |
| `.env` | — | 手で書く（下記） |

## 1. 前提の確認

- Python 3.13 の仮想環境（`myvenv313`）
- Ollama が動いていること
- **埋め込みモデル `bge-m3`**（1024次元）。取り込みに必須

```powershell
.\myvenv313\Scripts\python.exe -m pip install -r requirements.txt
ollama pull bge-m3
```

回答生成の `gpt-oss:20b` は**取り込みには要らない**。画面を使うときに要る。

### 接続先（`.env`）

既定は `http://127.0.0.1:11434` で、手元のOllamaを使うならこの節は飛ばしてよい。
別のマシン（ColabのL4など）のOllamaを使う場合だけ、リポジトリ直下に `.env` を置く。

```
OLLAMA_HOST=https://example.ngrok-free.dev
OLLAMA_API_KEY=<認証つきプロキシを挟んでいる場合だけ>
```

`localhost` とは書かないこと。Windowsでは先にIPv6の `::1` に解決され、1リクエスト
あたり約2.1秒を浪費する（`127.0.0.1` なら約80ms）。

疎通を先に確かめる。**取り込みを始めてから落ちるのを防ぐため、ここで必ず確認する。**

```powershell
.\myvenv313\Scripts\python.exe -c "from dotenv import load_dotenv; load_dotenv(); from ingest import embedder; print(embedder.OLLAMA_HOST); embedder.check_ollama(); print('OK')"
```

`埋め込みモデル bge-m3 がありません` と出たら `ollama pull bge-m3` が済んでいない。

## 2. 方法A: 移植先で取り込む

### 2-1. 資料を `docs_source/` へ集める（**通常は不要**）

`git clone` した時点で `docs_source/`（767ファイル）は揃っている。**手元と同じ版を
入れたいなら、この節は飛ばして 2-2 へ進むこと。**

走らせるのは資料を最新にしたいときだけである。

```powershell
.\myvenv313\Scripts\python.exe -m scripts.fetch_docs
```

**外部通信はここだけである。** `docs_sources.toml` に書かれた宛先しか取りに行かず、
ページ内のリンクは辿らない。`kind = "local"` の3件（go-spec・csharp-spec・python-spec）は
通信せず、`docs/pg_data/` から写すだけである。

成功すると、こう出る（`--- 結果 ---` の行が出れば通っている）。

```
更新: 13件
変更なし: 0件
  csharp: 581ページ書き出し / 取得失敗0件 / 本文なし0件
```

**`失敗` が出た資料は取り込まれない。** 1件の失敗で他は止まらないので、結果の行を
必ず読むこと。宛先が HTML を返した場合も失敗として報告される。

**走らせたら `docs_source/` の差分をコミットすること。** 追跡対象なので、取り直した
結果がそのまま次の移植先へ渡る版になる。

### 2-2. DBへ取り込む

```powershell
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --source-dir docs_source `
    --db docs_store.sqlite3 --keep-code-blocks
```

**3つのオプションはどれも省略できない。**

| オプション | 省くとどうなるか |
|---|---|
| `--source-dir docs_source` | 社内資料（`source/`）を技術ドキュメントのDBへ入れてしまう |
| `--db docs_store.sqlite3` | 社内資料のDBを上書きする。**パスを間違えても例外は出ず、空のDBが黙って作られる** |
| `--keep-code-blocks` | コード例がチャンクの途中で割れる（実測8.3%が破損） |

実行中は1ファイルずつ進捗が出る。**最後の3行が完了の証拠**である。

```
--- 結果 ---
取り込み: 53075チャンク / 767ファイル
DB内の総チャンク数: 53075（本文50906種）
```

**終了コードを確認すること。** `失敗: Nファイル` が出ていれば、そのファイルは入って
いない。終了コードは1になる。

### 2-3. 進み方の目安

初回は1時間前後かかる。**途中で止まっても、もう一度同じコマンドを打てば続きから
進む**（内容のハッシュで既に入ったファイルを飛ばす）。

- 埋め込み: 実測12.65チャンク/秒（NVIDIA L4・ngrok経由）
- ファイルごとの差分判定: 実測0.66〜0.74秒/ファイル（53,075チャンクのDBで）。
  767ファイルでおよそ10分。**2回目以降はここが待ち時間の大半になる**

## 3. 方法B: DBをコピーする

`docs_store.sqlite3`（273MB）をリポジトリ直下へ置くだけでよい。ベクトルは
`bge-m3` の1024次元で、マシンに依存しない。

**コピー前にStreamlitを止めること。** 書き込み中のファイルをコピーすると壊れる。

置いたら中身を確かめる。

```powershell
.\myvenv313\Scripts\python.exe -c "from ingest import store; c = store.open_store('docs_store.sqlite3'); print('チャンク:', c.count(), '本文:', c.chunk_count()); print('整合性:', c.integrity()); print('資料数:', len(store.indexed_sources(c)))"
```

期待する出力（2026-09-13 時点）:

```
チャンク: 53075 本文: 50906
整合性: (0, 0)
資料数: 764
```

**`整合性` は `(0, 0)` でなければならない。** 左は本文だけあって検索に出ない孤児、
右は出現だけあって本文が引けない行で、どちらも件数には表れずに検索結果を歪める。

`チャンク: 0` なら置き場所かファイル名が違う。

## 4. 動いていることの確認

取り込みCLIは最後に自動で検証する（接続を開き直し、検索を1回通し、整合性を見る）。
`取り込み後の検証に失敗しました` が出なければ、その3つは通っている。

画面から確かめるなら:

```powershell
.\myvenv313\Scripts\python.exe -m streamlit run rag_chat_app.py
```

サイドバーの「検索対象」を**技術ドキュメント**にして、`C#のrecord型の書き方` のように
尋ねる。回答の下の「参考にした情報」に `csharp/language-reference/...` のような出典が
出れば通っている。**DBが空のときはサイドバーに警告が出る。**

### 検索の質まで測る（任意）

```powershell
.\myvenv313\Scripts\python.exe -m scripts.check_retrieval --corpus docs
```

関連21問で根拠が残ること、圏外11問が空になることを見る（実測 2026-09-13: どちらも全問で期待どおり）。
**`gpt-oss:20b` が要る**（検索クエリを英語へ訳すため）。冒頭に出る `Ollama:` の行が
意図した宛先になっていることを必ず確かめること。

**走らせる前にモデルを暖めること。** 実測: 起動直後の最初の呼び出しは99.6秒かかる。
このスクリプトは翻訳が1問も効かないと中止する。

## 5. つまずきどころ

| 症状 | 原因 | 対処 |
|---|---|---|
| 検索結果が全部空 | `--db` のパス違いで空のDBが作られた | `取り込み先:` の行に出る絶対パスを確認 |
| 取り込みが進んでいないように見える | 差分判定に1ファイル0.7秒かかる | 待つ。標準出力はファイルへ流すとまとめて出るので `-u` を付けると流れが見える |
| 資料を直したのに何も処理されない | 内容が変わっていない。取り込み**規則**を変えたときも差分では処理されない | `--force` を付ける |
| `401` / `404` が返る | 認証つきプロキシ、またはトンネルが落ちた | `OLLAMA_API_KEY` を確認。Colab経由なら起動し直す |
| 翻訳が効かない（`check_retrieval`） | `gpt-oss:20b` が宛先に無い、またはモデルの読み込み待ち | 冒頭の `Ollama:` の行を確認。先に1回叩いて暖める |
| Ctrl+C で止めたのに処理が続く | シェルだけが落ちてPythonが残ることがある | `Get-CimInstance Win32_Process -Filter "Name='python.exe'"` で確認して止める |
| コード例が途中で切れる | `--keep-code-blocks` の付け忘れ | 付け直して `--force` で入れ直す |

## 6. オフラインの移植先

外部へ出るのは **2-1 の `fetch_docs` だけ**である。`docs_source/`（23MB）ごと持ち込め
ばこの手順は不要になり、取り込みが触る外部は `OLLAMA_HOST` だけになる。

方法Bなら外部通信は一切要らない（画面を使うときのOllamaを除く）。

## 付録: いま入っているもの

実際に答えられる範囲は [コーディング対応ライブラリ.md](コーディング対応ライブラリ.md)
