# コーディング対応ライブラリ

チャット画面のサイドバーで「検索対象」を **技術ドキュメント** に切り替えると、
取り込んだ公式ドキュメントを根拠にコード例・Markdown例・Mermaid を答える。
モデル（`gpt-oss:20b`）の学習時点の知識ではなく、取り込んだ記法で答えさせるための
仕組みである。設計の経緯は
[2026-09-12-latest-docs-ingestion-design.md](superpowers/specs/2026-09-12-latest-docs-ingestion-design.md)
にある。

対象の一覧は `docs_sources.toml` が管理する。本書はその中身と、いま実際にDBへ
入っているものを記録する。**数値はすべて実測であり、測っていないものは
「未測定」と書いてある。**

## 1. 取り込み済み（`docs_store.sqlite3`、2026-09-13 時点）

総チャンク数 **54,053**（本文51,859種）。`docs_sources.toml` の13件すべてが入っている。

2026-09-13 に Go の言語仕様（go-spec、761チャンク）、C# の言語仕様
（csharp-spec、3,214チャンク）、Python の言語リファレンス（python-spec、
1,263チャンク）を足した。いずれも公式が HTML しか出しておらず、既存の2経路では
届かなかったものである。人が md 化した原本をリポジトリへ置き、`kind = "local"` で
写す（下の表と5節）。

2026-09-13 に全件を取り込み直した。Markdown のコードフェンスの追跡を CommonMark の
規則に合わせた（`ingest/parsers/md_parser.py`）ためで、字下げされた開きフェンスを
数えられず、そこから先がずっとフェンスの中とみなされていた。失われていた `## ` は
9,069件中2,205件から80件に減り、チャンクは47,525→48,256に増えた。増えたのは
MDX を使う2件（langchain-text-splitters・streamlit）にほぼ集中している。

### リポジトリに置いた原本から取っているもの（`kind = "local"`、2026-09-13 追加）

公開されている Markdown がどこにも無い資料を受ける経路である。外部通信をしない。

| ソース | 記録した版 | チャンク | 原本（バージョン管理下） |
|---|---|---|---|
| go-spec | go1.27 | 761 | `docs/pg_data/go-language-specification.md` |
| csharp-spec | ECMA-334:2026 | 3,214 | `docs/pg_data/csharp-language-specification-unified.md` |
| python-spec | 3.14 | 1,263 | `docs/pg_data/python-language-reference-unified.md` |

原本は go.dev/ref/spec・ECMA-334・docs.python.org/3/reference を md 化した
ものである。**原本は
`docs/pg_data/` に置くこと。`docs_source/` に手で置いてはいけない。** そこは
`fetch_docs` の出力であり（2026-09-13 から追跡対象だが、それは変わらない）、手で
置いたファイルは `docs_sources.toml` に記録が残らず、どの版を入れたのか追えなく
なるうえ、取り直した瞬間に消える。実測 2026-09-13: 未登録のまま置かれた Go 仕様書の
生コピーが `docs_source/go/doc/` に紛れており、取り込めば go-spec.md と重複した
劣化版（pandoc属性が残り1節が最大82,825バイト）が入るところだった。

**csharp-spec だけ日本語である。** 他の12件はすべて英語で、検索は質問を英語へ
訳してから当てる（`ingest/query_translation.py`）。この1件だけ言語が食い違う。
何が起きるかは4節に実測つきで書いてある。

ページ数は**本文のあるページの数**である。選別したページ数とは一致しない。
フロントマターだけのページ（リダイレクト指定や、目次だけの `index.md`）は
取り込んでも0チャンクにしかならないので書き出さず、`fetch_docs.py` が
「本文なし」として数える。実測 2026-09-13: go 8件、markdown 5件、mermaid 1件。

「記録した版」は `requirements.txt` で固定している版である。取得先は常に最新版の
ドキュメントなので厳密には一致しない。どの版を使っている状態で取り込んだかを
残すために持っている。ollama は Python パッケージとして固定していない（HTTPで
直接叩いている）ため `0.0.0` を入れてある。

**csharp-spec**（801節、2,411,764バイト、コードフェンス526）
**C# の言語仕様そのもの（ECMA-334）。** 字句構造、型、変数、変換、パターン、式、
文、名前空間、クラス、構造体、配列、インターフェイス、列挙型、デリゲート、例外、
属性、安全でないコード、付録（文法・移植性・標準ライブラリ・文書化コメント）。
`csharp` が「どう書くか」を教えるのに対し、こちらは「何が正しいか」を定める。
「確定代入の正確なルール」「オーバーロードの解決」のように、解説側に節として
存在しない規範的な規則はここにしか無い。

**原本の H1 は31個あり、そのすべてが章題である。** 取り込み側の約束は「H1 が1つ
だけあり、それが資料の題名」なので（`parse_md`）、そのまま写すと最初の1つだけが
題名になり、残り30個の章題は `# 章題` という行のまま直前の章の最後の節に紛れ込む。
`title = "C# 言語仕様書"` を設定に書くと、題名はその文字列から作り、原本の H1 は
章題として節の境界へ下りる。

節の境界は H4 まで下ろしてある（`section_level = 4`）。H1..H3 までだと1節が最大
55,115バイト残る（「9.4.4 確定代入を決定するための正確なルール」）。H4 まで下ろすと
801節・中央値1,981バイトになり、残る最大は「A.3 構文文法」（54,585バイト、割れない
1つのコード塊）と標準ライブラリの一覧だけになる。見出しは「9.4.4.15 Try-finally
ステートメント」のように番号が階層を持つので、`#` の数が潰れても出典から場所が
分かる。

**「A.3 構文文法」だけは割れる。** 54,585バイトが**1つのコードフェンス**で、
見出しが1つも無い。コードブロックの上限は2,400字なので（`ingest/chunker.py` の
`MAX_CODE_BLOCK_CHARS`）、この1節が**81チャンク**に切られる。文法の途中で切れた
断片が並ぶことになり、「C# の文法全体を見せて」には答えられない。個々の生成規則は
本文側（12章・13章など）が各所で引用しているので、そちらで引ける。

**この資料だけ日本語である。**（実測は4節）

## 2. 取り込み待ち

**現在なし。** `docs_sources.toml` の12件はすべて `docs_store.sqlite3` に反映済み
である。反映には Ollama への接続（埋め込み）が要るので、追加したときはこの節に
「未取り込み」として残し、埋め込みを走らせてから1節へ移すこと。

実測した所要時間は3回分ある（いずれも NVIDIA L4、ngrok 経由）。

| 日付 | 対象 | チャンク | 所要 |
|---|---|---|---|
| 2026-09-12 | streamlit / huggingface_hub / ollama / pymupdf ほか | 11,993 | 724秒 |
| 2026-09-13 | langchain-text-splitters / mcp | 19,382 | 1,532秒 |
| 2026-09-13 | csharp / go / mermaid / markdown（758ファイル） | 17,676 | 2,417秒 |

差分取り込みは効いている。2回目は6ファイル中4ファイルが「変更なし」でスキップ
され、新しい2件だけが処理された。3回目も既存6件はすべてスキップされている。

**ファイル数が多いと遅くなる。** 3回目は12.65チャンク/秒だった2回目に対して
**7.31チャンク/秒**で、ほぼ半分である。チャンク数はむしろ少ないのに時間がかかった。
1ページ1ファイルで758ファイルを処理したためで、原因は埋め込みの往復回数にある
（実測 2026-09-13: 埋め込みは1件でも8件でも1回あたり約640ms。`EMBED_BATCH_SIZE`
は8で、16GB環境で決めた値である）。**GPUの速さではなく往復の回数が効いている。**

4回目は 2026-09-13 の全件取り込み直し（764ファイル・48,256チャンク）である。
資料は1文字も変わっておらず、変わったのは取り込み側（フェンスの追跡）なので、
差分取り込みでは1件も処理されない。`--force` を付けて走らせた。所要は計測して
いない。**取り込みの規則を直したときは `--force` が要る**ことをここに残す。

5回目は go-spec の追加（1ファイル・577チャンク）で、他の764ファイルはすべて
「変更なし」である。**待ち時間の大半は埋め込みではなく差分判定だった。**

実測 2026-09-13（48,256チャンクのDB）: `store.stored_file_hash()` は1回あたり
**0.66〜0.74秒**かかる。`collection.get(where=...)` が全行を読んでから Python 側で
絞り込む作り（`ingest/vector_store.py` の `get()` → `_rows()`）だからで、
1ファイルにつき1回呼ぶため766ファイルで**およそ9分**になる。埋め込みのほうは
577チャンク＝73往復で、暖まった状態なら1往復0.4〜0.9秒（実測）なので1分に満たない。

**コーパスが大きいほど、変わっていないファイルを確かめるだけで時間がかかる。**
上の「原因は埋め込みの往復回数にある」は3回目（17,676チャンクを新規に入れた回）
の話で、そちらは今も正しい。1ファイルだけ足す回では比率が逆になる。直すなら
`get()` に絞り込みをSQLへ降ろす必要があり、この節の記録とは別の作業である。

## 3. 対象にできないもの

`llms-full.txt` を公開していないライブラリは、`kind = "llms"` では対象にできない。
GitHub に生の Markdown があるものは `kind = "github"` で取れるようになった
（[2026-09-13-github-docs-ingestion-design.md](superpowers/specs/2026-09-13-github-docs-ingestion-design.md)）。
どちらにも無いものは、人が md 化した原本をリポジトリへ置けば `kind = "local"` で
入る（5節）。**md 化の手間は人が払う。** 自動で HTML を Markdown に直す仕組みは
持たない。Web クローリングは却下したままである。

### Java（GitHub にも公式の Markdown が無い）

実測 2026-09-13: `dev-java/dev.java` と `java-tutorials/java-tutorials` はいずれも
404 である。Spring は実在するが **AsciiDoc** であり
（`spring-projects/spring-framework` 471ファイル/3.07MB、

## 4. 実測された品質と使い方

### 日本語で質問してよい

質問は内部で英語の検索クエリに訳してから検索する（`ingest/query_translation.py`）。
**回答は元の日本語の質問から生成する**ので、訳が外れても回答が壊れることはなく、
検索の精度が落ちるだけである。

この仕組みが要る理由は実測にある。取り込んだ資料は英語だが、検索の仕組み
（文字bigramのBM25、日本語で調整したしきい値）は社内資料向けに作られているため、
日本語のまま検索すると外す。

| 質問 | 訳された検索クエリ | Reranker | 答えたAPI |
|---|---|---|---|
| Streamlitのキャッシュはどう書く？ | `Streamlit st.cache_data usage` | 0.06 → **5.68** | `st.cache_data` / `st.cache_resource` |
| Streamlitでモーダルダイアログを出す書き方を教えて | `Streamlit modal dialog st.dialog example` | 3.40 | `st.dialog`（現行シグネチャ） |
| Streamlitでマーメイドの図を描くには | `Streamlit Mermaid diagram ...` | 0.77 | `st.mermaid_chart` |

翻訳を入れる前は、1行目の質問が CLI の `streamlit cache clear` を引き、モデルは
（渡された根拠に照らして正しく）「ドキュメントには記述がありません」と答えていた。

#### 翻訳プロンプトを直そうとして、やめた（2026-09-14）

上の go-spec・csharp-spec・python-spec の測定で「節の名前から離れた言い回しほど
外れる」が3回続けて出た。訳す側にそれを言えば直るのではないかと考えて測り、
**直らなかったので入れていない。** 同じことをもう一度試さないために残す。

試したのは `ingest/query_translation.py` の `_prompt()` に1段落足す案で、2通り
用意した。どちらも「日本語を逐語訳せず、その分野の資料が節の見出しに使う定型の語に
置き換えてください（例:「呼ばれる条件」→ invocation）」までは同じで、後半が違う。

- **B**: 「「〜の仕様」→ 語を足さず対象の名前だけ」
- **C**: 「ただし対象を指す語は削らないでください」（B が語を削りすぎたため）

54,053チャンク・床1.0で、落ちる3問・既存の関連25問・圏外11問を3案で通した。

| | 落ちる3問で0件 | 関連25問で0件 | 圏外11問で通過 |
|---|---|---|---|
| **A 現行** | 3 | **0** | 0 |
| B 語を削る | 2 | **1** | 0 |
| C 語を残す | 2 | **2** | 0 |

**1問救って1〜2問落とす。** 救えたのは「Pythonのデスクリプタで `__get__` が
呼ばれる条件」だけで、`called conditions` → `invocation conditions` になり
0件から3件（1.62）へ戻る。代わりに「Goのfor文でrange句」が
`Go for loop range syntax`（2件・2.47）→ `Go for range syntax`（0件）になる。

**C の「削らないでください」は効かなかった。** B と1文字も違わない
`Go for range syntax` を返す。否定形の指示でモデルの語の選び方を止められると
思ったのが誤りで、B が落とした1問は C でも落ちたままである。

**プロンプトを伸ばすと翻訳そのものが壊れる。** C だけで
「Streamlitでモーダルダイアログ」が4件（3.70）から0件になった。訳文を見ると
**原文の日本語がそのまま**返っている。`gpt-oss:20b` の生の返答を3回取ると
**2回が空文字**で、`translate_query` が JSON の破損として原文へ落としていた
（この設計自体は意図どおり動いている）。プロンプトを足す案には、狙った語の
選び方が変わるかどうかとは別に、この副作用がある。

**残る2問は翻訳では動かない。** 「Goのselect文で複数のチャネルを待つ構文」と
「Pythonのfor文の仕様」は、A・B・C の3案とも訳文が完全に同一で、3案とも0件で
ある。上の go-spec・python-spec の節に書いたとおり原因はコーパス側（`select` /
`for` という語が別の節と競合する）であり、訳し方を変えても届かない。

**同一プロセス内では翻訳は揺らがない。** 12問を5回ずつ測ると、60回すべてが
1文字違わず同じ訳になる。揺らぐのはプロセスをまたいだときだけで、
「C#のオーバーロード解決」は A のまま `... best function member selection rules`
（0件）を5回続けて返すプロセスと、`... best function member rules`（3件・2.04）を
3回続けて返すプロセスがあった。**この質問が不安定なのは A 自身が `selection` を
付けたり付けなかったりするため**であって、上の python-spec の節に書いた
「埋め込みサーバーを入れ替えると採否が動く」とは別の話である（あちらは訳文が
同一であることを確かめた上での観測である）。

**測定に使った質問を例文としてプロンプトへ書くことはしなかった。**
「for文のrange句 → for loop range」と書けばこの39問では直るが、それはこの質問集合に
合わせ込むだけで、他の質問に効く根拠が無い。

### API 名を書くと強い

同じ内容でも、API 名を含めた方が検索が当たる。実測（2026-09-12、Streamlit）:

- `st.cache_data`（API名）→ Reranker **7.02**
- `How do I cache data in Streamlit?`（英語の文）→ **5.73**
- `Streamlitのキャッシュはどう書く？`（日本語の文）→ **0.06**

分かっている API 名があれば質問に入れるとよい。翻訳を挟んでも同じで、上の
langchain の例のように、訳がクラス名まで届かないと外す。

### Go は版番号を入れると当たる

上表の最後の1件は外している。引いたのは FAQ の「Goに機能Xが無くて気になるなら」と

### 弱いところ

- **Go の入門的な解説は無い。** Effective Go は HTML で、まだ入っていない。文法は

- **仕様書は仕様書の語で書かれている。** 俗称（`comma ok`）や一般的な言い回し

## 5. ライブラリを追加する

`docs_sources.toml` に足して、取得と取り込みを走らせる。

```bash
python -m scripts.fetch_docs
python -m scripts.ingest_source --source-dir docs_source \
    --db docs_store.sqlite3 --keep-code-blocks
```

GitHub から取る場合は `kind = "github"` を書く。`llms-full.txt` を公開していない
対象（言語そのものの文法など）はこちらになる。

```toml
[[source]]
name = "csharp"
kind = "github"
repo = "dotnet/docs"
ref = "main"                     # 既定ブランチを明示する。golang/website は
paths = ["docs/csharp/linq"]     # master、mermaid-js/mermaid は develop である
resolve_code_refs = true         # 既定 false。MS Learn の :::code を解決する
version = "0.0.0"
```

未認証で足りる（Trees API はリポジトリにつき1回、未認証枠は60回/時）。
**トークンは要らない。**

公開されている Markdown がどこにも無い資料は `kind = "local"` を書く。原本を
リポジトリ（`docs/pg_data/`）へ置き、`path` でそれを指す。外部通信はしない。

```toml
[[source]]
name = "go-spec"
kind = "local"
path = "docs/pg_data/go-language-specification.md"  # リポジトリの根からの相対
section_level = 3   # 既定 2。H3 までを節の境界にする
version = "go1.27"
```

`section_level` は資料の見出しの作りを見て決める。取り込み側が節の境界にするのは
`## ` だけなので（`ingest/parsers/md_parser.py`）、H2 が少ない資料はそのままだと
1節が巨大になる。実測 2026-09-13（Go の仕様書）: 原文のままだと19節・最大82,825
バイト、`section_level = 3` で122節・中央値1,529バイト。**節の中央値が数千バイトを
超えるなら下ろす。**

**原本の H1 が複数あるなら `title` を書く。** 取り込み側の約束は「H1 が1つだけ
あり、それが資料の題名。`## ` が節の境界」である（`parse_md`）。章ごとに H1 を
持つ資料はこれを破り、最初の1つだけが題名になって、残りは `# 章題` という行の
まま直前の章の最後の節に紛れ込む。`title` を書くと、題名はその文字列から1行だけ
作り、原本の H1 はすべて章題として節の境界へ下りる。

```toml
[[source]]
name = "csharp-spec"
kind = "local"
path = "docs/pg_data/csharp-language-specification-unified.md"
section_level = 4     # H1..H4 が節の境界になる
title = "C# 言語仕様書"  # 原本の H1 は31個とも章題である
version = "ECMA-334:2026"
```

`title` と `section_level` を両方書くと階層が潰れる（C# では H1〜H4 がすべて
`## ` になる）。C# の仕様書の見出しは「9.4.4.15 Try-finally ステートメント」の
ように番号が階層を持つので、`#` の数を失っても出典から場所が分かる。**番号の
無い資料でこの組み合わせを使うと分からなくなる。**

写すときに本文を直すのは3箇所だけである（`scripts/local_source.py` の
`normalise` と `render_page`）。原本は1バイトも変えない。

- 見出し末尾の pandoc 属性（`{#Introduction}` `{.subtitle}`）を落とす。HTML の id
  から機械的に作られた名残で、残すと出典の見出しが「Introduction {#Introduction}」
  になる。実測 2026-09-13: Go の仕様書は168見出しすべてに付いていた
- `section_level` までの見出しを `## ` へ引き上げる
- `title` があれば H1 を `## ` へ下ろし、本文の先頭へ `# 題名` を1行足す

どちらもコードフェンスの中は触らない。判定は取り込み側と同じ規則を使う
（`ingest/parsers/md_parser.py` の `scan_fences`）。

追加するときの注意が2つある。

**`llms.txt` ではなく `llms-full.txt` の URL を書くこと。** `llms.txt` は各ページへの
リンクの目次であって本文ではない（実測 2026-09-12: `docs.streamlit.io/llms.txt` は
66,927バイトあるがコードフェンスは**0個**）。目次を取り込むと、検索は当たるのに
答えが書けないという診断しにくい状態になる。

**ドキュメントのドメインはパッケージ名から推測できない。** 実例:

- `mcp` → `modelcontextprotocol.io`（PyPI 名と無関係）
- `langchain-text-splitters` → `docs.langchain.com`（`python.langchain.com` は HTML を返す）
- `huggingface_hub` → `huggingface.co/docs/huggingface_hub/`（サブパス）

URL を間違えても、サーバーが 200 で HTML を返すことがある。`fetch_docs.py` は
本文の先頭と `Content-Type` の両方を見て HTML を弾き、`NotDocumentationError` を
投げて1件の失敗として報告する（他のライブラリの取得は続く）。本文中に HTML の例が
出てくる正しい資料は捨てない（先頭だけで判定しているため）。

この歯止めは実害があって入れた。`python.langchain.com/llms-full.txt` は 404 では
なく、ドキュメントサイトの HTML を **200 で** 返す（実測 2026-09-13）。状態コード
しか見ていなかったため素通りし、HTML・CSS・JavaScript が **1,531チャンク**
（当時のコーパス11,993件の12.8%）DB に入っていた。汚染分は削除済みである。
この失敗は静かで診断が遠い。取り込みは成功と表示され、検索も当たり、ただ答えが
書けないノイズが混ざるだけだからである。

## 6. 更新

取得は内容の SHA-256 を前回と比べ、変わったものだけ書き出す。変わっていなければ
「変更なし」と報告してファイルを書き換えないので、取り込みも走らない。

`kind = "github"` は **1ページ1ファイル**で置くので、差分もページ単位で効く。
1ページ直っても再埋め込みは1ページ分で済み、出典も実際のページ名で出る。
フロントマターには木のコミット SHA が入るので、どの時点から取ったかが後から分かる
（`llms-full.txt` では取れない再現性である）。

定期実行はしない。人が `scripts/fetch_docs.py` を起動したときだけ外部へ通信する
（`AGENTS.md` の「外部ドキュメントの参照」参照）。

`docs_source/` と `docs_store.sqlite3` は `.gitignore` 済みである。
`source/` と `vector_store.sqlite3` と同じく、いつでも取り直せるためである。
追跡するのは設定ファイル `docs_sources.toml` だけ。
