# 処理箇所マップ

RAGパイプラインの主要処理が、どのファイルのどこで行われているかの索引。
行番号は 2026-09-02 時点（fix/rerank-measurement-record: ca62d88）のもの。

対象は本番コード（`ingest/`, `scripts/`, `rag_chat_app.py`）。

## 全体の流れ

```
source/ の資料
  └ ingest/parsers/         形式ごとに解析 → ParsedUnit（OCR / VLM はここで発動）
      └ ingest/chunker.py   チャンク分割
          └ ingest/embedder.py  ベクトル化（Ollama bge-m3）
              └ ingest/store.py ベクトルストアへ格納（SQLite）
                                    │
質問 ─ ingest/retrieval.py ─┬ ベクトル検索（ingest/vector_store.py）
                            ├ BM25検索（ingest/lexical.py）
                            ├ RRF で融合 → 上位8件
                            └ ingest/reranker.py で測り直して並べ替え
                                  → 上位4件 → ingest/prompting.py → LLM
```

実測結果（2026-09-02、795チャンク／49資料、6問）は
[設計書 8.1節](superpowers/specs/2026-08-30-reranker-design.md) に記録がある。要点:

- **上位4件の並びは6問すべてで変化した。** 1位が入れ替わったのは3問で、いずれもリランカー側が正しい
- 最大の効果は「見出しだけの短いチャンク」を落とすこと。ベクトルもBM25も短い完全一致を高く評価するため上位に来るが、回答の根拠にはならない
- **ゲートは影響を受けていない**（関連の最大距離 0.443 ≤ 0.50 < 圏外の最小距離 0.522）
- スコアの絶対値は採否に使えない。使えるのは同じ問いの中での相対順位だけ

### 3-6. 前段の並べ替え: RRF（Reciprocal Rank Fusion）

**どの候補をリランカーに見せるか**を決める前段。両アームの順位だけを融合する。

| 箇所 | 内容 |
|---|---|
| [retrieval.py:39](../ingest/retrieval.py#L39) | `RRF_K = 60`（順位の逆数を足すときの緩和定数） |
| [retrieval.py:205-209](../ingest/retrieval.py#L205-L209) | `1/(RRF_K + rank)` をベクトル側・BM25側それぞれから加算 |
| [retrieval.py:226-233](../ingest/retrieval.py#L226-L233) | RRFソート。スコア降順 → ベクトル距離昇順 → BM25スコア降順 → チャンクID（同点でも並びを決定的にするため） |
| [retrieval.py:237](../ingest/retrieval.py#L237) | 上位 `SEARCH_RESULT_COUNT = 4` 件で切る。リランカーを通すのはこの直前（[retrieval.py:235-236](../ingest/retrieval.py#L235-L236)）なので、切られるのは並べ替え後の順位である |
