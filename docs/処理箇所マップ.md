# 処理箇所マップ

RAGパイプラインの主要処理が、どのファイルのどこで行われているかの索引。
行番号は 2026-09-07 時点（feat/drop-navigation-slides）のもの。ナビゲーション用
スライド（章扉・目次・締め）の除外機能の追加（`ingest/navigation.py` の新設と
取り込みループの変更）に合わせて、**全参照を機械的に照合し直した**
（ラベルとリンク先の一致・範囲内・指す行の内容）。

その後、画像取り込み（`ingest/image_text.py` の新設、`.png`/`.jpg`/`.jpeg`/`.drawio`
対応、docx/xlsx/mdの埋め込み画像対応）に合わせて、1節・6節・7節を
2026-09-12（feat/image-ingestion）時点に照合し直した。2〜5節・8節の行番号は
2026-09-07時点のままで、この間の変更を反映していない。

対象は本番コード（`ingest/`, `scripts/`, `rag_chat_app.py`）。

## 全体の流れ

```
source/ の資料
  └ ingest/parsers/         形式ごとに解析 → ParsedUnit（OCR / VLM はここで発動）
      └ ingest/navigation.py  ナビゲーション用スライド（章扉・目次・締め）を除外
          └ ingest/chunker.py   チャンク分割
              └ ingest/embedder.py  ベクトル化（Ollama bge-m3）
                  └ ingest/store.py ベクトルストアへ格納（SQLite）
                                    │
質問 ─ ingest/retrieval.py ─┬ ベクトル検索（ingest/vector_store.py）
                            ├ BM25検索（ingest/lexical.py）
                            ├ RRF で融合 → 上位8件
                            └ ingest/reranker.py で測り直して並べ替え
                                  → 上位4件 → ingest/prompting.py → LLM
```

> **規則は日本語のセミナー資料の書式に強く結び付いている。** 英語資料や別テンプレート
> のスライドには当たらなくなり、取りこぼす側に倒れる。一方で**本文を誤って落とすことは
> ある**。先頭が数字だけの行で始まる短い本文（`38\n年次有給休暇は…`）、丸数字で始まる
> 本文（`①\n…`。`'①'.isdigit()` は真）、「目次」で始まる10字以下の見出しを持つ本文
> （`目次の作り方\n…`）はいずれも落ちる。**これは塞いでいない既知の限界であり**、
> 設計書2.4節に一覧がある（[navigation.py:6-23](../ingest/navigation.py#L6-L23)）。
>
> 本文を実際に守っているのは `_MAX_DIVIDER_LINES`（生の行数）である。
> `モデル就業規則.pdf` は1〜9ページすべてが「先頭の内容行が数字のみ」で（PDFの
> ページ番号が本文の先頭に来るため）、9ページとも普通の本文でありながら生の行数
> （16〜38行）だけで生き残っている（2026-09-07、このPDFを単体でパースして確認。
> 94ユニット中9件）。
>
> 全ユニットがナビゲーション判定になった資料は、`scripts/ingest_source.py` が
> 除外せず警告を出す（2-3節）。

## 3. Reranker でランキングしている箇所

RRFで融合した上位 `RERANK_CANDIDATE_COUNT = 8` 件を、クロスエンコーダ

実測結果（2026-09-02、795チャンク／49資料、6問）は
[設計書 8.1節](superpowers/specs/2026-08-30-reranker-design.md) に記録がある。要点:

- **上位4件の並びは6問すべてで変化した。** 1位が入れ替わったのは3問で、いずれもリランカー側が正しい
- 最大の効果は「見出しだけの短いチャンク」を落とすこと。ベクトルもBM25も短い完全一致を高く評価するため上位に来るが、回答の根拠にはならない

- スコアの絶対値は採否に使えない。使えるのは同じ問いの中での相対順位だけ

### 3-6. 前段の並べ替え: RRF（Reciprocal Rank Fusion）

**どの候補をリランカーに見せるか**を決める前段。両アームの順位だけを融合する。

| 箇所 | 内容 |
|---|---|
| [retrieval.py:47](../ingest/retrieval.py#L47) | `RRF_K = 60`（順位の逆数を足すときの緩和定数） |
| [retrieval.py:249-253](../ingest/retrieval.py#L249-L253) | `1/(RRF_K + rank)` をベクトル側・BM25側それぞれから加算 |
| [retrieval.py:270-277](../ingest/retrieval.py#L270-L277) | RRFソート。スコア降順 → ベクトル距離昇順 → BM25スコア降順 → チャンクID（同点でも並びを決定的にするため） |
| [retrieval.py:281](../ingest/retrieval.py#L281) | 上位 `SEARCH_RESULT_COUNT = 4` 件で切る。リランカーを通すのはこの直前（[retrieval.py:279-280](../ingest/retrieval.py#L279-L280)）なので、切られるのは並べ替え後の順位である |
| [lexical.py:124](../ingest/lexical.py#L124) | BM25側のランキング（スコア降順、同点はID順） |

> 融合のキーは**本文のハッシュ（chunk_id）**である。両アームとも `chunks` の
> 本文単位で動くため、同じ本文が複数の資料に現れても候補枠を食い合わない。
>
> コード内コメント（[retrieval.py:179-181](../ingest/retrieval.py#L179-L181)）にある通り、RRFスコアは順位のみに依存するため**採否の判定には使えず**、採否はベクトル距離のしきい値が担っている。

> `ocr_bytes()` を遅延importする（7-1節）。呼び出し側が明示的に渡すのはテストだけで、
> 本番のディスパッチャ（[parsers/\_\_init\_\_.py:41-45](../ingest/parsers/__init__.py#L41-L45)）は
> `ocr_bytes` を渡さない。
>
> PDF/PPTX/DOCX/XLSX/Markdownは「この資料は画像を含むか」を判定してから走査を
> 分けるのではなく、`caption_image is not None or ocr_bytes is not None` が偽なら
> 画像走査そのものを省く（各パーサーのdocstring参照）。本番では`ocr_bytes`が渡らない
> ため、実質的に `caption_image`（VLM）が使えるときだけ埋め込み画像の説明もOCRも
> 実行される（6-4節）。**画像ファイル単体（`ingest/parsers/image_parser.py`）だけは
> この判定を持たない**。ファイルそのものが画像であり走査の要否を判定する必要が
> 無いため、`describe_image()` を無条件に呼ぶ。VLMが使えなくてもOCRは常に試みる
> （説明文のほうだけがVLMの有無に左右される）。
