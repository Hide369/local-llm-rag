# ローカル文書RAGチャット

PDF・PowerPoint・Word・Markdown を完全ローカルでベクトルDBに取り込み、出典付きで回答するRAGチャット。
既定では外部サービスへの送信は一切行わない
（GPUを強化したい場合のみ、任意で「[ColabのL4 GPUに接続する](#colabのl4-gpuに接続する)」を使える）。
「運転音26dB以下で奥行き510mmに設置できる機種」のように数値条件を含む質問は、ベクトル検索ではなく
Markdownのフロントマター由来のメタデータで機械的に絞り込み、条件に合う資料を全件そろえた表から回答する。

## 必要なもの

- Python 3.13（`myvenv313`）
- Ollama（インストール直後の標準ポート `http://127.0.0.1:11434` で待ち受けていること）
- モデル: `ollama pull bge-m3` と `ollama pull qwen2.5:7b-instruct`
  （`llama3.1:8b` でも動く。下記「モデルの比較」参照）

### Ollamaの待ち受けポートについて

`ingest/embedder.py` の `DEFAULT_OLLAMA_HOST` はOllamaの標準ポート
`http://127.0.0.1:11434` に合わせてあるため、通常は何も設定せずに動く。
`ollama list` が応答すれば、そのOllamaに接続できる。

標準以外のポートで動かしている場合のみ、環境変数 `OLLAMA_HOST` で上書きする。
`http://` から書くこと（コードはこの値をそのままURLに埋め込む）。

```powershell
$env:OLLAMA_HOST="http://127.0.0.1:12000"
.\myvenv313\Scripts\python.exe -m scripts.ingest_source
```

`localhost` は使わないこと。Windowsでは先にIPv6の `::1` に解決され、
1リクエストあたり約2.1秒を浪費する（`127.0.0.1` なら約80ms）。

なお `udemy1.py`〜`udemy3.py` は教材オリジナルのコードで `http://localhost:12000` を
直接埋め込んでおり、環境変数を読まない。これらを動かす場合は12000番で待ち受ける
Ollamaインスタンスを別途用意する必要がある（例: `$env:OLLAMA_HOST="127.0.0.1:12000"; ollama serve` で
2つ目のインスタンスを起動する。モデルは共有される）。

## 使い方

取り込みたい資料を `source/` に置く（`.pdf` / `.pptx` / `.docx` / `.md`）。
**サブフォルダに分類して置いてもよい**（例: `source/家電製品/*.md`）。再帰的に走査する。

```powershell
# 初回の取り込み（実測 約24分。source/ 直下8ファイルとMarkdown 30ファイル、
# 計38ファイル・496チャンクを処理した。OCR 23ページが時間の大半を占める）
.\myvenv313\Scripts\python.exe -m scripts.ingest_source

# Markdownだけを取り直す（フロントマターを直したときなど。OCRを伴わないため数十秒）
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --force --only-suffix .md

# PPTXだけを取り直す（スライドの分割ロジックを直したときなど）
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --force --only-suffix .pptx

# PDF/PPTX内の図・写真もVLMで説明文化する（大幅に時間が伸びる。事前に
# ollama pull qwen2.5vl:7b が必要。ColabのL4に接続していればそちらで処理される）
# 同じ機能はチャット画面（rag_chat_app.py）の「差分を取り込む」の
# チェックボックスからも使える
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --with-vlm

# チャットを起動する
.\myvenv313\Scripts\python.exe -m streamlit run rag_chat_app.py
```

`--only-suffix` を指定したときは孤児削除（`source/` から消えた資料をDBからも消す処理）を
行わない。対象外の拡張子のファイルがすべて孤児と判定され、他形式のチャンクが丸ごと
消えてしまうためである。

2回目以降はファイルのハッシュを見て変更分だけを処理するため数秒で終わる。
UIサイドバーの「差分を取り込む」も同じ処理を呼ぶ。

**取り込み中は `chroma_db` を開くプロセスを他に一切起動しないこと。** 理由は
「既知の制約」の節を参照。コレクションを丸ごと作り直す場合はOCRを含む全ファイルを
再処理するため、初回と同程度の時間（約24分）がかかる。

### コマンドは必ず `python.exe -m` 経由で実行すること

`streamlit.exe` や `pytest.exe` のようなランチャーは、venv作成時のPython絶対パスを
実行ファイル内部に焼き込む。そのためプロジェクトフォルダを移動・改名すると
`Fatal error in launcher: Unable to create process using '...'` で起動しなくなる。

`python.exe` は自身の位置から環境を解決するため移動の影響を受けない。
`python.exe -m streamlit` の形ならランチャーを経由しないので常に動く。

（このリポジトリの `myvenv313` は実際に `09_RAG_FineTuning\04_...` で作成された後に
移動されており、`pyvenv.cfg` の `command` 行に当時のパスが残っている。
`python.exe` と `pythonw.exe` 以外の `Scripts\*.exe` は現在すべて壊れている。
`.exe` を使えるようにしたい場合は該当パッケージを
`python.exe -m pip install --force-reinstall --no-deps <package>` で入れ直す。）

## ColabのL4 GPUに接続する

ローカルPCのGPUが非力な場合、生成・埋め込みの両方をGoogle Colab（有料版のL4 GPU）上の
Ollamaに肩代わりさせられる。7B〜8Bクラスのモデル（`qwen2.5:7b-instruct` /
`llama3.1:8b` / `bge-m3`）はL4の24GB VRAMに収まる。

仕組みは単純で、[ingest/embedder.py](ingest/embedder.py) と [rag_chat_app.py](rag_chat_app.py)
が接続先を環境変数 `OLLAMA_HOST` から読む既存の仕組みをそのまま使う。Colab側にOllamaと、
`X-API-Key` ヘッダーで認証する軽量なリバースプロキシを立て、ngrokでその1ポートだけを
外部公開する。

**手順**

1. [colab/run_ollama_server.ipynb](colab/run_ollama_server.ipynb) をGoogle Colabで開く
   （ランタイム → ランタイムのタイプを変更 → GPU: L4）
2. [ngrok](https://ngrok.com) の無料アカウントでauthtokenを取得しておく
3. ノートブックのセルを上から順に実行する。最後に表示される `OLLAMA_HOST`
   （ngrokの公開URL）と `OLLAMA_API_KEY` を控える
4. ローカルで `.env.example` を `.env` にコピーし、その2つの値を書き込む
5. いつも通り起動する

   ```powershell
   .\myvenv313\Scripts\python.exe -m streamlit run rag_chat_app.py
   ```

   サイドバーのモデル選択に関わらず、生成・埋め込みともにColab側のOllamaで処理される。

**知っておくこと**

- Colabのランタイムはアイドルや時間経過で切断される。常時稼働のAPIとしてではなく、
  使う時だけノートブックを起動する運用を前提にしている。切断されたら
  ノートブックを再実行し、新しいURLとAPIキーで `.env` を更新する。
- `X-API-Key` が一致しないリクエストはプロキシが401で拒否するが、ngrokのURLと
  APIキー自体は他人に共有しないこと（Colab上の資料・会話内容に到達できてしまう）。
- ローカルのOllamaに戻すには、`.env` の `OLLAMA_HOST` / `OLLAMA_API_KEY` を削除するか
  コメントアウトすればよい（既定値の `http://127.0.0.1:11434` に戻る）。

## 構成

| パス | 役割 |
|---|---|
| `ingest/` | 取り込みパイプライン（UIに依存しない） |
| `ingest/conditions.py` | 質問から絞り込み条件を抽出する（LLMに依存） |
| `ingest/catalog.py` | 条件で資料を絞り込み仕様表に整形する（LLMに依存しない） |
| `scripts/ingest_source.py` | 取り込みCLI |
| `ingest/lexical.py` | BM25の全文検索（文字bigramトークナイザ含む。外部依存なし） |
| `ingest/retrieval.py` | ベクトル検索とBM25をRRFで融合し、圏内ゲートで採否を決める |
| `scripts/check_retrieval.py` | 関連度しきい値の距離実測とBM25側の回帰確認 |
| `rag_chat_app.py` | Streamlit UI |
| `udemy1.py` 〜 `udemy3.py` | 教材の各段階。`local_docs` コレクションを使い続ける |

このプロジェクトのコレクション（`local_docs_v2`、bge-m3 / 1024次元）は、教材が使う
`local_docs`（nomic-embed-text / 768次元）とは別名で `chroma_db/` 内に共存している。
次元が異なるベクトルを混在させないよう、意図的に別コレクションにしている
（`ingest/store.py` 参照）。現在 `local_docs_v2` は `source/` 直下8ファイルと
`source/家電製品/` 配下30ファイル（計38ファイル）から496チャンクを保持している
（PPTXをテキストボックス単位に分割したことで44→80チャンクに増え、他形式は
416チャンクのまま変わっていない。旧方式でも44だったのは、テキストを含む43枚の
うち852字の1枚が`CHUNK_SIZE`（800）を超えて`ingest/chunker.py`で2分割されて
いたため）。`local_docs` は21チャンクを保持している
（`chromadb` で `list_collections()` して実測）。

## モデルの比較

回答生成のモデルはサイドバーのプルダウンで切り替えられる。選べるのは
`rag_chat_app.py` の `MODELS` に列挙したモデルだけで、既定は `qwen2.5:7b-instruct`。
別のモデルを試すときは `MODELS` に追記する（`ollama pull` 済みであること）。
下の表の2モデルは同じ経路（条件抽出→絞り込み／検索→生成）で4回ずつ実測した
（2026-08-13）。`gpt-oss:20b` は動作確認のみで、同じ形式の実測はまだ無い。

| | qwen2.5:7b-instruct | llama3.1:8b |
|---|---|---|
| 条件抽出のルーティング | 3/3 | 3/3 |
| 最大容量と該当型番（文章で正答） | 3/4 | 4/4 |
| 「議題」と「次回会議の議題」の区別 | 4/4 | 4/4 |
| 1回答あたりの時間 | 約20.8秒 | 約15.8秒 |

**この3項目では llama3.1:8b のほうが速く、精度も同等以上である。** qwen2.5 は
説明を厚く書く傾向があり、好みで選んでよい。切り替えはサイドバーの「モデル名」だけで、
コード変更もDBの取り直しも要らない。

モデルを替えて分かったこと（プロンプトはモデルごとに壊れ方が違う）:

- **プレースホルダをそのまま返すモデルがある。** 並べ替え抽出の形式を
  `{"属性名": "最大"}` と書いていたとき、qwen2.5 は temperature 0 で毎回
  `{"属性名": "最大"}` を返し、並べ替えが無効になっていた（llama3.1 は置き換える
  ため気づけない）。キーの決め方は文で説明し、例は架空の属性
  （`example_kg`）で示す（`ingest/conditions.py` の `_ranking_prompt`）。
- **「同じ値の製品が複数あるときは全部挙げる」の一文で両モデルが改善した。**
  qwen2.5 は 0/4 → 3/4、llama3.1 は 3/4 → 4/4。同点の2機種のうち1つしか
  挙げないことがあったため。

## 既知の制約

- **検索はベクトルとBM25のハイブリッドで、採否を決めるしきい値は1つだけである。**
  `ingest/lexical.py` が文字bigramの自前実装（外部依存なし）でBM25の転置索引を組み、
  `ingest/retrieval.py` がベクトル検索の結果とRRF（Reciprocal Rank Fusion）で融合する。
  文字bigramを使うのは、形態素解析器だと辞書に無い語で分割位置が変わり、「UD-0900i」の
  ような型番や新しい専門用語ほど問い合わせ文と本文で分割がずれてしまうためである。
  採否の判定は `RELEVANCE_THRESHOLD` の1つだけで行い、BM25スコアに数値の下限
  （フロア）は設けていない。方式は「圏内ゲート」で、ベクトル側の候補が1件でも
  `RELEVANCE_THRESHOLD` 以内にあればその質問は資料で答えられる（圏内）とみなし、
  BM25側のヒットはスコアを問わず採用する。1件も無ければ何も返さない。
  数値のBM25フロアを見送ったのは、BM25スコアが正規化されておらずクエリ長にほぼ
  比例して伸びるためである。`scripts/check_retrieval.py` の実測では、長い圏外質問
  「今日の東京の天気を教えてください」が29.87、短い圏内質問「ファインチューニング」が
  35.93で、差はわずか6.06しかなく、これより長い圏外質問が1つ来るだけで逆転しうる。
  一方で距離は、関連する質問の最大距離0.456、圏外の質問の最小距離0.522
  （bge-m3 / 496チャンク時点の実測。社内文書と製品カタログが混在した状態で、
  機種の照会と条件による絞り込みの両方を含む質問で測定）ときれいに分離しており、
  こちらを関門にするほうが堅い。しかし「こんにちは」のような意味的に空な挨拶は、
  これとは切り分けられない（実測距離0.353、コーパスの重心付近に埋め込まれるため
  1件ヒットしてしまう）。これは構造的な限界であり、しきい値の調整では解決しない。
  代わりに `ingest/prompting.py` のプロンプトが、検索結果が質問に無関係なら回答に
  使わず「社内文書からは回答できない」旨を伝えるようモデルに明示的に指示することで
  対処している。
- **BM25インデックスはディスクへ永続化せず、起動のたびにDBから組み直す。** ファイルへ
  永続化すると、差分取り込みのたびにDBとファイルの両方を更新する二重管理になり、
  更新漏れがあっても例外が出ないまま検索結果だけが静かに古くなる。信頼できる情報源を
  ChromaDBひとつに保つため、`ingest/retrieval.py` の `build_index()` はプロセス起動時に
  コレクションの全チャンクからBM25インデックスをメモリ上に組み立て直す。
- **PPTXは1スライド1チャンクではなく、テキストボックス単位で分割する。** 実測では
  1スライドに複数の話題が同居し、チャンクのベクトルがスライド全体の平均に薄まって、
  その中の1話題を指す質問の順位を落としていた（`ingest/parsers/pptx_parser.py`）。
  この変更で43スライドが80チャンクになった（他形式のチャンク数は変わらない）。
  スライドの表題を分割後の全チャンクへ複写しており、1チャンクだけを見ても何の話か
  分かるようにしている。出典の形式は変わらず `スライド{n}` のままだが、1つのスライドが
  複数チャンクに分かれるため、同じスライド番号の出典が根拠に複数回現れることがある。
- **資料を入れ替えたら `scripts/check_retrieval.py` で両方の実測をやり直すこと。**
  ベクトルの距離もBM25のスコアもコーパスの中身に依存する。資料構成が変わったら実行し、
  ベクトル側の分離が保たれているか確認して、必要なら実測値の間に `RELEVANCE_THRESHOLD`
  を設定し直す（BM25にはフロアを設けていないため調整対象はこの1つだけである）。
  このスクリプトは「ファインチューニング」で スライド11 がBM25側の上位に入るかという
  回帰確認も同時に行う。
- **`scripts.ingest_source` の実行中は `chroma_db` を開く他のプロセスを一切起動しない
  こと。** `udemy1.py`〜`udemy3.py` もこのプロジェクトと同じ `chroma_db/` ディレクトリを
  共有している（コレクションは別だが、格納先のストアは同一）。ChromaDBの
  `PersistentClient` は複数プロセスからの同時書き込み・読み込みを想定しておらず、
  実際にStreamlit経由で起動していた `udemy3.py` のプロセスが `chroma_db` を開いたまま
  取り込みを実行したところ、`local_docs_v2` のベクトル（HNSW）インデックスだけが
  壊れる事故が発生した。症状は2通り観測している。1つはメタデータ層（チャンク本文・
  出典）は無傷のまま、ベクトル検索がどの質問でも直近に取り込んだ数ファイルの
  チャンクしか返さなくなるという静かな壊れ方。もう1つは `collection.count()` すら
  `chromadb.errors.InternalError`（`Error loading hnsw index`）で例外になる完全な
  読み込み不能で、この場合 `index_metadata.pickle` の `dimensionality` が `None` に
  なり、ベクトルセグメントの `max_seq_id` がメタデータセグメントより遅れていた。
  どちらも原因は同じ同時アクセスであり、どちらに遭遇しても復旧手順（コレクション
  削除＋全量再取り込み）は共通である。取り込み前に `Get-Process` 等でStreamlit
  （教材のものを含む）が起動していないことを必ず確認すること。
- **画像PDFのOCR結果には認識誤りが残る。** 唯一の画像PDF
  （`Claude_Code_法人導入ガイド_スライド.pdf`）から抽出した日本語には
  「デ プT」「口一カル」のような誤認識が含まれる。ベクトル検索自体はこの程度の
  ノイズを吸収して機能するが、OCR由来のチャンクを出典として引用する際は元のテキストが
  完全に正確ではないことを踏まえること。UI上ではOCR由来の出典に「（OCR）」と
  マークして区別している。
- このPCはGPUを使えないため、OCRを連続実行すると熱により約2.5倍遅くなる。全38ファイルの
  フルリビルドが実測で約24分かかったのもこの影響が大きい。
- **数値条件による絞り込みには次の限界がある。**
  - 絞り込みが効くのはフロントマターを持つMarkdownだけである。PDF・PPTX・DOCXは
    構造化された属性を持たないため対象外で、従来どおりベクトル検索で扱う。
  - 条件の抽出は `llama3.1:8b` に依存しており、不等号の向きを取り違える可能性がある
    （実測で `$lte` を `$gte` と返した例がある）。誤った向きのまま絞り込むと、
    例外は出ずに誤った一覧が根拠として使われる。
  - 配列属性（`tags` / `target_users`）では絞り込めない。ChromaDBの `where` が
    リストへの部分一致を扱えないため、取り込み時にメタデータから除外している。
  - 質問文に数値として書かれていない条件は採用しない（`ingest/conditions.py` の
    `_grounded`）。「大容量」のような程度の表現からモデルがしきい値をでっち上げる
    実測への対処であり、その副作用として漢数字（「二十六デシベル」）で書かれた条件は
    読み取れずベクトル検索へ落ちる。
  - 一覧そのものは条件に合う資料を全件そろえるが、**その一覧を読んで多段の推論を
    する部分は `llama3.1:8b` の能力に依存する。** 「条件に合う機種を挙げ、かつ片方の
    条件だけを満たさない機種の型番と理由も述べよ」という2つの問いを含む質問では、
    後半に答えられない（必要な行は一覧に並んでいる）。以前ここには「最大の洗濯容量と
    該当型番には正しく答えられた」と書いていたが、1回の試行を一般化した誤りだった
    （下記のとおり、素の表では8回中2回しか当たらない）。
  - **一覧にファイル名は載せない**（`ingest/catalog.py` の `_row`）。モデルは行を丸写し
    するので、載せると回答が「UD-1100S_spec_step3.md です」と、利用者には意味のない
    取り込み元の名前になる（旧形式では8回中8回）。型番と仕様書は1対1に対応するため、
    絞り込み経路の出典は型番が担う。散文チャンクを渡すベクトル検索経路は従来どおり
    ファイル名で出典を示す。

- **回答の言い回しはプロンプトでは制御できない。** `llama3.1:8b` は結論を
  「答え： 型番：UD-1100iE 達成率：125%」のように言い直す。これを指示で止めようとすると
  逆効果で、「結論は一度だけ簡潔に述べ、同じ内容を言い換えて繰り返さないでください」を
  足した版は7回中2回で型番そのものを答えられなくなり（「型番は出典されていません」）、
  「『答え：』のような要約行で繰り返してはいけません」と名指しで禁じた版は3回中1回で
  逆に「答え：」を出した。そのため表示側で行頭のラベルだけを機械的に落としている
  （`ingest/answer_text.py`）。中身は消さない。回答本体がその行にしか無い出力
  （「答え：省エネ基準達成率が125%の機種は、UD-1100iEです。」）があり、行ごと捨てると
  回答が消えるためである。

- **「最大の◯◯は」には探させず、並べ替えて先頭に置いて答えさせる。**
  `llama3.1:8b` は12行の表から最大値を見つけられない（素の表で8回中2回。外した6回は
  10.0kgを挙げて11.0kgを見落とす）。そこで質問から並べ替える属性を取り出し
  （`ingest/conditions.py` の `extract_ranking`）、その属性の降順に行を並べ、
  さらに**その属性を行の先頭カラムに出す**（`ingest/catalog.py`）。モデルには行の
  先頭を掴む癖があるので、掴む場所に答えを置く。列順まで直すのは、先頭の数値を
  容量として読むためである（アルファベット順では `drying_capacity_kg` が先に来て、
  6.0kgを洗濯容量として答えた）。回答の文章化はプロンプトの文例が受け持つ。
  この組み合わせで8回中7回が正答（2026-08-13実測。素の表の8回中2回から改善）。
  実測で分かった注意点:
  - 文例の型番と数値は架空（`AAA-000`）にしてある。実在の値を書くとそのまま答えに写る。
    プレースホルダの `◯◯` すら「最大◯◯kgです」と出力されたことがある。
  - 「指示だけ」では効かない。「文章で書き、行を貼り付けるな」だけのときは4回とも
    行の丸写しだった。文例を足して初めて4回とも文章になった。
  - 最大値の要約行（「washing_capacity_kg が最大なのは 11.0（…）」）を表の先頭に
    足す案は**逆効果**だった（8回中2回まで低下し、5回は設置できない機種を答えた）。
  - **条件から外れる機種（`exceeding`）はモデルに渡さない。** 「もっと大容量だが
    設置できない」機種を表に入れると、それを条件に合う機種として答えた。
    利用者には見せる価値があるので、画面の「絞り込んだ一覧」にだけ出している。
    そのため回答に「UD-1400Xは545mm必要なため設置不可」まで書かせることはできない。
- **議事録の「議題」と「次回会議の議題」を取り違えることがある**（実測で6回中1回）。
  第5回議事録には「●議題：会議準備サマリー機能の最終仕様について」（1件）と
  「●次回会議の議題：…」（2件）が並んでおり、まとめて3件として答えた例がある。
  対処を4通り試したが、いずれも現状（6回中5回正答）を上回らなかった（2026-08-13実測）。
  - 「『次回』『前回』など別の回を混ぜるな」と指示 → **0/6**。別の会議（第2回）の
    議題を答え始めた。否定形で「別の回」に触れると、そちらへ引っ張られる。
  - 「見出しを見分けて、質問された見出しだけを答えよ」と指示 → 5/6。変わらず。
  - **docxを「●」見出しごとのセクションに分割**（Markdownと同じ形。`＞ 議題` と
    出典に出るようにする）→ **0/8 に悪化**。検索は正しく「＞ 議題」を1位で引く
    （距離0.375）が、モデルは同時にヒットする「＞ 次回会議の議題」の箇条書き2件を
    選ぶ。文書まるごとを渡したほうが正しく読める。この変更は差し戻した。
  - 分割した上で見出し指示を足す → 1/6。
  llama3.1:8b の読解力の天井であり、プロンプトと分割では動かない。
- **追質問は直前の質問を継ぎ足して検索する**（`ingest/retrieval.py` の `contextual_query`）。
  「決定事項を教えてほしい」のような質問はそれ単独では検索できず、実測では上位4件が
  導入ガイドPDFと就業規則で埋まって議事録が1件も入らなかった（距離0.456〜0.459）。
  直前の質問を前に置くと第5回議事録が0.401で1位になり、決定事項そのものを答えられた
  （4回中3回。2026-08-13実測）。継ぎ足すのは直前の1問だけで、モデルへ渡す質問文は
  生のままである。話題が変わったときは継ぎ足した分が雑音になるが、実測では順位は
  保たれた（有給休暇の質問に会議の質問を継ぎ足しても就業規則が1位。距離は
  0.296→0.352に悪化）。LLMによる質問の書き換えを使わないのは、1問あたり数秒の
  追加コストを避けるためである。
