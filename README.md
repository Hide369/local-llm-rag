# ローカル文書RAGチャット

PDF・PowerPoint・Word・Markdown を完全ローカルでベクトルDBに取り込み、出典付きで回答するRAGチャット。
既定では外部サービスへの送信は一切行わない
（GPUを強化したい場合のみ、任意で「[ColabのL4 GPUに接続する](#colabのl4-gpuに接続する)」を使える）。
「運転音26dB以下で奥行き510mmに設置できる機種」のように数値条件を含む質問は、ベクトル検索ではなく
Markdownのフロントマター由来のメタデータで機械的に絞り込み、条件に合う資料を全件そろえた表から回答する。

## 必要なもの

- Python 3.13（`myvenv313`）
- Ollama（インストール直後の標準ポート `http://127.0.0.1:11434` で待ち受けていること）
- モデル: `ollama pull bge-m3`（埋め込み）と `ollama pull gpt-oss:20b`（回答生成）
  。生成モデルを別のものにするときは、pullしたうえで `rag_chat_app.py` の
  `MODELS` に追記する（下記「モデルの比較」参照）

### Ollamaの待ち受けポートについて

`ingest/embedder.py` の `DEFAULT_OLLAMA_HOST` はOllamaの標準ポート
`http://127.0.0.1:11434` に合わせてあるため、通常は何も設定せずに動く。
`ollama list` が応答すれば、そのOllamaに接続できる。

標準以外のポートで動かしている場合のみ、環境変数 `OLLAMA_HOST` で上書きする。
`http://` から書くこと（コードはこの値をそのままURLに埋め込む）。

```powershell
$env:OLLAMA_HOST="http://127.0.0.1:12000"
.\myvenv313\Scripts\python.exe -m scripts.ingest_source
```

`localhost` は使わないこと。Windowsでは先にIPv6の `::1` に解決され、
1リクエストあたり約2.1秒を浪費する（`127.0.0.1` なら約80ms）。

## 使い方

取り込みたい資料を `source/` に置く（`.pdf` / `.pptx` / `.docx` / `.xlsx` / `.md` / `.txt` /
`.png` / `.jpg` / `.jpeg` / `.drawio`）。
サブフォルダに入れてもよい。`source/` 配下は再帰的に走査される。
**サブフォルダに分類して置いてもよい**（例: `source/家電製品/*.md`）。再帰的に走査する。

画像ファイル（`.png` `.jpg` `.jpeg`）は1枚をそのまま1ユニットとして取り込む。`.drawio`
だけは他形式と扱いが違い、ラスタライズしてOCRにかけるのではなく、draw.ioのmxGraph
XMLから図形のラベル文字を直接読む（ラベルはすでに構造化されたテキストとしてファイル
の中にあり、画像化してから推測し直すのは手元の正解を捨てる遠回りだからである）。
そのぶん失うものもある。矢印の向きや囲みの入れ子までは復元できない（詳しくは
「既知の制約」）。

```powershell
# 初回の取り込み（実測 約24分。source/ 直下8ファイルとMarkdown 30ファイル、
# 計38ファイル・496チャンクを処理した。OCR 23ページが時間の大半を占める）
.\myvenv313\Scripts\python.exe -m scripts.ingest_source

# Markdownだけを取り直す（フロントマターを直したときなど。OCRを伴わないため数十秒）
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --force --only-suffix .md

# PPTXだけを取り直す（スライドの分割ロジックを直したときなど）
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --force --only-suffix .pptx

# PDF/PPTX内の図・写真もVLMで説明文化する（大幅に時間が伸びる。事前に
# ollama pull qwen2.5vl:7b が必要。ColabのL4に接続していればそちらで処理される）
# チャット画面からの取り込みはこれを常に行う（下の「図表の説明文化」参照）。
# CLIで選べるようにしてあるのは、初回の全量取り込みで外せるようにするためである
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --with-vlm

# チャットを起動する
.\myvenv313\Scripts\python.exe -m streamlit run rag_chat_app.py
```

検索結果は常にリランカー（`bge-reranker-v2-m3` のONNX INT8版）による並べ替えを
通る。RRFで融合した上位8件を測り直すもので、1問あたり約1.3秒（i5-1240Pでの実測。
8候補の中央値）増える。画面から切ることはできない。使うかどうかを判断する材料が
画面に無く、外したままにすれば並べ替えが黙って落ちるだけだったためである（図表の
説明文化を自動にしたのと同じ理由）。

モデルが用意できないとき（初回の570MBを取得できないなど）は**検索を止めない**。
並べ替えずに検索し、その理由をサイドバーに出す。並べ替えは順序を良くするもので
あって、検索が成立する条件ではない。

初回のみモデルの取得に570MB・約1分かかる（`huggingface_hub` の既定キャッシュに
入る）。推論はOCRと同じ `onnxruntime` を使う。`tokenizers` と `huggingface_hub` は
かつてchromadbが依存として持ち込んでいたが、chromadbを外したので
`requirements.txt` で明示している。

`--only-suffix` を指定したときは孤児削除（`source/` から消えた資料をDBからも消す処理）を
行わない。対象外の拡張子のファイルがすべて孤児と判定され、他形式のチャンクが丸ごと
消えてしまうためである。

2回目以降はファイルのハッシュを見て変更分だけを処理するため数秒で終わる。
UIサイドバーの「差分を取り込む」も同じ処理を呼ぶ。

### 図表の説明文化（VLM）とOCR

対象はPDF/PPTXの埋め込み画像だけではない。DOCXの埋め込み画像、XLSXに貼り付けた
スクリーンショット、Markdownが `![alt](path)` で参照する画像、`.png`/`.jpg`/`.jpeg`
単体のすべてが同じ経路（`ingest/image_text.py` の `describe_image()`）を通る。
VLMの説明文（`[図の説明] `）とOCRで読んだ文字（`[画像内の文字] `）は独立に実行し、
片方が失敗してももう片方の結果は残す（Ollamaが止まっているだけでOCRの読めた文字
まで捨てることになるのを避けるため）。埋め込み画像にもOCRを通すのはこの版からで、
以前はVLMの説明文しか付かなかった。

ただしPDF/PPTX/DOCX/XLSX/Markdownでは、文書中の**埋め込み画像を読みに行くかどうか
自体**がVLM（`caption_image`）を使える場合に限られる。「この資料は画像を含むか」を
判定してから走査を分けるのではなく、VLMが使えなければ画像走査そのものを省く実装に
なっているためで、`describe_image()` はOCR単体でも呼び出せる作りだが現状そちらを
渡す経路はテスト以外に無い。したがってVLMが使えないときはこれらの形式の埋め込み
画像には説明もOCRも付かない（本文だけは従来どおり取り込まれる）。
`.png`/`.jpg`/`.jpeg` 単体はこの限りではない。ファイルそのものが画像であり
「画像を含むかどうか」を判定する必要が無いため、VLMの有無によらずOCRは常に試みる
（説明文のほうだけがVLMの有無に左右される）。画像PDFのページ全体OCR（「既知の
制約」参照）も同様にVLMの有無とは無関係に従来どおり動く。

チャット画面からの取り込み（「差分を取り込む」とアップロードの両方）は、図表の
説明文化を**常に行う**。以前はサイドバーのチェックボックスで選ばせていたが、
「この資料は画像を含むか」は資料を開かなければ分からず、外し忘れれば図表の説明が
黙って欠けるだけだった。パーサーは画像を見つけたときにしか
`caption_image` を呼ばないため、図の無い資料に渡しても取り込みは遅くならない。

VLMが使えないとき（`ollama pull qwen2.5vl:7b` がまだ、Ollamaが停止しているなど）は
**取り込みを止めない**。図表の説明を付けずに取り込み、その理由を画面に出す。
本文だけでも入れられるほうが役に立つためである。`caption_image` を渡したまま
失敗させる選択は取っていない。画像1枚ごとに4回のリトライ（1+2+4秒）が走り、
モデル未pullの環境では取り込みが極端に遅くなる（`ingest/vlm.py` の `_MAX_ATTEMPTS`）。
取り込み前に一度だけ `check_vlm()` で確かめ、駄目なら渡さない。

CLIの `--with-vlm` はそのまま残してある。初回の全量取り込み（38ファイル・約24分）に
205枚分の説明文化が上乗せされると現実的な待ち時間でなくなるため、ここだけは
選べるようにしてある。

**この版を導入したら、既存のPDF/PPTXは `--force` で1回入れ直す必要がある。**
以前から取り込み済みのPDF/PPTXのチャンクは、埋め込み画像のOCR（今回追加）を
まだ通っていない。ファイルの中身自体は変わっていないため、通常の差分取り込み
（ハッシュ判定でスキップする仕組み）ではこの変更は拾われない。反映するには
対象拡張子を指定して強制的に入れ直す。

```powershell
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --force --only-suffix .pdf --with-vlm
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --force --only-suffix .pptx --with-vlm
```

**この入れ直しにどれだけ待つかの実測**（2026-09-12、絞り込みなしで
`--force --with-vlm` を全44ファイル（.md 30 / .pptx 7 / .docx 5 / .pdf 2）に流した場合）:
Colab L4上のOllama（`bge-m3` の埋め込み、`qwen2.5vl:7b` のVLM、OCRも含めて全部リモート。
ngrok経由でローカルから接続）で **2340秒（39分0秒、02:33:45Z〜03:12:45Z、終了コード0）**。
812チャンク・33件のナビゲーション除外（7ファイル）に加えて、画像からは
「[図の説明] 」186行・「[画像内の文字] 」164行（9ファイル）が入った。186と164の差の
およそ20枚は、説明文はついたがOCRでは何も拾えなかった画像で、写真や装飾的な図に
ありがちな想定どおりの分布である。

この39分を読むときは2点とも数字と一緒に見ること。

- **このコーパスに `.xlsx`・`.drawio`・単体の `.png`/`.jpg`/`.jpeg` は一つも含まれていない。**
  つまり39分はPDF/PPTX/DOCXの埋め込み画像経路だけの実測で、スクリーンショットを
  貼り込んだExcelや`.drawio`図が混じるコーパスではこれより伸びる。
- **これはGPU（Colab L4、Ollamaはngrok経由でリモート接続）の数字であり、ローカルCPUの
  Ollamaで走らせた場合の数字ではない。** ローカルCPUで同じコマンドを流すと、この
  数字よりはるかに長く待つことになる。

### 画面から資料を取り込む（アップロード）

`source/` はサーバー側にあり、ブラウザーから使う利用者は資料を置けない。
サイドバーの「資料をアップロード」を押すとダイアログが開き、その場で選んだ
ファイルを取り込める。CLIと同じ解析・チャンク・埋め込みを通る。

`source/` の取り込みとは2点だけ振る舞いが違う。

- **原本を残さない。** 一時ファイルに書き出して取り込み、取り込みが終われば消える。
  DBに残るのはチャンクだけで、ストアを作り直したら再アップロードが必要になる。
- **資料キーに `uploads/` が付く。** `source/` 直下の同名資料を上書きしないためと、
  ダイアログの一覧・削除をキーの前方一致だけで済ませるため。出典表示にも
  `uploads/…` と出るので、由来はそのまま画面で分かる。

アップロードした資料は孤児削除の対象から外してある。外さないと、誰かが
「差分を取り込む」を押した瞬間に消える。消す時期はダイアログ内の一覧にある
削除ボタンで利用者が決める。

`source/` に `uploads/` という名前のサブフォルダを作ると資料キーが衝突するため、
取り込みは明示的なエラーで止まる。別の名前を使うこと。

なおDBもStreamlitプロセスも1つである。アップロードした資料は**全利用者の検索
対象になる**。利用者ごとの分離はない（[docs/server-deployment.md](docs/server-deployment.md)）。

ストアを作り直す場合はOCRを含む全ファイルを再処理するため、初回と同程度の時間
（約24分）がかかる。取り込み中にStreamlitを開いたままでもよい。SQLiteの
トランザクションが1資料の入れ替えを不可分にしており、最悪でも「database is locked」
という**表に出る**失敗になる。

### ナビゲーション用スライドの除外

取り込み時に、章扉・目次・締めの3種のスライドを自動で除外する。判定規則は
[ingest/navigation.py](ingest/navigation.py) にある。これらは短くキーワード密度が高いため
検索で上位に来やすいが、中身が無く質問に答える根拠にはならない。

除外した件数は取り込みの要約に出る（CLIの出力・Streamlitサイドバーの両方）。
見えないところで静かに消えることはない。全ユニットがナビゲーション判定になった
資料は、規則の誤爆を疑うべき兆候として、除外せずに警告だけ出す。

判定規則は取り込み済みのDBには遡って適用されない。ファイルの中身が変わらない限り
ハッシュ判定でスキップされるため、規則を足しただけでは既存のチャンクは更新されない。
反映するには対象の拡張子を指定して強制的に入れ直す。

```powershell
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --force --only-suffix .pptx
```

**除外の実測（2026-09-07）。** セミナー資料7本を入れ直した結果、DB内の総チャンク数は
予測どおり **570出現 / 本文512種**（608−38=570、538−26=512）になった。

回帰ケース「ファインチューニングについて教えてほしい」は **OK になった**。畳み込み後
（`feat/fold-duplicate-chunks` 時点）は上位3件が章扉・章扉・目次で全滅していたが、今回は
すべて中身のある本文に置き換わった。

ゲートの距離は、畳み込み後の関連の最大 0.420 / 圏外の最小 0.522 から
**関連の最大 0.455 / 圏外の最小 0.545** に動いた。しきい値0.50を挟んだ分離は保たれている
（余白は0.102→0.090とわずかに狭い）。

BM25の絶対値は大小関係が逆転した。圏外の最大 **30.46** が関連の最小 **18.96** を上回り、
BM25に床（フロア）を設けない判断（`ingest/retrieval.py`）が以前より強く裏づけられた。

詳しい実測手順と数値は
[.superpowers/sdd/2026-09-06-navigation-slides/task-6-measurements.md](.superpowers/sdd/2026-09-06-navigation-slides/task-6-measurements.md)
と設計書7節を参照。

### コマンドは必ず `python.exe -m` 経由で実行すること

`streamlit.exe` や `pytest.exe` のようなランチャーは、venv作成時のPython絶対パスを
実行ファイル内部に焼き込む。そのためプロジェクトフォルダを移動・改名すると
`Fatal error in launcher: Unable to create process using '...'` で起動しなくなる。

`python.exe` は自身の位置から環境を解決するため移動の影響を受けない。
`python.exe -m streamlit` の形ならランチャーを経由しないので常に動く。

（このリポジトリの `myvenv313` は実際に `09_RAG_FineTuning\04_...` で作成された後に
移動されており、`pyvenv.cfg` の `command` 行に当時のパスが残っている。
`python.exe` と `pythonw.exe` 以外の `Scripts\*.exe` は現在すべて壊れている。
`.exe` を使えるようにしたい場合は該当パッケージを
`python.exe -m pip install --force-reinstall --no-deps <package>` で入れ直す。）

## 技術ドキュメントの取り込み

公式ドキュメントを取り込み、モデルの古い知識ではなく取り込んだ記法で
コード例を答えさせる。社内資料とは**別のDB**（`docs_store.sqlite3`）に入れ、
画面のサイドバー「検索対象」で切り替える。

**どのライブラリに答えられるか**、各資料が実際に扱う範囲、対象にできない
ライブラリとその理由は [docs/コーディング対応ライブラリ.md](docs/コーディング対応ライブラリ.md)
にまとめてある。

```powershell
# 1. 取得（外部通信あり。docs_sources.toml に書かれたURLだけ）
.\myvenv313\Scripts\python.exe -m scripts.fetch_docs

# 2. 取り込み（Ollama への接続が要る）
.\myvenv313\Scripts\python.exe -m scripts.ingest_source --source-dir docs_source `
    --db docs_store.sqlite3 --keep-code-blocks
```

対象ライブラリは `docs_sources.toml` で管理する。追加するときは
`llms-full.txt` の URL を書くこと。**`llms.txt` は本文ではなくリンクの目次
である。** 実測（2026-09-12）: `docs.streamlit.io/llms.txt` は66,927バイト・
コードフェンス0個。対して `llms-full.txt` は1,927,203バイト・コードフェンス
1,877個・`## ` 見出し659個。目次を取り込んでも記法の質問には答えられない。

`llms-full.txt` を公開しているかどうかはライブラリごとに違う。実測
（2026-09-12）で確認できた範囲では、streamlit・langchain（LangChainのサイトが
`langchain-text-splitters` を含めて公開）・ollama・huggingface_hub・pymupdf は
公開している。fastapi・pytest・numpy は404で、対象にできない。

`--keep-code-blocks` はコードブロックを途中で割らずに1チャンクへ収める。
指定しないと、実測（2026-09-12、実際に取り込んだ `docs_source/streamlit.md`、
3,427チャンク）でチャンクの8.3%（284件）がフェンスの途中で割れる。
`--keep-code-blocks` を指定すると4,567チャンク中1.6%（74件）まで下がる。
区切り文字にフェンス（`` "\n```" ``）を足す案も試したが、実測では17.0%に
悪化したため採らなかった（`ingest/chunker.py` の `_split_keeping_code`）。
コードブロックには2,400字の上限があり、938ブロック中33個（3.5%、中央値122字・
平均465字・最大24,864字）がこれを超えて再分割される。
社内資料の取り込みでは `--keep-code-blocks` を指定しない（結果が変わる）。

`docs_source/` と `docs_store.sqlite3` は追跡しない。`source/` と
`vector_store.sqlite3` と同じく、いつでも取り直せるためである。

**実測した完了条件（2026-09-12）:**

- `python -m scripts.fetch_docs` は初回に streamlit 1,919,381B /
  langchain-text-splitters 1,003,315B / ollama 233,901B /
  huggingface_hub 1,785,858B / pymupdf 21,987B を書き出した。2回目の実行は
  5件とも「変更なし」と報告し、ファイルを書き換えなかった。
- `python -m scripts.ingest_source --source-dir docs_source --db
  docs_store.sqlite3 --keep-code-blocks` は、NVIDIA L4（ngrok経由で接続した
  Colab、5ファイル）で **11,993チャンク／5ファイルを724秒（12分4秒、
  14:03:47Z〜14:15:51Z）** で取り込んだ。内訳は huggingface_hub 4,913 /
  streamlit 4,567 / langchain-text-splitters 1,531 / ollama 898 /
  pymupdf 84。DB合計は出現11,993・本文10,879種。
- 社内資料の `vector_store.sqlite3` はこの取り込みの前後で1バイトも変わって
  いない（4,894,720バイト、更新日時も不変）。

### 日本語の質問と英語コーパスの言語不一致（検索クエリの英語翻訳）

Task 1〜6を終えた時点では、この機能は**日本語の質問に対して機能していなかった**。
コーパス（取り込んだ公式ドキュメント）は英語で書かれているのに対し、BM25側
（`ingest/lexical.py`）は日本語の文字bigramに合わせて調整済みである。実測
（gpt-oss:20b、`docs_store.sqlite3`、2026-09-12）:

| 質問 | 1位のヒット | リランカー |
|---|---|---|
| 「Streamlitのキャッシュはどう書く？」 | CLIコマンド `streamlit cache clear` | 0.06、以降 −3.33, −3.45, −4.66 |
| "How do I cache data in Streamlit?"（英語） | Cachingの節、続けて `@st.cache_data` の例 | 5.73 |
| `st.cache_data`（API名そのもの） | ほぼ完全一致 | 7.02 |

3問とも日本語質問ではモデルは「ドキュメントには記述がありません」と（正しく）
答えていたが、実際にはコーパス中に `cache_data` を含むチャンクが56件、
`cache_resource` が29件、`dialog` が47件あった。**検索が的外れだったのが
原因で、モデルの読解が誤っていたわけではない。**

そこで `ingest/query_translation.py` の `translate_query(query, ask)` が、
検索にだけ使う英語の検索クエリへ質問を翻訳する。**回答の生成は原文の日本語
質問のまま行う**（`rag_chat_app.py` は翻訳後のクエリを `search()` にだけ渡し、
`build_docs_prompt(question, hits)` には常に原文の `question` を渡す）。
これが無いと、コーパスと質問の言語が食い違ったまま検索が成立せず、
実装した機能全体が日本語話者に対して動かない。導入後の実測

## ColabのL4 GPUに接続する

ローカルPCのGPUが非力な場合、生成・埋め込みの両方をGoogle Colab（有料版のL4 GPU）上の
Ollamaに肩代わりさせられる。現在Colab側に置いているのは `gpt-oss:20b`（生成）・
`bge-m3`（埋め込み）・`qwen2.5vl:7b`（VLM）の3つで、合計してもL4の24GB VRAMに収まる。

仕組みは単純で、[ingest/embedder.py](ingest/embedder.py) と [rag_chat_app.py](rag_chat_app.py)
が接続先を環境変数 `OLLAMA_HOST` から読む既存の仕組みをそのまま使う。Colab側にOllamaと、
`X-API-Key` ヘッダーで認証する軽量なリバースプロキシを立て、ngrokでその1ポートだけを
外部公開する。

**手順**

1. [colab/run_ollama_server.ipynb](colab/run_ollama_server.ipynb) をGoogle Colabで開く
   （ランタイム → ランタイムのタイプを変更 → GPU: L4）
2. [ngrok](https://ngrok.com) の無料アカウントでauthtokenを取得しておく
3. ノートブックのセルを上から順に実行する。最後に表示される `OLLAMA_HOST`
   （ngrokの公開URL）と `OLLAMA_API_KEY` を控える
4. ローカルで `.env.example` を `.env` にコピーし、その2つの値を書き込む
5. いつも通り起動する

   ```powershell
   .\myvenv313\Scripts\python.exe -m streamlit run rag_chat_app.py
   ```

   サイドバーのモデル選択に関わらず、生成・埋め込みともにColab側のOllamaで処理される。

**知っておくこと**

- Colabのランタイムはアイドルや時間経過で切断される。常時稼働のAPIとしてではなく、
  使う時だけノートブックを起動する運用を前提にしている。切断されたら
  ノートブックを再実行し、新しいURLとAPIキーで `.env` を更新する。
- `X-API-Key` が一致しないリクエストはプロキシが401で拒否するが、ngrokのURLと
  APIキー自体は他人に共有しないこと（Colab上の資料・会話内容に到達できてしまう）。
- ローカルのOllamaに戻すには、`.env` の `OLLAMA_HOST` / `OLLAMA_API_KEY` を削除するか
  コメントアウトすればよい（既定値の `http://127.0.0.1:11434` に戻る）。

ベクトルは `vector_store.sqlite3`（bge-m3 / 1024次元 / cosine）に保存する。1つの
埋め込みモデルしか入らない設計で、モデルを差し替えるときはファイルごと消して
入れ直す（`ingest/vector_store.py` 参照）。現在のファイル数とチャンク数は
`scripts.ingest_source` が実行のたびに表示するので、そちらを正とすること。

**テーブルは2つに分かれている。** `chunks` が本文とベクトルを、`occurrences` が
資料ごとの出現とメタデータを持つ。同じ本文が複数の資料に現れるとき、本文は1行に
畳まれ、出典を複数持つ。メタデータは `source` `location` `file_hash` から製品属性まで
すべて資料固有なので、共有できるのは本文とベクトルだけである。

保存は出現単位のまま、検索だけが本文単位になる。`get()` は従来どおり
`source::location::index` のIDで出現を返すため、`ingest/catalog.py` は影響を受けない。
BM25索引とベクトル行列は `chunks` から作る。

**1テーブル時代のDBは自動では変換されない。** `open_store` が検出して停止するので、
`python -m scripts.migrate_store vector_store.sqlite3` を実行する。退避を作ってから
変換し、件数と孤児を検証してから確定する。再埋め込みは要らない。

`chroma_db/` には旧コレクション `local_docs`（nomic-embed-text / 768次元）が
残っているが、本システムはもう読み書きしない。Udemy教材の `udemy3.py` が使う。

## モデルの比較

回答生成のモデルはサイドバーのプルダウンで選ぶ。候補は `rag_chat_app.py` の
`MODELS` に列挙したモデルだけで、現在は `gpt-oss:20b` の1つ。接続先のOllamaに
置いてある生成モデルがこれだけだからである。別のモデルを使うときは、先に
`ollama pull` してから `MODELS` に追記する。

下の表は `qwen2.5:7b-instruct` と `llama3.1:8b` を同じ経路（条件抽出→絞り込み／
検索→生成）で4回ずつ実測した記録である（2026-08-13）。**どちらも現在は `MODELS` に
無いが、プロンプトの書き方を決めた根拠なので残してある。** `gpt-oss:20b` は
動作確認のみで、同じ形式の実測はまだ無い。

| | qwen2.5:7b-instruct | llama3.1:8b |
|---|---|---|
| 条件抽出のルーティング | 3/3 | 3/3 |
| 最大容量と該当型番（文章で正答） | 3/4 | 4/4 |
| 「議題」と「次回会議の議題」の区別 | 4/4 | 4/4 |
| 1回答あたりの時間 | 約20.8秒 | 約15.8秒 |

**この3項目では llama3.1:8b のほうが速く、精度も同等以上である。** qwen2.5 は
説明を厚く書く傾向がある。なお埋め込みは `bge-m3` で固定なので、生成モデルを
入れ替えてもDBの取り直しは要らない。

モデルを替えて分かったこと（プロンプトはモデルごとに壊れ方が違う）:

- **プレースホルダをそのまま返すモデルがある。** 並べ替え抽出の形式を
  `{"属性名": "最大"}` と書いていたとき、qwen2.5 は temperature 0 で毎回
  `{"属性名": "最大"}` を返し、並べ替えが無効になっていた（llama3.1 は置き換える
  ため気づけない）。キーの決め方は文で説明し、例は架空の属性
  （`example_kg`）で示す（`ingest/conditions.py` の `_ranking_prompt`）。
- **「同じ値の製品が複数あるときは全部挙げる」の一文で両モデルが改善した。**
  qwen2.5 は 0/4 → 3/4、llama3.1 は 3/4 → 4/4。同点の2機種のうち1つしか
  挙げないことがあったため。

## 既知の制約

以下で `llama3.1:8b` / `qwen2.5:7b-instruct` を名指ししている項目は、そのモデルで
取った実測の記録である。現在の `MODELS` は `gpt-oss:20b` だけなので**同じ症状が今も
出るとは限らない**が、プロンプトや設計定数がその形になっている理由なので残してある。
生成モデルを入れ替えたら測り直すこと。

- **検索はベクトルとBM25のハイブリッドで、採否を決めるしきい値は1つだけである。**
  `ingest/lexical.py` が文字bigramの自前実装（外部依存なし）でBM25の転置索引を組み、
  `ingest/retrieval.py` がベクトル検索の結果とRRF（Reciprocal Rank Fusion）で融合する。
  文字bigramを使うのは、形態素解析器だと辞書に無い語で分割位置が変わり、「UD-0900i」の
  ような型番や新しい専門用語ほど問い合わせ文と本文で分割がずれてしまうためである。
  採否の判定は `RELEVANCE_THRESHOLD` の1つだけで行い、BM25スコアに数値の下限
  （フロア）は設けていない。方式は「圏内ゲート」で、ベクトル側の候補が1件でも
  `RELEVANCE_THRESHOLD` 以内にあればその質問は資料で答えられる（圏内）とみなし、
  BM25側のヒットはスコアを問わず採用する。1件も無ければ何も返さない。
  数値のBM25フロアを見送ったのは、BM25スコアが正規化されておらずクエリ長にほぼ
  比例して伸びるためである。`scripts/check_retrieval.py` の実測では、長い圏外質問
  「今日の東京の天気を教えてください」が29.87、短い圏内質問「ファインチューニング」が
  35.93で、差はわずか6.06しかなく、これより長い圏外質問が1つ来るだけで逆転しうる
  状態だった（**2026-08-16 / 約460チャンク時点**）。
  そして**その逆転は2026-09-07・索引512件の実測で実際に起きている**。圏外の最大が
  30.46、関連の最小が18.96で、圏外側が上回った。床を設けていれば、この関連質問は
  落ちていた。
  一方で距離は、関連する質問の最大距離0.455、圏外の質問の最小距離0.545
  （bge-m3 / 2026-09-07・570出現・本文512種の実測）ときれいに分離しており、
  こちらを関門にするほうが堅い。しきい値0.50を挟んだこの分離は、
  496チャンク時点の0.456／0.522から測るたびに動いているが、向きは変わっていない。
  しかし「こんにちは」のような意味的に空な挨拶は、
  これとは切り分けられない（実測距離0.353、コーパスの重心付近に埋め込まれるため
  1件ヒットしてしまう）。これは構造的な限界であり、しきい値の調整では解決しない。
  代わりに `ingest/prompting.py` のプロンプトが、検索結果が質問に無関係なら回答に
  使わず「社内文書からは回答できない」旨を伝えるようモデルに明示的に指示することで
  対処している。
- **BM25インデックスはディスクへ永続化せず、起動のたびにDBから組み直す。** ファイルへ
  永続化すると、差分取り込みのたびにDBとファイルの両方を更新する二重管理になり、
  更新漏れがあっても例外が出ないまま検索結果だけが静かに古くなる。信頼できる情報源を
  ベクトルストアひとつに保つため、`ingest/retrieval.py` の `build_index()` は
  ストアの全チャンクからBM25インデックスをメモリ上に組み立て直す。
- **PPTXは1スライド1チャンクではなく、テキストボックス単位で分割する。** 実測では
  1スライドに複数の話題が同居し、チャンクのベクトルがスライド全体の平均に薄まって、
  その中の1話題を指す質問の順位を落としていた（`ingest/parsers/pptx_parser.py`）。
  この変更で43スライドが80チャンクになった（他形式のチャンク数は変わらない）。
  スライドの表題を分割後の全チャンクへ複写しており、1チャンクだけを見ても何の話か
  分かるようにしている。出典の形式は変わらず `スライド{n}` のままだが、1つのスライドが
  複数チャンクに分かれるため、同じスライド番号の出典が根拠に複数回現れることがある。
- **複数の資料が共有する記述には出典が複数付く。** 畳まれたチャンクは代表1件を名乗り、
  残りの数を添える（`CNN画像認識セミナー.pptx スライド25 ほか6資料`）。代表は
  `(source, location)` の昇順で決まるので、取り込み順を変えても入れ替わらない。
  出現が1件のチャンク（大半）の出典は従来と一字も変わらない。
  画面の詳細表示では出現をすべて並べるが、プロンプトに入るのは短い形だけである。
  7つのファイル名をモデルに読ませても、どれを引くかの判断を増やすだけで精度に寄与しない。
- **資料を入れ替えたら `scripts/check_retrieval.py` で両方の実測をやり直すこと。**
  ベクトルの距離もBM25のスコアもコーパスの中身に依存する。資料構成が変わったら実行し、
  ベクトル側の分離が保たれているか確認して、必要なら実測値の間に `RELEVANCE_THRESHOLD`
  を設定し直す（BM25にはフロアを設けていないため調整対象はこの1つだけである）。
  このスクリプトは「ファインチューニング」で スライド11 がBM25側の上位に入るかという
  回帰確認も同時に行う。
- **ベクトルの検索は総当たりである。** 近似最近傍の索引を持たず、全チャンクとの
  cosine距離を毎回計算する。現在の規模では1回0.19ミリ秒、100倍の規模でも8.93ミリ秒
  で、体感に影響しない（[設計書](docs/superpowers/specs/2026-09-05-sqlite-vector-store-design.md)
  2.2節の実測）。数万チャンクを超えるなら索引の導入を再検討すること。

  これは2026-09-05にChromaDBから移行した結果である。ChromaDBのHNSW索引は1日に2回
  壊れ、しかも `count()` は正しい件数を返し続けたため、**ベクトルが失われたことが
  次回起動まで露見しなかった**。壊れない最小構成を選び、索引そのものを無くした。
- **画像PDFのOCR結果には認識誤りが残る。** 唯一の画像PDF
  （`Claude_Code_法人導入ガイド_スライド.pdf`）から抽出した日本語には
  「デ プT」「口一カル」のような誤認識が含まれる。ベクトル検索自体はこの程度の
  ノイズを吸収して機能するが、OCR由来のチャンクを出典として引用する際は元のテキストが
  完全に正確ではないことを踏まえること。UI上ではOCR由来の出典に「（OCR）」と
  マークして区別している。
- **`.drawio` はラベル抽出であり、矢印の向きや囲みの入れ子（囲みの中に別の囲みが
  ある構造）は取れない。** mxGraphのXMLから図形のラベル文字列だけを読み順に並べて
  おり、画像化してOCRにかけていない。手元にある構造化テキストを画像へ変換して
  から推測し直すのは遠回りだからだが、その代わり図の見た目のつながりを聞く質問
  には答えられない（`ingest/parsers/drawio_parser.py`）。
- **`ws._images`（openpyxl）と `paragraph._p`（python-docx）は私的APIであり、
  ライブラリを上げたときに黙って空になりうる。** 公開APIには埋め込み画像を辿る
  口が無いため使っている。受け入れの根拠はテストが画像1枚を検出することだけで、
  上げた直後にそれが崩れても例外にはならず、埋め込み画像が静かに取り込まれなく
  なるだけである。なお `ws._images` は `read_only=True` のロードでは常に空になる
  ため、xlsx_parserは画像読み取り用の関数（VLM）が渡されたときだけブックをもう
  一度 `read_only=False` で読み込み直す（`ingest/parsers/xlsx_parser.py` の
  `_sheet_images`）。画面からの取り込みはVLMが使える限り常にその関数を渡すため、
  画像の有無によらず実質的に毎回この2回目の読み込みが発生する。
- **「装飾画像」とみなしてVLMの説明を捨てる閾値（OCRで10文字未満）は未実測の
  仮値である。** ロゴに含まれる社名の断片のような数文字が全チャンクに散らばる
  のを防ぐために置いたが、実データで調整していない
  （`ingest/image_text.py` の `MIN_OCR_CHARS_FOR_DECORATION`）。
- **Markdownが参照する画像は、画面からのアップロードでは見つからない。** ブラウザーの
  アップローダーはフォルダ構造を保持できず、選んだファイルをすべて同じ一時ディレクトリ
  に並べて書き出す。Markdownがサブフォルダ相対で参照する画像（例 `images/foo.png`）は
  この時点で置き場所が失われ、mdだけを送っても見つからない。取り込み自体は止めずに
  進み、見つからなかった参照先は取り込み結果の報告に列挙される
  （`IngestReport.missing_images`）。画像も検索対象にしたい場合は `source/` 側にmdと
  画像を一緒に置いて取り込むこと。
- **`IngestReport.missing_images` は、Markdownの画像走査そのものが行われたときしか
  埋まらない。** `--with-vlm` を付けない取り込みでは `md_parser` は画像を一切走査
  しないため（本文冒頭「対象はPDF/PPTXの埋め込み画像だけでは…」節参照）、この
  報告はいつも空になる。Streamlit経由の取り込みも、VLMに接続できないときは
  `caption_image=None` で走るため同じことが起きる。しかもGUI利用者がこれに
  遭遇しやすいのはまさにVLMが使えないとき（Ollama未起動・モデル未pull）であり、
  「画像参照が見つからなかった」という報告が出ないことを「見つかった」の意味に
  取り違えないこと。
- **Markdownの画像参照は、mdファイル自身があるディレクトリからの相対パスとして
  解決する。** `source/家電製品/手順書.md` が `../共通画像/図.png` を参照していても、
  `共通画像/` を親ディレクトリと共有する別の資料の画像を指しているつもりでは
  解決されず、`missing_images` に挙がる。仕様どおりの挙動だが（`md_parser._resolve`）、
  複数資料で画像を共有している構成では最初につまずきやすい点である。
- **DOCXのヘッダー・フッターに埋め込まれた画像は取り込まれない。** 表のセルの画像や
  浮動配置の画像は段落走査のあと `document.part.related_parts` から拾えるが、
  ヘッダー・フッターの画像はヘッダー/フッターパート配下にあり、`document.part`
  直下の `related_parts` には現れない（`ingest/parsers/docx_parser.py`）。
- このPCはGPUを使えないため、OCRを連続実行すると熱により約2.5倍遅くなる。OCRは
  ColabのL4へ逃がせない（rapidocrとonnxruntimeはローカルのCPUで動く）ので、
  全量取り込みの所要時間はここで決まる。実測は2通りある。埋め込みもローカルCPUで
  行っていた頃が38ファイルで約24分、埋め込みをColabのL4に逃がした2026-09-06が
  49ファイル・686チャンクで5分36秒だった。
- **重複チャンクの畳み込み（2026-09-06）の実測。** 608出現のうち21種類の本文が91行を
  占めており、畳んで **538本文（70行・11.5%削減）** になった。すべて資料をまたぐ定型
  スライド（「事前質問への回答」が7資料、「ご清聴ありがとうございました」が7資料、
  「おすすめの学習リソース」が5資料、「講師プロフィール」が4資料、章扉が2〜3資料）で、
  同一資料内の重複はゼロだった。
  BM25の上位は「ファインチューニングについて教えてほしい」で2〜6位が同一本文5件、
  スコアまで一致していた。畳んだ結果、期待するスライドは **10位から4位** に上がった
  （「ファインチューニング」単独は3位のまま）。
  **回帰ケースの判定は NG のまま残る。** 基準は上位3件だが、空いた枠を目次スライドが
  埋めるためである。畳んだ後の上位3件は章扉・定型スライド・目次で、3件とも中身のない
  ナビゲーション用スライドである。これは重複とは別の問題で、別ブランチで扱う。
  （追記・2026-09-07: `feat/drop-navigation-slides` でこの回帰ケースは OK になった。
  上記「ナビゲーション用スライドの除外」節の実測を参照。）
  **ゲートの距離は動いていない**（関連の最大 0.420 / 圏外の最小 0.522 で畳み込み前と同一）。
  7資料が共有するスライドを含む7ファイルを `--force` で入れ直しても、共有チャンクの
  出典は7件のまま残り、`integrity()` は `(0, 0)` を返した。
- **数値条件による絞り込みには次の限界がある。**
  - 絞り込みが効くのはフロントマターを持つMarkdownだけである。PDF・PPTX・DOCX・XLSX・TXTは
    構造化された属性を持たないため対象外で、従来どおりベクトル検索で扱う。
  - 条件の抽出は `llama3.1:8b` に依存しており、不等号の向きを取り違える可能性がある
    （実測で `$lte` を `$gte` と返した例がある）。誤った向きのまま絞り込むと、
    例外は出ずに誤った一覧が根拠として使われる。
  - 配列属性（`tags` / `target_users`）では絞り込めない。メタデータをスカラーだけの
    平らな辞書に保っており、`where` もリストへの部分一致を扱わないため、取り込み時に
    メタデータからは除外している。ただし値そのものは捨てず、キー名を伴わない形で
    チャンク本文へ載せているため、ベクトル検索とBM25の両方には効く
    （`ingest/parsers/md_parser.py` の `_array_values`）。「学生向け」のように本文へ
    一度も現れない語を索引に残すためである。絞り込めないのは条件式であって、
    検索そのものではない。

    実測（2026-09-06、`source/家電製品/` の30ファイル）。配列の値181種類のうち
    **89種類（49%）は、それを宣言している資料の本文に一度も現れない**。「一人暮らし」は
    8資料のタグにありながら本文には0回である。そうした語で引く10問の成績は、本文へ
    載せる前が「7問が上位4件に入り、うち5問が1位」、載せた後が「10問すべてが1位」だった。
    関連/圏外の距離（0.420 / 0.522）は前後で変わっておらず、他の検索を悪化させていない。
  - 質問文に数値として書かれていない条件は採用しない（`ingest/conditions.py` の
    `_grounded`）。「大容量」のような程度の表現からモデルがしきい値をでっち上げる
    実測への対処であり、その副作用として漢数字（「二十六デシベル」）で書かれた条件は
    読み取れずベクトル検索へ落ちる。
  - 一覧そのものは条件に合う資料を全件そろえるが、**その一覧を読んで多段の推論を
    する部分は `llama3.1:8b` の能力に依存する。** 「条件に合う機種を挙げ、かつ片方の
    条件だけを満たさない機種の型番と理由も述べよ」という2つの問いを含む質問では、
    後半に答えられない（必要な行は一覧に並んでいる）。以前ここには「最大の洗濯容量と
    該当型番には正しく答えられた」と書いていたが、1回の試行を一般化した誤りだった
    （下記のとおり、素の表では8回中2回しか当たらない）。
  - **一覧にファイル名は載せない**（`ingest/catalog.py` の `_row`）。モデルは行を丸写し
    するので、載せると回答が「UD-1100S_spec_step3.md です」と、利用者には意味のない
    取り込み元の名前になる（旧形式では8回中8回）。型番と仕様書は1対1に対応するため、
    絞り込み経路の出典は型番が担う。
  - **散文チャンクを渡すベクトル検索経路も、本文にはファイル名を出さない**
    （`ingest/prompting.py` の `build_prompt`）。文脈には `[出典]` を付けて渡すが、
    それはチャンクの境目を示すためで、本文に書くことは明示的に禁じている。
    出典は回答の下の「参考にした情報」を開くと出る。

- **回答の言い回しはプロンプトでは制御できない。** `llama3.1:8b` は結論を
  「答え： 型番：UD-1100iE 達成率：125%」のように言い直す。これを指示で止めようとすると
  逆効果で、「結論は一度だけ簡潔に述べ、同じ内容を言い換えて繰り返さないでください」を
  足した版は7回中2回で型番そのものを答えられなくなり（「型番は出典されていません」）、
  「『答え：』のような要約行で繰り返してはいけません」と名指しで禁じた版は3回中1回で
  逆に「答え：」を出した。そのため表示側で行頭のラベルだけを機械的に落としている
  （`ingest/answer_text.py`）。中身は消さない。回答本体がその行にしか無い出力
  （「答え：省エネ基準達成率が125%の機種は、UD-1100iEです。」）があり、行ごと捨てると
  回答が消えるためである。

  **一方で禁止形の指示が効いた例もある。** `ingest/prompting.py` の
  `build_prompt` / `build_docs_prompt` は「本文には出典を書かないでください」と
  禁止形で指示しており、2026-09-12にこの禁止を追加した後、`gpt-oss:20b` で
  生成した回答10件を実測したところ、本文にファイル名（出典）が出た例は
  **0件**だった。上の `llama3.1:8b` の逆効果はこの実測が誤りだったことを示す
  ものではなく、**モデルによって禁止形の効き方が違う**ことを示す事例として
  両方残す。実測は `gpt-oss:20b` のみで、`llama3.1:8b` / `qwen2.5:7b-instruct`
  では確認していない。

- **「最大の◯◯は」には探させず、並べ替えて先頭に置いて答えさせる。**
  `llama3.1:8b` は12行の表から最大値を見つけられない（素の表で8回中2回。外した6回は
  10.0kgを挙げて11.0kgを見落とす）。そこで質問から並べ替える属性を取り出し
  （`ingest/conditions.py` の `extract_ranking`）、その属性の降順に行を並べ、
  さらに**その属性を行の先頭カラムに出す**（`ingest/catalog.py`）。モデルには行の
  先頭を掴む癖があるので、掴む場所に答えを置く。列順まで直すのは、先頭の数値を
  容量として読むためである（アルファベット順では `drying_capacity_kg` が先に来て、
  6.0kgを洗濯容量として答えた）。回答の文章化はプロンプトの文例が受け持つ。
  この組み合わせで8回中7回が正答（2026-08-13実測。素の表の8回中2回から改善）。
  実測で分かった注意点:
  - 文例の型番と数値は架空（`AAA-000`）にしてある。実在の値を書くとそのまま答えに写る。
    プレースホルダの `◯◯` すら「最大◯◯kgです」と出力されたことがある。
  - 「指示だけ」では効かない。「文章で書き、行を貼り付けるな」だけのときは4回とも
    行の丸写しだった。文例を足して初めて4回とも文章になった。
  - 最大値の要約行（「washing_capacity_kg が最大なのは 11.0（…）」）を表の先頭に
    足す案は**逆効果**だった（8回中2回まで低下し、5回は設置できない機種を答えた）。
  - **条件から外れる機種（`exceeding`）はモデルに渡さない。** 「もっと大容量だが
    設置できない」機種を表に入れると、それを条件に合う機種として答えた。
    利用者には見せる価値があるので、画面の「絞り込んだ一覧」にだけ出している。
    そのため回答に「UD-1400Xは545mm必要なため設置不可」まで書かせることはできない。
- **議事録の「議題」と「次回会議の議題」を取り違えることがある**（実測で6回中1回）。
  第5回議事録には「●議題：会議準備サマリー機能の最終仕様について」（1件）と
  「●次回会議の議題：…」（2件）が並んでおり、まとめて3件として答えた例がある。
  対処を4通り試したが、いずれも現状（6回中5回正答）を上回らなかった（2026-08-13実測）。
  - 「『次回』『前回』など別の回を混ぜるな」と指示 → **0/6**。別の会議（第2回）の
    議題を答え始めた。否定形で「別の回」に触れると、そちらへ引っ張られる。
  - 「見出しを見分けて、質問された見出しだけを答えよ」と指示 → 5/6。変わらず。
  - **docxを「●」見出しごとのセクションに分割**（Markdownと同じ形。`＞ 議題` と
    出典に出るようにする）→ **0/8 に悪化**。検索は正しく「＞ 議題」を1位で引く
    （距離0.375）が、モデルは同時にヒットする「＞ 次回会議の議題」の箇条書き2件を
    選ぶ。文書まるごとを渡したほうが正しく読める。この変更は差し戻した。
  - 分割した上で見出し指示を足す → 1/6。
  llama3.1:8b の読解力の天井であり、プロンプトと分割では動かない。
- **追質問は直前の質問を継ぎ足して検索する**（`ingest/retrieval.py` の `contextual_query`）。
  「決定事項を教えてほしい」のような質問はそれ単独では検索できず、実測では上位4件が
  導入ガイドPDFと就業規則で埋まって議事録が1件も入らなかった（距離0.456〜0.459）。
  直前の質問を前に置くと第5回議事録が0.401で1位になり、決定事項そのものを答えられた
  （4回中3回。2026-08-13実測）。継ぎ足すのは直前の1問だけで、モデルへ渡す質問文は
  生のままである。話題が変わったときは継ぎ足した分が雑音になるが、実測では順位は
  保たれた（有給休暇の質問に会議の質問を継ぎ足しても就業規則が1位。距離は
  0.296→0.352に悪化）。LLMによる質問の書き換えを使わないのは、1問あたり数秒の
  追加コストを避けるためである。
- リランカーはRRF上位8件しか見ない。9位以降にある正解は救えない。効果は
  `python -m scripts.check_retrieval --with-reranker` で確認できる。
- `INTRA_OP_THREADS = 8` はi5-1240P（Pコア4＋Eコア8）固有の実測値である。
  既定の16論理コアはEコアを巻き込んで遅くなるため明示している。CPUが変われば
  測り直すこと。
- リランカーのONNXセッションは常駐し、メモリを約600MB使う。16GBのPCで
  `qwen3:32b` のような大きな生成モデルと併用するときは注意が要る。
