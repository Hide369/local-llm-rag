# 良いテストを書く

**このリファレンスは、次のときにロードします。** テストの作成または変更、モックの追加、または
テスト用のクリーンアップ/ヘルパー メソッドを追加します。

## 概要

特定のブレークを捕捉するためのテストが存在します。 2 つの原則がすべてを支配する
ここで：

```
1. Every test names the break it catches
2. Every test exercises the real thing
```

厳密な TDD では、最初に作成したテストと監視するテストの両方が自然に生成されます。
実際のコードに対して失敗することは、失敗する可能性があり、利益を得るだけであることがすでに証明されています。
実際の依存関係が遅いか外部のものであることが判明した場合のモック。

## 原則 1: 休憩に名前を付ける

テスト本体を作成する前に、次の質問に答えてください: **本番環境でどのような変更が必要か
このテストを失敗させます — そして、その変更はバグですか、それとも決定ですか?** テスト
間違ったブランチを捕まえたり、副作用を見逃したり、間違ったりすることでその場所を獲得します
口論、境界訴訟、または契約違反。

**期待値を個別に導き出します。** リテラルを使用し、手動でチェックします。
備品;リテラルを使用したテーブル駆動テスト `want` 値が優先されます
形。テスト対象のコード (またはそのヘルパー) によって計算される期待値
コードが何を実行してもパスします。

```typescript
// ❌ Mirror assertion: the same builder computes both sides — always true
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ Hand-derived literal
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**変化検出機能はありません。** 意図的な決定のみがテストに失敗する可能性がある場合 —
定数の値、正確なメッセージの文言、プライベート構造 — 起動されます
再設計中、バグを回避します。に依存する動作をテストする
決定: そうではない `expect(MAX_RETRIES).toBe(5)` しかし、「失敗した呼び出しは
5 回再試行しましたが、6 回目の試行は行われません。」

**テキストではなく動作** スクリプト、スキル、または設定であることをアサートします。
正確な行が含まれている場合は、そのソースがソースであることのみを証明します。走る
制御された入力に対するスクリプトと出力のアサート、副作用、または
終了コード。エージェントに指示する文書は消費者によってテストされます。
エージェントの行動 (スーパーパワー:ライティングスキル);人間のための散文は何の利益ももたらさない
まったくテスト。

**フレームワークではなく、コードです。** コードが作成するコントラクトをテストします。
その境界 - 登録するルート、発行するクエリ、ペイロード
あなたがプロデュースします。上流のメカニックは、メンテナーが書くためのテストです
(古典的: ルーターをアサートすると、登録されたハンドラーが呼び出されます。
これはフレームワークのテストであり、あなたのテストではありません）。上流の行動が真の場合
驚いたかもしれませんが、
仮定。同じ境界がコード内にも適用されます: コンストラクター、
ゲッター、定数、および簡単な転送は、次の場合にのみテストを取得します。
検証、正規化、デフォルト化、派生、強制、または副作用の原因 —
それ以外の場合は、それらに依存する最初の消費者に見える結果をアサートします。

### ゲート機能

```
BEFORE writing the test body:
  Name the production change that would make this test fail.

  Cannot name one            → redesign around an observable behavior
  "The source text changed"  → run the artifact and assert its effects
  Only intentional decisions → change detector; test the behavior
                               that depends on the decision

  Confirm the expected value is derived without the code under test.
  IF it reuses the code's logic or helpers:
    Replace it with a literal or hand-checked fixture
```

## 原則 2: 本物を練習する

**モックはアサーションを獲得しません。** モック アサーションは、モックが成功したときに合格します。
存在し、存在しない場合は失敗します。
コンポーネント。実際のコンポーネントの動作をアサートします。モックがあなたのものなら
チェックしているか、モックを解除するか、アサーションを削除します。

```typescript
// ✅ Real behavior
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ Mock existence
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**あなたの人間のパートナーの訂正:** 「私たちは、人間の行動をテストしているのですか？」
模擬？」

**適切なレベルでモックを作成します。** 実際のメソッドのあらゆる副作用を学習します。
交換する前に。遅い操作や外部操作を嘲笑し、何を保持するか
テストは実際のものに依存します。不明な場合は、実際のテストを実行してください
まず実装して、実際に何が起こるかを観察してください。

```typescript
// ❌ The mock swallows the config write that duplicate detection reads
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ Mock only the slow server startup; the config write stays real
vi.mock('MCPServerManager');
```

**double を具体的にします。** 引数、呼び出し回数、または順序付けが異なる場合
契約の一部であることを主張する — 何でも受け入れる偽物が検証する
何もない。各ブランチ (成功、エラー、不正な形式) に独自のフィクスチャを与えるか、
スパイなので、間違ったブランチでは期待を満たすことはできません。

**実際のデータを完全にミラーリングします。** 存在する完全な構造をモック化します。
実際には、テストで読み取ったフィールドだけでなく、文書化されたすべてのフィールドが対象となります。
部分モックは、ダウンストリーム コードが省略されたフィールドを読み取ると、サイレントに失敗します。
テストは成功しますが、統合は中断されます。

**プロダクション クラスはプロダクション メソッドのみを持ちます。** のみをクリーンアップします。
テストには、決してテスト ユーティリティとしてではなく、テスト ユーティリティ内での存続が必要です。 `destroy()` で
プロダクションクラス。質問: このメソッドはテストからのみ呼び出されますか?これはありますか
クラスはこのリソースのライフサイクルを所有していますか?間違った答え → テストユーティリティ。

**複雑なモックよりも実際のコンポーネントを優先します。** モックのセットアップが大きくなりすぎる場合
テストロジック、モックは実際のコンポーネントが持つメソッドをミス、またはテスト
モックが変更されると中断し、実際の統合テストに切り替える
コンポーネント。 **あなたの人間のパートナーの質問:** 「
ここで嘲笑する？」

### ゲート機能

```
BEFORE adding a mock or test helper:
  List the real method's side effects; keep the ones the test
  depends on real — mock the slow/external level below them.

  Mock responses mirror the complete real structure.

  A method only tests call lives in test utilities, not production.

  About to assert on the mock itself?
    Unmock it or delete the assertion.
```

## テストは実装に同梱されます

TDD サイクル — テストの失敗、最小限の実装、リファクタリング — とは
「完全」という意味です。動作に必要なテストのみを出荷します。
些細なコードと人間の散文は何も得られず、テストは満足するように書かれます
プロセスには永久にメンテナンス費用がかかります。

## 突然変異チェック

終了する前に、運用コードを精神的に変更します。少なくとも 1 つのテスト
現実的な各突然変異では失敗するはずです。

- 定数または引数が間違っています
- 間違ったブランチハンドラー
- 状態変化または副作用が欠落している
- 空またはデフォルトの戻り値
- ゼロ、空、nil、未承認、または不正な入力の検証が欠落している

何もキャッチできない突然変異は、その動作を保護されていないものとしてマークします。
トートロジーとしてテストします。

## クイックリファレンス

|あなたが... |する |
|---------------|-----|
|任意のテストを作成する |見つかった問題に名前を付けます。決定ではなくバグです。
|期待値を構築する |それを手動で導き出します。テスト対象のコードでは決して使用しないでください。
|スクリプトまたはドキュメントをテストする |それを実行し、そのコンシューマーの圧力テストを行います。そのテキストを決して grep しないでください。
|依存関係テストに手を伸ばす |文書化された仕組みではなく、境界契約をテストしてください。
|モック化された要素に対してアサートしたい |実際のコンポーネントをテストするか、モックを解除します。
|メソッドをモックしようとしています |その副作用について学びましょう。低速/外部レベルをモックする |
|模擬応答を作成する |実際の構造を完全に反映 |
|テストでのみクリーンアップが必要です |テストユーティリティに入れてください。
|モックセットアップバルーンを見る |実際のコンポーネントを使用した統合テストに切り替える |
|テスト ファイルを終了する |突然変異チェックを実行する |

## 警告サイン

- セットアップとアサーションは同じオブジェクトを共有し、同等性を保証します
- テストは、パニック、クラッシュ、またはセレクターの欠落によってのみ失敗する可能性があります
- テストはあらゆる意図的な変更で失敗し、偶発的な破損では失敗しません
- 期待値はループ、ビルダー、またはヘルパーの背後に隠されています
- テストはソース テキストを grep するか、削除されたシンボルが削除されたままであることをアサートします。
- フレームワークだけが残っている場合でもテストは重要です
- テストはカバレッジを目的として存在し、副作用や結果がないことを確認します
- アサーションは、 `*-mock` テスト ID、またはモックを削除すると失敗します
- メソッドはテストファイルからのみ呼び出されます
- モックのセットアップがテストの半分以上を占める場合、またはモックが必要な理由を説明できない
- 「念のために」嘲笑する
