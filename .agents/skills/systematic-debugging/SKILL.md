# 体系的なデバッグ

## 概要

**基本原則:** 修正を試みる前に、常に根本原因を見つけてください。症状の修正は失敗です。

**このプロセスの規定に違反することは、デバッグの精神に違反することになります。**

## 鉄の法則

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

フェーズ 1 が完了していない場合、修正を提案することはできません。

## いつ使用するか

あらゆる技術的な問題に使用します:
- テストの失敗
- 本番環境でのバグ
- 予期しない動作
- パフォーマンスの問題
- ビルドの失敗
- 統合の問題

**これは、次の場合に特に使用してください。**
- 時間的プレッシャーがある（緊急事態では推測が難しくなります）
- 「たった 1 つの簡単な修正」は当然のことのように思えます
- すでに複数の修正を試しています
- 以前の修正は機能しませんでした
- 問題を完全に理解していません

**次の場合はスキップしないでください**
- 問題は単純なようです (単純なバグにも根本原因があります)
- 急いでいます (急いでいるとやり直しが保証されます)
- マネージャーは今すぐ修正してほしいと考えています (スラッシングよりも体系的な方が早いです)

## 4 つのフェーズ

次のフェーズに進む前に、各フェーズを完了する必要があります。

### フェーズ 1: 根本原因の調査

**修正を試みる前に:**

1. **エラー メッセージをよく読んでください**
   - 過去のエラーや警告をスキップしないでください
   - 多くの場合、正確な解決策が含まれています
   - スタックトレースを完全に読み取ります
   - 行番号、ファイルパス、エラーコードをメモします。

2. **一貫した再現**
   - 確実にトリガーできますか?
   - 正確な手順は何ですか?
   - 毎回そうなんですか？
   - 再現できない場合 → 推測せずにさらにデータを収集する

3. **最近の変更を確認**
   - 何が変化してこのようなことが起こったのでしょうか?
   - Git diff、最近のコミット
   - 新しい依存関係、構成の変更
   - 環境の違い

4. **マルチコンポーネント システムの証拠を収集**

   **システムに複数のコンポーネントがある場合 (CI → ビルド → 署名、API → サービス → データベース):**

   **修正を提案する前に、診断機器を追加してください:**
   「」
   各コンポーネントの境界について:
     - コンポーネントに入力されるデータをログに記録します
     - どのようなデータがコンポーネントから出たかをログに記録します
     - 環境/構成の伝播を確認する
     - 各層の状態を確認する

   一度実行して、どこが壊れているかを示す証拠を収集します
   次に、証拠を分析して障害のあるコンポーネントを特定します
   次に、その特定のコンポーネントを調査します
   「」

   **例 (多層システム):**
   「」バッシュ
   # レイヤー 1: ワークフロー
   echo "=== ワークフローで利用可能なシークレット: ===
   エコー「IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}」

   # レイヤ 2: ビルド スクリプト
   echo "=== ビルド スクリプトの環境変数: ===
   環境 | grep ID ||エコー「IDENTITYが環境にありません」

   # レイヤ 3: 署名スクリプト
   echo "=== キーチェーンの状態: ===
   セキュリティリスト-キーチェーン
   セキュリティ検索-アイデンティティ -v

   # レイヤー 4: 実際の署名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   「」

   **これにより、次のことが明らかになります:** どのレイヤーが失敗するか (シークレット → ワークフロー ✓、ワークフロー → ビルド ✗)

5. **トレース データ フロー**

   **エラーがコールスタックの奥深くにある場合:**

   参照 `root-cause-tracing.md` 完全な逆方向トレース手法については、このディレクトリにあります。

   **クイックバージョン:**
   - 悪い価値はどこから生まれるのでしょうか?
   - これを悪い値と呼んだものは何ですか?
   - ソースが見つかるまで追跡を続けます
   - 症状ではなく原因で修正する

### フェーズ 2: パターン分析

**修正する前にパターンを見つけてください:**

1. **実用的な例を見つける**
   - 同じコードベース内で同様の動作するコードを見つける
   - 壊れたものと同じように動作するものは何ですか?

2. **参考資料との比較**
   - パターンを実装する場合は、リファレンス実装を完全に読んでください
   - 流し読みしないでください - すべての行を読んでください
   - 申請前にパターンを十分に理解してください

3. **相違点を特定する**
   - 働いているのと壊れているのは何が違うのですか？
   - どんなに小さいものであっても、すべての違いを列挙します
   - 「そんなことは関係ない」と思わないでください

4. **依存関係を理解する**
   - これには他にどのようなコンポーネントが必要ですか?
   - どのような設定、構成、環境ですか?
   - どのような仮定を立てますか?

### フェーズ 3: 仮説とテスト

**科学的方法:**

1. **単一の仮説を立てる**
   - 明確に述べます：「Y があるため、根本的な原因は X だと思います」
   - 書き留めてください
   - 曖昧ではなく具体的にしてください

2. **最小限のテスト**
   - 仮説をテストするために可能な限り小さな変更を加えます
   - 一度に 1 つの変数
   - 複数のことを一度に修正しないでください

3. **続行する前に確認してください**
   - うまくいきましたか？はい → フェーズ 4
   - うまくいかなかったのですか？新しい仮説を立てる
   - 修正を上に追加しないでください

4. **分からないとき**
   - 「X がわかりません」と言う
   - 知ったかぶりしないでください
   - 助けを求める
   - もっと研究してください

### フェーズ 4: 実装

**症状ではなく根本原因を修正してください:**

1. **失敗したテスト ケースの作成**
   - 可能な限り簡単な再現
   - 可能であれば自動テスト
   - フレームワークがない場合の 1 回限りのテスト スクリプト
   - 修正する前に必ず必要です
   - を使用します。 `superpowers:test-driven-development` 適切に失敗するテストを作成するスキル

2. **単一修正を実装**
   - 特定された根本原因に対処する
   - 一度に 1 つの変更
   - 「私がここにいる間」の改善はありません
   - バンドルされたリファクタリングなし

3. **修正の確認**
   - テストは合格しましたか?
   - 他に壊れたテストはありませんか?
   - 問題は実際に解決されましたか?
   - を使用します。 `superpowers:verification-before-completion` 成功を主張する前のスキル

4. **修正が機能しない場合**
   - 停止
   - カウント: 修正を何回試しましたか?
   - < 3 の場合: フェーズ 1 に戻り、新しい情報を使用して再分析します。
   - ** ≥ 3: 停止してアーキテクチャに質問します (下記のステップ 5)**
   - アーキテクチャに関する議論をせずに修正 #4 を試みないでください。

5. **3 つ以上の修正が失敗した場合: 質問のアーキテクチャ**

   **アーキテクチャ上の問題を示すパターン:**
   - それぞれの修正により、別の場所での新しい共有状態/結合/問題が明らかになります
   - 修正を実装するには「大規模なリファクタリング」が必要です
   - 修正が行われるたびに、別の場所に新しい症状が発生します

   **立ち止まって基本的な質問をしてください:**
   - このパターンは基本的に健全ですか?
   - 私たちは「まったくの惰性でそれに固執している」のでしょうか？
   - アーキテクチャをリファクタリングするべきでしょうか、それとも症状の修正を続けるべきでしょうか?

   **さらに修正を試みる前に、人間のパートナーと話し合ってください**

   これは失敗した仮説ではありません。これは間違ったアーキテクチャです。

## 危険信号 - 停止してプロセスに従ってください

次のように考えていることに気づいたら、
- 「今はすぐに解決します。後で調査してください。」
- 「X を変更して、それが機能するかどうかを確認してください。」
- 「複数の変更を追加し、テストを実行」
- 「テストをスキップしてください。手動で確認します」
- 「おそらく X です。修正させてください。」
- 「よくわかりませんが、これはうまくいくかもしれません」
- 「パターンには X とありますが、別の方法で調整します。」
- 「主な問題は次のとおりです: [調査せずに修正をリストします]」
- データフローを追跡する前にソリューションを提案する
- **「もう 1 回修正を試みる」(すでに 2 回以上試した場合)**
- **各修正により、別の場所で新たな問題が明らかになります**

**これらはすべて「停止」を意味します。フェーズ 1 に戻ります。**

**3 つ以上の修正が失敗した場合:** アーキテクチャを質問します (フェーズ 4.5 を参照)

## あなたの人間のパートナーがあなたが間違っていることを示している

**次のリダイレクトに注意してください:**
- 「そんなことは起こらないの？」 - 確認せずに推測した
- 「それは私たちに見せてくれますか...?」 - 証拠収集を追加する必要がありました
- 「推測はやめてください」 - あなたは理解せずに修正を提案しています
- 「これを徹底的に考えてください」 - 症状だけでなく根本的な問題を問う
- 「行き詰まってしまったのですか？」 (イライラ) - あなたのアプローチは機能していません

**これらが表示されたら:** 停止してください。フェーズ 1 に戻ります。

## 一般的な合理化

|言い訳 |現実 |
|--------|--------|
| 「問題は簡単です、プロセスは必要ありません」 |単純な問題にも根本原因があります。単純なバグの場合は処理が速くなります。 |
| 「緊急事態のため、手続きをする時間がありません」 |体系的なデバッグは、推測と確認によるスラッシングよりも高速です。 |
| 「まずこれを試してから調査してください」 |最初の修正はパターンを設定します。最初からちゃんとやれよ。 |
| 「修正が機能することを確認してからテストを書きます」 |テストされていない修正は定着しません。まずテストで証明してください。 |
| "一度に複数の修正を行うことで時間を節約できます" |何がうまくいったのかを切り分けることができません。新たなバグを引き起こす。 |
| 「参照が長すぎます。パターンを調整します」 |部分的に理解するとバグが保証されます。完全に読んでください。 |
| 「問題がわかりました。修正させてください。」 |症状の確認 ≠ 根本原因の理解。 |
| 「もう 1 回修正を試行」 (2 回以上失敗した後) | 3 つ以上の障害 = アーキテクチャ上の問題。質問パターン、もう修正しないでください。 |

## クイックリファレンス

|フェーズ |主な活動 |成功基準 |
|------|------|------|
| **1.根本原因** |エラーの読み取り、再現、変更の確認、証拠の収集 |何が、なぜなのかを理解する |
| **2.パターン** |実際の例を見つけて比較 |違いを特定する |
| **3.仮説** |フォーム理論、最小限のテスト |確認された仮説または新しい仮説 |
| **4.実装** |テストの作成、修正、検証 |バグは解決され、テストは合格しました |

## プロセスで「根本原因がない」ことが判明した場合

系統的な調査により、問題が真に環境的、タイミング依存、または外部的なものであることが判明した場合:

1. プロセスが完了しました
2. 調査内容を文書化する
3. 適切な処理（リトライ、タイムアウト、エラーメッセージ）を実装する
4.将来の調査のためにモニタリング/ログを追加する

**ただし:** 「根本原因がない」ケースの 95% は調査が不完全です。

## サポートテクニック

これらのテクニックは系統的なデバッグの一部であり、次のディレクトリで利用できます。

- **`root-cause-tracing.md`** - コールスタックを介してバグを逆方向に追跡し、元のトリガーを見つける
- **`defense-in-depth.md`** - 根本原因を見つけた後、複数のレイヤーで検証を追加します
- **`condition-based-waiting.md`** - 任意のタイムアウトを条件ポーリングに置き換えます。
